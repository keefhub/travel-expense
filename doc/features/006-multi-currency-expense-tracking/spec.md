## 1. Business analysis — BA

### 1.1 Purpose

A traveller spends in more than their trip's home currency — a taxi paid in JPY while the trip currency is SGD, for example. The app must accept and store expenses in whatever currency the traveller actually paid, without forcing an exchange rate at the moment of entry, and must still let the traveller see a meaningful, honest total: broken down by original currency always, and converted into the trip currency whenever enough rate information is available. When it isn't available, the app must say so rather than show a silently wrong (or silently blank) number.

### 1.2 Actors & preconditions

- **Actor**: the traveller (single-user, single active trip — OVERVIEW §1).
- **Preconditions**: an active trip exists with a trip currency (feature 001/002/003); at least one category exists (feature 010) so an expense can be recorded (feature 005) at all. Scenarios 3–5 additionally presuppose one or more expenses already recorded, at least one of them in a non-trip currency.

### 1.4 Data touched

- **Expense** (read) — `currency`, `amount` fields, already captured by feature 005.
- **ExchangeRate** (read/write) — `{ currency, rate }`, already defined and persisted by feature 012 (`lib/types.ts`, `lib/storage.ts`), but with no producer or consumer yet — this feature is the first to read and write it.
- **Trip** (read) — `currency`, to know which currency needs no rate.

### 1.5 Edge cases & negative paths

- No expenses recorded yet → nothing to group; no currency-totals section is shown. `[derived]`
- All recorded expenses are in the trip currency → one group, no missing rate is possible, converted total equals the total. `[derived]`
- A rate is entered as zero, negative, or non-numeric → rejected; no rate is stored for that currency. `[derived]`
- The user enters a rate for the currency that already matches the trip currency → not meaningful (BR-006-11 already treats it as rate 1); the entry is rejected rather than silently stored and ignored. `[derived]`
- The user re-enters a rate for a currency that already has one → the new value replaces the old one (BR-006-12). `[derived]`
- Multiple non-trip currencies are in use and only some have rates → totals by currency still show all of them (BR-006-09); the converted total is marked incomplete and names the currencies still missing a rate (BR-006-10). `[in spec]`

### 1.6 Out of scope

- Automatic or live exchange-rate lookups — OVERVIEW §2 states rates are fixed and manually entered; this feature does not fetch rates from anywhere.
- The full Exchange Rate Management page (viewing, editing, and deleting every stored rate in one place) — that is feature 007. This feature only needs entering and storing a rate to work end-to-end for its own scenarios.
- The full Home Dashboard layout (trip summary, budget vs. remaining, pie chart by category, last 5 transactions) — that is feature 009. This feature only adds the currency-totals section that 009 will later fold into the complete layout.
- Historical or time-varying exchange rates (e.g., "this rate applied only to expenses before date X") — only the current rate per currency is modeled, consistent with BR-006-12.
- Editing or deleting an already-recorded expense's currency or amount — no feature has introduced expense editing yet.

## 2. Technical specification — SA

### 2.1 Approach

Add one new pure module, `lib/currency.ts`, holding all multi-currency calculation logic: grouping expenses by currency, validating and applying a rate entry, and computing the converted total together with a completeness flag. No new storage key is needed — `travel-expense:exchange-rates` and its accessors (`getExchangeRates`/`saveExchangeRates`) were already added in feature 012, ahead of any feature that used them. Two existing placeholder screens each get a minimal, working surface wired to this module: `app/settings/page.tsx` gains a small rate-entry form, and `app/page.tsx` gains a "spending by currency" section. Both are explicitly scoped as minimal and are marked for expansion by features 007 (full rate management) and 009 (full dashboard) respectively, following the same placeholder-then-expand pattern already used for `app/settings/page.tsx` and the dashboard section of `app/page.tsx`.

## 7. Open questions & risks

1. **Rate history** (raised in Challenge 3): if a later feature needs to know which rate applied to a specific historical expense (rather than always using the current rate), `ExchangeRate { currency; rate }` would need a timestamp or a rate-per-expense snapshot. No current feature file asks for this; flagged only so it isn't a surprise later.
2. **Minimal UI durability** (raised in Challenge 1): the home-page currency-totals block and the settings rate-entry form added here are intentionally minimal and are expected to be replaced (not merely extended) when features 007 and 009 are implemented. `/writing-plans` for 007/009 should treat this feature's UI code as disposable scaffolding, not a base to preserve.
3. **Rounding/precision**: neither the feature file nor OVERVIEW specifies a rounding rule for converted amounts (e.g., `1500 * 0.01 = 15` exactly here, but real rates will produce longer decimals). This spec assumes standard IEEE-754 float arithmetic with 2-decimal display formatting (`toFixed(2)`, consistent with the `SGD 12.50` example in OVERVIEW §2), with no explicit rounding of the underlying stored/summed values. If financial-grade rounding matters, that should be confirmed before or during feature 008 (budget), where conversion also matters.
