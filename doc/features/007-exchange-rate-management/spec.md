## 1. Business analysis — BA

### 1.1 Purpose

A traveller who has recorded expenses in more than one currency needs a dedicated place to see
which currencies still need a conversion rate, enter one, and revisit it later to correct or update
it — not just a bare entry form with no memory of what's already been set. This feature turns
feature 006's minimal "enter a rate so the dashboard can convert something" mechanism into an actual
management screen: it scopes the currency choices to what the trip actually needs, shows the trip's
own currency for context, and lets a previously-entered rate be seen and changed, not just
overwritten blind.

### 1.2 Actors & preconditions

- **Actor:** the traveller.
- **Precondition:** an active trip exists (feature 001/002/003) with a trip currency. Scenarios 2–4
  additionally presuppose at least one expense recorded in a non-trip currency (feature 005/006).

### 1.3 Business rules

| ID | Rule | Source |
|---|---|---|
| BR-007-01 | Opening exchange rate settings shows the trip's own currency. | Scenario "User views exchange rate settings" |
| BR-007-02 | Opening exchange rate settings shows the set of currencies used by recorded expenses that differ from the trip currency — not the full list of app-supported currencies. | Scenario "User views exchange rate settings" |
| BR-007-03 | Entering a valid exchange rate (from a shown currency to the trip currency) and saving persists that rate to local storage. | Scenario "User adds an exchange rate" |
| BR-007-04 | Saving a rate makes the dashboard's converted totals reflect it. | Scenario "User adds an exchange rate" |
| BR-007-05 | If a rate already exists for a currency, selecting that currency shows the existing rate value, not a blank field — the user is editing a known value, not guessing whether one exists. | `[derived]` — Scenario "User updates an exchange rate" ("Given an exchange rate already exists... When the user changes the exchange rate value") presupposes the user can see the current value before changing it; nothing in this app persists a rate anywhere else the user could check it first. |
| BR-007-06 | Changing an existing rate's value and saving replaces the stored rate for that currency — it does not create a second entry. | Scenario "User updates an exchange rate" |
| BR-007-07 | After an update, the dashboard's converted totals are recalculated using the new rate. | Scenario "User updates an exchange rate" |
| BR-007-08 | Entering zero, a negative number, or a non-numeric value as the exchange rate shows a validation message and does not save. | Scenario "User enters an invalid exchange rate" |
| BR-007-09 | The trip's own currency is never offered as something to enter a rate for (a rate from a currency to itself is meaningless). | `[derived]` — BR-007-02 already limits the shown set to non-trip currencies; feature 006's existing `validateExchangeRateInput` independently rejects `currency === tripCurrency`, confirming this as an established rule, not a new one this feature introduces. |
| BR-007-10 | When no recorded expense uses a currency other than the trip currency yet, the settings screen says so rather than showing an empty, unexplained control. | `[derived]` — design.md's own "Empty states: every list gets a short plain sentence" rule, applied to BR-007-02's now-currency-scoped list, which can legitimately be empty (a trip with only trip-currency expenses, or no expenses yet). |

### 1.4 Data touched

- **Reads:** the active `Trip` (for its currency), the `Expense` list (to derive which non-trip
  currencies are in use), the `ExchangeRate` list (to check whether a selected currency already has
  a saved rate, and to know what to replace on save).
- **Writes:** the `ExchangeRate` list — replaces or appends exactly one entry per successful save
  (feature 006's `setExchangeRate` already guarantees at most one entry per currency; this feature
  does not change that contract).

### 1.5 Edge cases & negative paths

- No expense has been recorded in any non-trip currency yet — the currency selector has nothing to
  offer (BR-007-10). `[derived]`
- A currency was used in a past expense, a rate was set for it, and no expense in that currency
  exists anymore — cannot happen yet in this app (no way to delete an expense exists at any shipped
  feature), so this edge case is unreachable today; not designed for. `[derived, deferred]`
- Whitespace-only rate input (e.g. `"   "`) must be treated as blank, not accepted — matching this
  app's existing trim-then-check pattern (`lib/trip.ts`'s `validateTripForm`, `lib/expenses.ts`'s
  `validateExpenseForm`, feature 006's own `validateExchangeRateInput`). `[derived]`
- A storage failure on save must show a friendly error and preserve the user's entered rate input so
  they don't have to retype it — matching the precedent already established for every other form in
  this app (features 001–006). `[in spec via OVERVIEW's storage-error rule, applied here]`

### 1.6 Out of scope

- Deleting a saved exchange rate — no scenario describes this.
- Automatic/looked-up exchange rates — OVERVIEW confirms rates are "fixed and manually provided by
  the user," unchanged by this feature.
- Any change to how the dashboard computes or displays converted totals
  (`getConvertedTotals`/the "Spending by currency" section) — that's feature 006's territory; this
  feature only affects how a rate gets entered, seen, and updated.
- Any change to `lib/expenses.ts`, the record-expense form, or expense validation.
- A rates *list* view showing every currency that has ever had a rate set, independent of current
  expense usage — BR-007-02 scopes the shown currencies to what's actually in use now, not a
  historical ledger.

## 2. Technical specification — SA

### 2.1 Approach

Feature 006 already built the minimal version of this: `lib/currency.ts` exports
`validateExchangeRateInput` and `setExchangeRate` (both complete, unchanged by this feature), and
`components/ExchangeRateForm.tsx` renders a currency `<select>` (currently sourced from
`getSupportedCurrencies().filter(c => c !== trip.currency)` — every supported currency except the
trip's own) plus a rate `<input>`, calling those two functions on submit. This feature narrows and
completes that existing form rather than replacing it: (1) a new pure function,
`getCurrenciesNeedingRates(expenses, tripCurrency)`, replaces the currency source so the dropdown
only lists currencies actually used in recorded expenses (BR-007-02); (2) the rate `<input>` is
split into a small child component keyed by the selected currency
(`<RateInput key={currency} .../>`), so switching currencies remounts it with a lazily-initialized
value read from `getExchangeRates()` for that currency — showing the existing rate if one exists, or
blank if not (BR-007-05) — without introducing a `useEffect`-driven state sync, which this repo's
ESLint config (`react-hooks/set-state-in-effect`) would reject for a "reset local state when a prop
changes" pattern; the `key`-remount idiom is the correct React-native way to do this and needs no
effect at all; (3) `app/settings/page.tsx` gains one line displaying the trip currency (BR-007-01, a
page-level concern, not the form's).

### 2.2 Design elements

| ID | Element | Satisfies |
|---|---|---|
| TS-007-01 | `lib/currency.ts` — new `getCurrenciesNeedingRates(expenses: Expense[], tripCurrency: string): string[]`. Pure function: derives the deduplicated, sorted set of `expense.currency` values present in `expenses` that are not equal to `tripCurrency`. Reuses the same dedup approach as the existing `getExpenseTotalsByCurrency` (a `Set`/`Map` over `expense.currency`, filtered and sorted) — additive only, no existing export's behavior changes. | BR-007-02, BR-007-09 |
| TS-007-02 | `components/ExchangeRateForm.tsx` — change the `currencyOptions` source from `getSupportedCurrencies().filter((c) => c !== trip.currency)` to `getCurrenciesNeedingRates(getExpenses(), trip.currency)`. When this list is empty, render a short plain sentence ("No other currencies recorded yet.") instead of an empty `<select>`, and do not render the rate input/submit button at all in that state. | BR-007-02, BR-007-10 |
| TS-007-03 | `components/ExchangeRateForm.tsx` — extract the rate-input/error/saved-message portion of the form into a new inner component, `RateInput`, taking `{ currency: string; tripCurrency: string }` props. Rendered by the parent as `<RateInput key={currency} currency={currency} tripCurrency={trip.currency} />` — the `key` forces React to unmount and remount `RateInput` (resetting all of its local state) whenever the selected `currency` changes, which is what makes TS-007-04's lazy initializer read the right currency's existing rate on every currency switch without any effect. | BR-007-05 (groundwork) |
| TS-007-04 | `RateInput`'s rate-input state is initialized via `useState(() => { const existing = getExchangeRates().find(r => r.currency === currency); return existing ? String(existing.rate) : ""; })` — a one-time, mount-time read (safe: `RateInput` remounts fresh on every currency change per TS-007-03, so "mount-time" here means "every time the user switches currency," which is exactly when the displayed value needs to change). | BR-007-05 |
| TS-007-05 | `RateInput`'s submit handler is otherwise unchanged from the current `ExchangeRateForm`'s: calls `validateExchangeRateInput(currency, rateInput, tripCurrency)` (feature 006, unchanged), and on success `saveExchangeRates(setExchangeRate(getExchangeRates(), currency, Number(rateInput.trim())))` (feature 006's functions, unchanged — `setExchangeRate` already replaces any existing entry for `currency`, satisfying BR-007-06 with no new code). A `storage-error` (a failed `SaveResult`) shows the friendly message and leaves `rateInput` exactly as the user typed it — no reset, matching this app's existing storage-error-preserves-input precedent. | BR-007-03, 04, 06, 07, 08, and the §1.5 storage-error edge case |
| TS-007-06 | `app/settings/page.tsx` — add one line displaying the trip's currency (e.g. `Trip currency: {trip.currency}`) above `<ExchangeRateForm trip={trip} />`. | BR-007-01 |

### 2.6 Non-functional notes

- **Hydration safety:** `app/settings/page.tsx` already follows the established
  `useSyncExternalStore`-over-a-per-mount-store pattern (feature 006) — this feature's one added
  line reads `trip.currency` from already-resolved state, not from storage directly, so no new
  hydration risk.
- **No `useEffect` for state sync:** the `key={currency}`-remount idiom (TS-007-03) is used
  specifically to avoid a `useEffect` that would call `setRateInput(...)` in response to a `currency`
  change, which this repo's ESLint config (`react-hooks/set-state-in-effect`) rejects as a hard
  error — verified empirically against this exact rule while planning feature 005 and 011's plans in
  this same session.
- **Mobile-first form:** `RateInput` follows `design.md` §6 (label above input, `role="alert"`
  errors, `role="status"` success confirmation, `gap-1`/`gap-4` spacing), matching
  `ExchangeRateForm`'s existing markup style exactly — no new visual pattern introduced.
- **Offline:** no network calls; unaffected by the offline requirement.

## 3. BDD acceptance criteria — BA

```gherkin
# AC-007-01
Scenario: Opening exchange rate settings shows the trip currency
  Given the user has an active trip with currency "SGD"
  When the user opens exchange rate settings
  Then the trip currency "SGD" is displayed

# AC-007-02
Scenario: The currency selector lists only currencies used in recorded expenses
  Given the trip currency is "SGD"
  And the user has recorded expenses in "JPY" and "USD", and none in any other non-trip currency
  When the user opens exchange rate settings
  Then the currency selector offers exactly "JPY" and "USD"
  And "SGD" is not offered as a currency to set a rate for

# AC-007-03
Scenario: No non-trip-currency expenses shows an explanatory empty state
  Given the trip currency is "SGD"
  And every recorded expense (if any) is in "SGD"
  When the user opens exchange rate settings
  Then a short message explains that no other currencies have been recorded yet
  And no currency selector or rate input is shown

# AC-007-04
Scenario: A valid new rate is saved and reflected on the dashboard
  Given the user has recorded an expense in "JPY" and no rate exists for "JPY" yet
  When the user selects "JPY", enters a valid positive rate, and saves
  Then the rate is saved in local storage for "JPY"
  And the home dashboard's converted total reflects that rate

# AC-007-05
Scenario: Selecting a currency with an existing rate shows that rate
  Given a rate of 0.0091 already exists for "JPY" (trip currency "SGD")
  When the user selects "JPY" in exchange rate settings
  Then the rate field shows "0.0091", not blank

# AC-007-06
Scenario: Updating an existing rate replaces it, not duplicates it
  Given a rate of 0.0091 already exists for "JPY"
  When the user changes the value to 0.0095 and saves
  Then exactly one stored rate exists for "JPY", with value 0.0095
  And the home dashboard's converted total is recalculated using 0.0095

# AC-007-07
Scenario Outline: Invalid rate values are rejected
  Given the user is entering a rate for a currency shown in exchange rate settings
  When the user enters "<rate>" and saves
  Then a validation message is shown
  And no rate is saved for that currency

  Examples:
    | rate |
    | 0    |
    | -3   |
    | abc  |

# AC-007-08
Scenario: A storage failure preserves the entered rate
  Given saving will fail because storage is unavailable
  When the user enters a valid rate for a shown currency and saves
  Then a friendly storage error message is shown
  And the rate field still shows the value the user entered
  And no rate is saved
```

## 7. Open questions & risks

1. **(Challenge 3)** BR-007-05's "show the existing rate on selection" is a derived, not literal,
   requirement. Low-stakes if wrong — reverting to a blank-on-every-selection field is a small,
   isolated change confined to `RateInput`'s initializer.
2. The empty-state copy ("No other currencies recorded yet.") and the "Trip currency: {code}" label
   text (TS-007-02, TS-007-06) are SA-authored strings, not literal spec text — cheap to change if
   the user wants different wording.
3. **(§1.5, deferred)** The "rate exists but the currency is no longer used" scenario is unreachable
   today (no expense-delete feature exists) but would become relevant if a future feature adds one.
   Not designed for now; flagged so whoever builds expense-deletion knows to revisit this screen's
   currency-scoping rule (BR-007-02) at that point.
