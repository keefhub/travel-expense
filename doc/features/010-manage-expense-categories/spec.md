## 1. Business analysis — BA

### 1.1 Purpose

A traveller organizing trip expenses needs categories that fit their trip, not just the six fixed
defaults — and once a custom category exists, they need to fix a typo (rename) or remove one they
no longer use (delete), without able to touch the defaults, which stay stable for every trip.

### 1.2 Actors & preconditions

- **Actor:** the traveller, recording expenses against their one active trip.
- **Precondition (both surfaces):** an active trip exists. `/categories` is reached via the bottom
  nav (already wired, feature 015, complete) and — per this app's existing convention for every
  other nav destination (`/settings`, `/trip/edit`) — redirects to `/` when no trip is saved. The
  record-expense page (`/expenses/new`) already carries this same precondition (feature 005,
  complete).

### 1.4 Data touched

- **Categories** (custom only — defaults are code constants, never persisted; established fact,
  `lib/categories.ts:12-23`) — created, renamed, deleted.
- **Expenses** — read (to check whether a category is in use) and rewritten in bulk (to cascade a
  rename onto every expense using the old name) by the *already-shipped* `renameCategory`. This
  feature's UI work does not change that cascade's logic, only surfaces it.

### 1.5 Edge cases & negative paths

- **Blank or whitespace-only name in the Add-New modal** `[in spec, implied]` — `addCategory`
  already trims and rejects an empty result (`reason: "invalid"`, `lib/categories.ts:33-45`); the
  modal must surface that as a validation message, not a silent no-op or a crash.
- **Cancelling the Add-New modal** `[derived]` — must leave the expense form's currently selected
  category exactly as it was before the modal opened, and must not write anything to storage.
- **A storage failure while adding, renaming, or deleting** `[derived]` — OVERVIEW's confirmed
  requirement ("Local storage errors should show a user-friendly error message") applies here the
  same as everywhere else; `addCategory`/`renameCategory`/`deleteCategory` already return
  `{ ok: false, reason: "storage", error }` for this case (existing, shipped), so the UI's job is
  only to display `error`, not to invent new error handling.
- **Renaming a category to a name that only differs in case from another existing category** (e.g.
  "food" vs. "Food") `[in spec, implied]` — already rejected as a duplicate by `renameCategory`'s
  existing case-insensitive check (`lib/categories.ts:67-70`); no new design needed, verified by
  reading the existing implementation.
- **Renaming a category to its own current name** (no-op rename) `[derived]` — `renameCategory`'s
  duplicate check explicitly excludes the category's own current name
  (`c.name !== oldName`, `lib/categories.ts:68`), so this proceeds as a harmless rewrite, not a
  rejected duplicate; verified by reading the existing implementation, no new design needed.

### 1.6 Out of scope

- **Any change to `lib/categories.ts`'s existing functions** — `addCategory`, `renameCategory`,
  `deleteCategory`, `getAllCategories`, `isDefaultCategoryName`, `DEFAULT_CATEGORIES` are complete
  and unchanged by this spec.
- **A confirmation dialog before deleting a custom category** — not requested by any scenario (see
  §6 Challenge 1 for why this isn't being added speculatively).
- **An "add category" control anywhere other than the record-expense dropdown** — explicitly
  excluded from `/categories` by BR-010-09.
- **Reordering, grouping, icons, or colors for categories** — not requested.
- **Import/merge of categories, or bulk operations** — not requested.

## 2. Technical specification — SA

### 2.1 Approach

Two new small client components plug into the two places this feature needs UI: `AddCategoryModal`
(a self-contained, validating add-category dialog, invoked from the record-expense form) and
`CategoryManager` (a list of every category with rename/delete for custom ones, mounted by the
`/categories` route). Both call the already-shipped `lib/categories.ts` functions directly and
report success back to their caller via a callback — the same self-contained-validation pattern
`components/ExchangeRateForm.tsx`'s `RateInput` already uses for a very similar shape of problem
(collect one value, validate it against domain rules, save it, report success), not the
`NewTripConfirm`/`ResetAppDataConfirm` pattern (which is pure yes/no confirmation with no data entry
of its own — see §6 Challenge 2 for why that distinction matters here).

### 2.2 Design elements

- **TS-010-01** (satisfies BR-010-01) — no new code. `components/ExpenseForm.tsx`'s existing
  category `<select>`, backed by `getAllCategories()`, already renders the six defaults. Cited for
  traceability only.

- **TS-010-02** (satisfies BR-010-02, BR-010-03, BR-010-08, and the blank-name/cancel edge cases in
  §1.5) — add `components/AddCategoryModal.tsx`:
  ```ts
  export default function AddCategoryModal(props: {
    onAdded: (name: string) => void;
    onCancel: () => void;
  }): JSX.Element
  ```
  `'use client'` (it owns `useState` for the name input and an error message, matching every other
  hook-using standalone component file in this codebase — `TripSetupForm.tsx`/`TripEditForm.tsx`
  both declare their own `'use client'` despite only ever being mounted from an already-client
  parent). On submit: calls `addCategory(name)` (the raw, untrimmed input — `addCategory` already
  trims internally). On `{ ok: true }`: calls `onAdded(name.trim())` and does not manage its own
  visibility (the parent owns whether the modal is shown). On `{ ok: false }`: maps `reason` to a
  message (`"invalid"` → "Enter a category name.", `"duplicate"` → "This category already exists.",
  `"storage"` → the returned `error` string verbatim) and displays it `role="alert"`, keeping the
  modal open with the entered text preserved. Renders as a fixed-position overlay
  (`role="dialog"` `aria-modal="true"`) so it visually sits above the expense form without
  navigating away from it. A "Cancel" button calls `onCancel()` with no storage interaction.

- **TS-010-03** (satisfies BR-010-02, BR-010-08, and the cancel edge case in §1.5) — modify
  `components/ExpenseForm.tsx`:
  - The categories list becomes stateful: `const [categories, setCategories] = useState(() =>
    getAllCategories());` (was a plain, never-updated snapshot before this task).
  - Add `const [showAddCategory, setShowAddCategory] = useState(false);`.
  - Add a first `<option>` in the category `<select>`, before the existing `"Select a category"`
    placeholder, with a sentinel value (e.g. `"__add_new_category__"`) and label `"+ Add New"`.
  - The `<select>`'s `onChange`: if the new value equals the sentinel, call
    `setShowAddCategory(true)` and **do not** call `setValues(...)` for `category` — since
    `value={values.category}` still holds whatever it held before, React re-renders the (still
    controlled) `<select>` back to that same value on the very next render, so the sentinel is never
    actually committed to form state. This is the mechanism that satisfies "cancelling leaves the
    selected category unchanged" — there's nothing to revert, because nothing was ever set to the
    sentinel in the first place. Every other value takes the existing branch (`setValues({
    ...values, category: e.target.value })`).
  - When `showAddCategory` is `true`, render `<AddCategoryModal onAdded={...} onCancel={() =>
    setShowAddCategory(false)} />` as a sibling of the `<form>` (not replacing it — the underlying
    form's other field values must survive the modal being open, since the traveller may already
    have filled in amount/date/etc. before realizing they need a new category).
  - `onAdded={(name) => { setCategories(getAllCategories()); setValues({ ...values, category: name
    }); setShowAddCategory(false); }}` — refresh the list from storage (now authoritative, includes
    the new entry), select the new category on the form in progress, close the modal.

- **TS-010-04** (satisfies BR-010-04, BR-010-05, BR-010-06, BR-010-07's delete/rename half) — add
  `components/CategoryManager.tsx`:
  ```ts
  export default function CategoryManager(): JSX.Element
  ```
  `'use client'`. Owns: `categories` (`useState(() => getAllCategories())`, refreshed after every
  mutation), `editingName: string | null` (which custom category, by current name, is mid-rename —
  `null` when none), `renameValue: string`, `renameError: string | null`, `deleteError: string |
  null`. Renders a list; each category checked against `isDefaultCategoryName` — a default renders
  its name only (BR-010-07: no actions); a custom category not currently being edited renders its
  name plus "Rename" and "Delete" buttons; a custom category with `editingName === category.name`
  renders a text input (seeded with the current name) plus "Save"/"Cancel" instead. "Rename" sets
  `editingName`/seeds `renameValue`. "Save" calls `renameCategory(editingName, renameValue)`: on
  success, refreshes `categories` and clears `editingName`/`renameError`; on failure, sets
  `renameError` (shown inline for that row, `role="alert"`) and stays in edit mode. "Cancel" clears
  `editingName`/`renameError` with no storage call. "Delete" calls `deleteCategory(name)` directly —
  **no confirmation step** (§6 Challenge 1) — on success refreshes `categories`; on failure sets
  `deleteError`, shown once at the top of the list, `role="alert"`.

- **TS-010-05** (satisfies BR-010-09, and the trip precondition in §1.2) — modify
  `app/categories/page.tsx`: replace the placeholder with the same hydration-safe,
  trip-gated-redirect shell every other nav-destination route in this app already uses
  (`app/settings/page.tsx`/`app/trip/edit/page.tsx`'s `createTripStore` +
  `useSyncExternalStore` + a `useEffect` redirecting to `/` via `router.replace` when no trip is
  saved), mounting `CategoryManager` when a trip exists.

### 2.6 Non-functional notes

- **Mobile-first:** `AddCategoryModal` is a fixed, full-viewport overlay with a centered panel and
  page-gutter-consistent padding, so it works at phone width without needing its own breakpoint
  logic; its name input is `autoFocus`ed so a traveller can start typing immediately, matching this
  app's minimal-friction form conventions.
- **Local-storage failure mode:** fully covered by the already-shipped `CategoryMutationResult`
  `"storage"` reason — no new error-handling design needed, only surfacing what already exists.
- **Design-token note:** per this repo's established, repeatedly-applied practice (features 005
  through 014), new UI is built against the **committed** `app/globals.css` baseline
  (`--background`/`--foreground` only), not the unrelated, still-uncommitted dark-mode theming
  refactor sitting in the working tree. Where this codebase's own already-shipped code references a
  token beyond those two (e.g. `text-[var(--muted)]`, `divide-(--border)` in already-committed
  `Dashboard.tsx`/`app/settings/page.tsx`), that's a pre-existing, quietly-no-op gap this feature is
  not responsible for fixing — new code here may use the same tokens for visual structure
  consistency with its neighbors, understanding they render as unstyled until that refactor lands.
- **Next.js check:** no new Next.js API. Both new components are plain client components using
  `useState` and event handlers — the same pattern `TripSetupForm.tsx`/`ExchangeRateForm.tsx`
  already use. No vendored-doc lookup needed.

The blast radius is also categorically smaller — a category is a label, trivially recreated with the same name if deleted by mistake, whereas reset/new-trip destroy trip, expense, and rate data wholesale. | 2 | BA → SA | TS-010-02/TS-010-04 have the new components call `addCategory`/`renameCategory`/`deleteCategory` directly and manage their own validation error state, rather than following `NewTripConfirm`/`ResetAppDataConfirm`'s pattern of pure `onConfirm`/`onCancel` callbacks with zero internal storage logic. | 4 | BA → SA | Moving "add category" into the record-expense dropdown (lower friction, mid-task) could encourage more near-duplicate categories (e.g. "Food" and "Foods") than a deliberate, separate management page would.
