Task 2: [UI] — ExpenseForm wires "+ Add New" into the category dropdown
Completed: 2026-09-12
Commit: 1ba4518

Summary:
  Made ExpenseForm.tsx's categories list stateful, added a "+ Add New"
  first dropdown option, and mounted AddCategoryModal as a sibling of
  the expense form (never nested inside it). Selecting "+ Add New"
  opens the modal without committing to form state; adding a category
  refreshes the list and selects the new category. Documented in
  REFERENCE.md's ExpenseForm.tsx entry.

Key Decisions:
  - None beyond what the plan already specified verbatim, except the
    fix described below.

Deviations:
  - Gate B's first pass FAILED on a real bug (not a false positive this
    time): the original onChange handler detected "+ Add New" by
    comparing e.target.value against a sentinel string
    ("__add_new_category__"). Nothing prevented a traveller from
    naming an actual custom category exactly that string via
    AddCategoryModal (addCategory only rejects blank/duplicate names),
    which would then collide with the sentinel and make that one
    category permanently unselectable from the dropdown. Fixed by
    switching detection to e.target.selectedIndex === 0 (the "+ Add
    New" option is always rendered first), which cannot collide with
    any category name since it checks position, not value. The fix
    stayed entirely inside ExpenseForm.tsx, per the plan's negative
    constraint against modifying lib/categories.ts.
  - Re-running both gates after the fix (required since the fix
    touched the same file Gate A had already reviewed) surfaced a
    second, smaller gap: REFERENCE.md's ExpenseForm.tsx entry still
    described the old value-based sentinel detection instead of the
    new position-based one. The controller corrected this directly
    (a one-clause doc edit) rather than dispatching a third automated
    attempt, consistent with CLAUDE.md's outer-loop guidance to take
    over manually for a fully-diagnosed, mechanical follow-up rather
    than retry indefinitely. The correction was independently verified
    by reading the actual code (`selectedIndex`/`ADD_NEW_CATEGORY`
    usage) before committing.
  - Step 5's manual browser checks (5a-5f) could NOT be performed — no
    browser-automation tool exists in this environment. The
    implementer did the best available substitute: found a dev server
    already running, curled /expenses/new (200, no crash), and
    confirmed the served JS bundle actually contains the sentinel
    string and "+ Add New" text. Both review gates independently
    traced every scenario against the real code as the deepest
    available substitute. Marked "NOT PERFORMED" in plan.md rather
    than falsely ticked.
  - RESIDUAL GAP flagged to the user: Step 5's manual browser checks
    (defaults still listed, "+ Add New" ordering, opening it preserves
    the current selection, adding/selecting a unique category,
    duplicate/blank rejection, cancel leaves nothing changed, and the
    modal rendering above the bottom nav) should be run by a human in
    an actual browser before treating this task as fully verified
    end-to-end.

Files Changed:
  - components/ExpenseForm.tsx (modified — added the "+ Add New" flow)
  - REFERENCE.md (modified — one hunk, the ExpenseForm.tsx entry
    rewrite, including the controller's post-fix correction; isolated
    via `git add -p` from unrelated pre-existing uncommitted
    REFERENCE.md edits)

Verification:
  npx tsc --noEmit   exit 0, no output
  npm run lint       exit 0, no output
  npm run build      exit 0, same 8-route table (no new route)
  Manual browser checks (Step 5): NOT PERFORMED. No browser automation
    tool available in this environment. Partial substitute: dev server
    + curl + served-bundle grep confirming the change is live.

Review Gate — Spec:    PASS (attempt 1)
Review Gate — Quality: PASS (attempt 2 — see Deviations; attempt 1 found a real sentinel-
