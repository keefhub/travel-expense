  Two side effects of that typing, both benign and both verified by a gate: a body that parses to JSON
  literal `null` now returns 400 rather than throwing into the 500 path, and `rawBody ?? {}` is a

Review Gate — Spec:    PASS (attempt 1); PASS (attempt 2, after fix)
Review Gate — Quality: FAIL (attempt 1) -> fix -> PASS (attempt 2)

  Fix cycle 1 (both gates re-run, because the fix touched a file the passing gate had reviewed):
  the quality gate found that a `null` element in the shares array — e.g. {"shares":[null]} — passed
  the Array.isArray/length guard, then threw a TypeError on the property read inside the main
  try/catch, answering 500 "Could not save the expense." instead of 400 "Invalid expense data.".
  Fixed by filtering body.shares through a type predicate that keeps only genuine plain objects and
  returning 400 when the filtered length differs, before any property read. The plan's own step 4j
  throws identically, so this was a plan hole the implementer reproduced faithfully, not an
  implementer error; the affected step is struck in plan.md and the same warning was added to Task 5's
  equivalent step, which would otherwise inherit the hole. A gate re-verified that a well-formed
  payload is unaffected (the guard is unreachable for an all-object array).

  Non-blocking findings carried forward, not fixed (each is either outside this task's diff or
  mandated by the plan's own text):
  1. The cent-sum check is vacuous when amount * 100 overflows to Infinity: { amount: 1e307,
     shares: [{ participantId: null, amount: 9e306 }] } passes because Infinity !== Infinity is false.
     Both values are finite so Number.isFinite admits them. Fix would be a Number.isSafeInteger guard
     on totalCents (or bounding amount) — a new validation rule the plan does not specify.
  2. Shares are validated in integer cents but written unrounded, so a sub-cent pair such as
     0.001 + 9.999 against 10.00 passes and persists non-zero sub-cent shares. Same root cause logged
     under Task 3; the fix belongs in lib/sharedExpenses.ts (rounding the shares alone would be wrong
     when the expense amount is itself sub-cent).
  3. include: { shares: true } has no orderBy, so response share order is whatever Postgres returns;
     the participants GET orders explicitly by createdAt. Harmless while consumers key by
     participantId, noted only for symmetry with the 019 precedent.
