## 1. Business analysis — BA

### 1.1 Purpose

A shared trip's expenses need to record not just what was spent, but **who paid** and **who it
should be split among**, so that a later feature (021 — View Trip Balances) can compute who owes
whom. Today, an expense has no notion of a payer or a split; this feature adds that attribution
to the shared-trip expense-recording flow, while leaving a solo (unshared) trip's expense form
completely unchanged.

### 1.2 Actors & preconditions

- **Actor**: any current member of a shared trip — the trip creator, or a participant who joined
  via the trip's share link (feature 017). No login exists; identity is device-bound, exactly as
  in features 016–019.
- **Preconditions**: an active shared trip exists (a share link has been generated per feature
  016); the acting device is either the trip's creator (holds the trip's `creatorToken`) or a
  current participant (holds a `participantToken` for that trip, per feature 017/019).
- A **solo (unshared) trip** is also in scope, but only to confirm the negative case: its expense
  form must show no payer/split fields at all (Scenario "A solo trip's expense form has no payer
  or split fields").

### 1.3 Business rules

| ID | Rule | Source |
| --- | --- | --- |
| BR-020-01 | A shared-trip expense records exactly one payer, chosen from the trip's creator or its current participants. | Scenario "I record an expense split evenly among participants"; Assumption 3 |
| BR-020-02 | A shared-trip expense records a split-among set of one or more of the creator/participants, each assigned a share amount in the expense's own currency. | Scenario "I record an expense split evenly among participants"; Assumption 6 |
| BR-020-03 | Two split methods are available: **even** (shares computed automatically) and **exact** (each selected person's share is typed in). No percentage method exists. | Scenario "I split an expense by exact amounts instead of evenly"; Assumption 1 |
| BR-020-04 | Opening the expense form on a shared trip pre-selects the recording device's own identity as payer, and pre-selects every current participant (including the creator) in the split. | Scenario "Payer and split-among default to sensible values"; Assumption 3 |
| BR-020-05 | An even split's per-person shares are rounded to 2 decimal places and always sum to exactly the expense total; any rounding remainder is absorbed into one share rather than lost or spread silently. | Scenario "An uneven equal split rounds correctly"; Assumption 4 |
| BR-020-06 | An exact-amount split's entered shares must sum exactly to the expense total, or the form refuses to save and shows an error. | Scenario "Exact amounts that don't add up to the total are refused"; Assumption 5 |
| BR-020-07 | Saving is refused, with an error shown, if the split-among selection is empty — even if that means the payer themself was deselected. | Scenario "Saving with no one selected in the split is refused"; Assumption 6 |
| BR-020-08 | Switching the split method (even ↔ exact) recalculates the shares fresh; values entered/computed under the previous method are never carried over. | Scenario "Switching split method recalculates the shares"; Assumption 7 |
| BR-020-09 | A participant who has since left or been removed (feature 019) still appears by name as payer or split-member on any expense they were previously attributed to. | Scenario "A departed participant's name still appears on past attributions"; Assumption 9; feature 019 Assumption 1 |
| BR-020-10 | An existing shared-trip expense's payer and split-among attribution can be changed after the fact, and the change is saved. | Scenario "I edit an existing expense's payer or split"; Assumption 8 (narrowed — see §6 Challenge #1) |
| BR-020-11 | A solo (unshared) trip's expense form shows no payer or split-among fields at all — it is unchanged from feature 005. | Scenario "A solo trip's expense form has no payer or split fields"; Assumption 2 |
| BR-020-12 | If the server cannot be reached while saving a shared-trip expense, a friendly error is shown and no expense record is created. | Scenario "Saving fails when the server is unreachable" |
| BR-020-13 | Recording, viewing, or editing a shared-trip expense's attribution is only available to the trip's creator or one of its current participants. | [derived] — mirrors the existing auth pattern for every other shared-trip action (016/017/019); OVERVIEW §2 "identity-by-device... no login" |

### 1.4 Data touched

- **Expense (shared-trip)** — a new server-side record: the same fields feature 005 already
  defines (amount, currency, category, date, payment method, location, optional description),
  plus a payer and a set of per-person split shares. This is distinct from the existing
  **local-storage `Expense`** used by solo trips, which gains no new fields.
- **Trip participants** — read-only in this feature: the current creator/participant roster
  (feature 019) supplies the selectable payer/split options.
- **Split share** — new: one row per person included in an expense's split, recording who (or a
  name snapshot of who, once departed) and how much.

### 1.5 Edge cases & negative paths

- [in spec] Split-among selection ends up empty → refused (BR-020-07).
- [in spec] Exact amounts don't sum to the total → refused (BR-020-06).
- [in spec] Uneven even split (total not divisible by participant count) → rounds to 2dp, sums
  exactly (BR-020-05).
- [in spec] Switching split method discards the other method's values (BR-020-08).
- [in spec] A departed participant's name still shows on past attributions (BR-020-09).
- [in spec] Network failure while **saving** → friendly error, nothing created (BR-020-12).
- [derived] Network failure while **loading** the form (fetching the current participant roster,
  or fetching an existing expense to view/edit) — the Gherkin only covers a save-time failure;
  loading needs the same friendly-error treatment so the screen doesn't render a broken or empty
  participant list silently. Mirrors feature 019's identical "server unreachable" scenario for its
  own list load.
- [derived] A shared trip with **no joined participants yet** (creator only) — the payer and split
  default to the creator alone; a valid even split of 100% to the creator must still work.
- [derived] Editing an expense's attribution: the selectable payer/split options are **current**
  participants only. A participant who has since departed cannot be newly re-selected during an
  edit, even though their name still displays on the parts of the attribution that already
  reference them and weren't changed.
- [derived] A device that is neither the trip's creator nor a current participant reaches a
  shared-trip expense URL directly (e.g. a stale link, or a removed participant) — treated the
  same as every other shared-trip screen's stray-visitor case (019's `ManageParticipants`
  precedent): redirected home rather than shown any trip data.
- [derived] A selected participant's exact-mode share is entered as `0` — allowed (they remain
  part of the split, at zero); only a **negative** or non-numeric entry is invalid.

### 1.6 Out of scope

- Percentage-based splitting (Assumption 1 / Deferred).
- Computing or displaying running balances / who-owes-whom (feature 021).
- Marking any part of a split as settled (feature 022).
- Re-attributing a departed participant's past expenses to someone else.
- Concurrent edits to the same expense's attribution from two devices at once.
- Editing any field of a shared-trip expense **other than** payer/split (amount, category, date,
  payment method, location, description) — no such general edit capability exists anywhere in the
  app today; see §6 Challenge #1.
- A list or dashboard view of a shared trip's expenses — no such screen exists yet for shared
  trips (the solo-trip `Dashboard.tsx` reads only local-storage expenses). This feature adds only
  a record screen and a single-expense detail screen, both reached directly by URL; see §7.

## 2. Technical specification — SA

### 2.1 Approach

Today, **every** expense — solo or shared-trip — is written to `localStorage` only; no `Expense`
model exists on the server, and a shared trip's creator/participants have no shared view of
expenses at all. This feature is the point where shared-trip expenses move server-side, because
attribution and splitting only make sense once every trip member can see the same data. Two new
Prisma models (`Expense`, `ExpenseShare`) back a new `/api/trips/[id]/expenses` API, authenticated
the same way as the existing participants API (`x-creator-token` / `x-participant-token`). A new
`lib/sharedExpenses.ts` module owns split-calculation, attribution validation, and the fetch
wrappers, reusing `lib/expenses.ts`'s existing `ExpenseFormValues`/`validateExpenseForm`/
`PAYMENT_METHODS` for the fields this feature doesn't change. Two new routes under
`/trips/[token]/expenses/...` (mirroring `/trips/[token]/participants`'s "resolve my role, then
render" pattern) serve both the creator and participants; the existing `/expenses/new` route
gains a one-line redirect so a creator whose local trip is shared lands in the new flow instead.
The trip creator has no `Participant` row (confirmed in `ManageParticipants.tsx` — they are shown
as a fixed "Trip creator" label, never a data row), so attribution needs a way to represent them
without a database id; a client-side sentinel id (`TRIP_CREATOR_ID`) fills that role in the UI and
domain layer, translated to/from `null` only at the API boundary.

```ts
// lib/sharedExpenses.ts — key signatures (contracts, not bodies)
export const TRIP_CREATOR_ID = "__creator__"; // never collides with a cuid; translated to/from
                                               // `null` only inside the fetch wrappers below

export interface AttributionOption { id: string; name: string }
export function buildAttributionOptions(participants: ParticipantSummary[]): AttributionOption[];
// [{ id: TRIP_CREATOR_ID, name: "Trip creator" }, ...participants], creator always first

export type SplitMethod = "even" | "exact";

export function calculateEvenSplit(totalAmount: number, selectedIds: string[]): Record<string, number>;
// selectedIds non-empty; every id gets floor(totalAmount*100/n)/100 EXCEPT the last id in array
// order, which gets the remainder (totalAmount - base*(n-1)) rounded to 2dp — shares always sum
// exactly to totalAmount

export interface ExactSplitValidation { valid: boolean; error?: string }
export function validateExactSplit(
  totalAmount: number,
  amounts: Record<string, string>,
  selectedIds: string[],
): ExactSplitValidation;
// missing/non-numeric/negative entry for any selectedIds member -> "Enter an amount for every
// selected participant."; parsed sum (compared in integer cents) !== totalAmount (integer cents)
// -> "The amounts must add up to the total."

export function validateAttribution(
  selectedIds: string[],
  splitMethod: SplitMethod,
  totalAmount: number,
  exactAmounts: Record<string, string>,
): { errors: { split?: string } };
// selectedIds.length === 0 -> "Select at least one participant for the split."; splitMethod
// "exact" delegates to validateExactSplit; "even" never fails here

export function toSharesPayload(
  selectedIds: string[],
  splitMethod: SplitMethod,
  totalAmount: number,
  exactAmounts: Record<string, string>,
): { participantId: string | null; amount: number }[];
// TRIP_CREATOR_ID -> null; amounts from calculateEvenSplit or parsed exactAmounts per splitMethod

export interface CreateSharedExpensePayload {
  amount: number; currency: string; category: string; date: string;
  paymentMethod: string; location: string; description?: string;
  payerParticipantId: string | null;
  shares: { participantId: string | null; amount: number }[];
}

export type SharedExpenseResult =
  | { ok: true; expense: SharedExpense }
  | { ok: false; error: string };

export function createSharedExpense(
  tripId: string, payload: CreateSharedExpensePayload, auth: ParticipantAuth,
): Promise<SharedExpenseResult>;

export function getSharedExpense(
  tripId: string, expenseId: string, auth: ParticipantAuth,
): Promise<SharedExpenseResult>;

export function updateSharedExpenseAttribution(
  tripId: string, expenseId: string,
  payerParticipantId: string | null,
  shares: { participantId: string | null; amount: number }[],
  auth: ParticipantAuth,
): Promise<SharedExpenseResult>;
```

All three fetch wrappers collapse a thrown fetch **and** a non-2xx response into the same
`{ ok: false, error: "Could not reach the server. Check your connection and try again." }` shape —
identical to `lib/participants.ts`'s existing pattern, not `lib/join.ts`'s distinct offline/
not-found branching, since no scenario here asks for that distinction.

### 2.6 Non-functional notes

- **Mobile-first**: `AttributionFields` follows the same stacked-field layout `ExpenseForm.tsx`
  already uses; the split rows are a simple vertical list (checkbox + name + amount), not a table,
  consistent with `design.md`'s component patterns for this app.
- **Offline**: shared-trip expense recording/viewing/editing requires connectivity (no local
  fallback), exactly like every other shared-trip action since feature 016 — OVERVIEW §2 already
  establishes this for the trip/participant data this feature extends.
- **Local-storage failure modes**: not applicable to the new server-backed models; the only
  local-storage touch this feature makes is the existing `getSharedTripLink()`/`getJoinedTrips()`
  reads it reuses unchanged, whose failure handling (safe `null`/`[]` fallback) is already
  established by feature 012.
- **Post-save UX**: the Gherkin does not specify what a shared-trip save redirects to (there is no
  shared-trip dashboard for it to land on, unlike feature 005's solo-trip redirect). This spec
  chooses "redirect to the saved expense's own detail page" as the minimal option that needs no
  new screen — flagged as an assumption in §7, not a confirmed requirement.

## 7. Open questions & risks

1. **Dashboard gap for shared trips** (Challenge #5, unresolved): after this feature ships, a
   trip creator's own `Dashboard.tsx` will not reflect any shared-trip expenses (it only reads
   `localStorage`), even though those expenses now exist and are attributed. This is a real,
   visible gap between what the creator sees and what's actually recorded. Recommend feature 021
   (View Trip Balances) explicitly own closing it, since it's the next feature to add any
   aggregate view of shared-trip expense data. Needs user confirmation before 021 is spec'd.
2. **Post-save destination** (§2.6): this spec chooses "redirect to the saved expense's detail
   page" over any success-message/dashboard pattern, since no shared-trip dashboard exists yet.
   This is a design choice, not something the feature file specifies — flagged in case the user
   prefers different post-save UX (e.g. a plain confirmation banner that stays on the form).
3. **No shared-trip expense list yet** (§1.6): this feature's two new routes are reachable only by
   direct URL (from the record form's own success redirect, or from a future balances view) — there
   is intentionally no browsable list of a shared trip's expenses yet. Confirm this is acceptable
   for the v2 slice, or whether a minimal list belongs in this feature rather than 021.
4. **Categories remain per-device, not trip-scoped** (§2.1, inherited limitation): `getAllCategories()`
   reads a purely local, per-device category list (custom categories a different participant added
   on their own device are invisible to others). This predates and is unrelated to feature 020, but
   becomes more visible once expense category choices are shared across trip members. Not treated
   as in-scope to fix here.
