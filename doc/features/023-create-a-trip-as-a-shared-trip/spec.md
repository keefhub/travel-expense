## 1. Business analysis — BA

### 1.1 Purpose

Every trip today starts as a local-storage-only "solo" trip and only becomes server-backed if and
when its creator later generates a share link (feature 016). This feature removes that two-step
path for new trips: from this feature onward, creating a trip — whether it is a device's very first
trip or an additional one alongside trips it already has — creates a server-backed row directly,
with a shareable link already attached, so the creator never has to take a separate "invite
friends" step before they can share their trip. This is the first slice of the retire-v1 initiative
(`doc/requirements/2026-09-20-retire-v1-local-trips.md`): it does not touch the existing v1
local-storage trip flow (features 001–015), which keeps working unchanged until feature 031 removes
it.

### 1.2 Actors & preconditions

- **Actor**: any user creating a trip — a first-time user with no trip at all, or a returning user
  who already has one or more trips (created and/or joined) on this device.
- **Precondition**: none required to reach the flow — this is deliberately the entry point for a
  device with nothing yet, and (per the approved sweep ruling) is also reachable from a device that
  already has trips.
- **Connectivity**: required. There is no offline path (BR-023-19).

### 1.4 Data touched

- **Writes**: a new server-side trip (destination country, currency, start date, end date, optional
  budget, a share token, a creator token) — via the same `POST /api/trips` feature 016 already
  built. A local, per-device record of every trip this device has created (distinct from the trips
  it has joined, which feature 017 already tracks separately).
- **Reads**: the fixed supported-country list (feature 004, unchanged); this device's existing sets
  of created and joined trips, to decide where to land and what the trip switcher shows.

## 2. Technical specification — SA

### 2.1 Approach

Trip creation reuses `POST /api/trips` (feature 016) completely unchanged — that endpoint already
creates the share token and creator token atomically at row-creation, so BR-023-02 costs nothing new
on the server. The client-side work is: (a) a new, async, server-backed sibling to the existing
`submitTripSetup`, wired into `TripSetupForm` in place of its local-storage default; (b) a new,
per-device *list* of trips this device has created, because verification against the real code
showed the obvious design — reusing feature 016's single-slot `sharedTripLink` — is a single value,
not a list, and would silently orphan a device's earlier created trip the moment it created a
second one (see the design history in §7); (c) reusing feature 018's existing `/trips/[token]`
viewer for a created trip's own page, extended to recognize its own creator, so every created trip
gets a real, stable, switchable URL instead of all of them competing for the single `/` route.

Two decisions were escalated to the user during this phase because they changed the shape of
already-shipped code or the size of the diff materially; both are recorded with their resolution in
§7 rather than re-derived here.

**Budget-omission rationale for TS-023-08**: `GET /api/join/[token]` (feature 017) deliberately never
returns `budget` — it is a public, unauthenticated endpoint and budget was an explicit
never-displayed-to-a-joiner decision in that feature. If the creator's own view refreshed its
cached trip snapshot from that same response, the creator's budget would be wiped from display on
every page load. Rendering from the locally cached `CreatedTrip.trip` instead (populated once at
creation, in TS-023-01/03) avoids this without touching the public endpoint's contract. Nothing in
this feature's scope changes that trip's data after creation, so the cache cannot go stale within
023 alone.

### 2.3 Data model

```typescript
// lib/types.ts — new
export interface CreatedTrip {
  tripId: string;
  shareToken: string;
  creatorToken: string;
  trip: Trip; // creation-time snapshot: destinationCountry, currency, startDate, endDate, budget?
}

// lib/tripCreation.ts — new file
export type CreateTripResult =
  | { ok: true; createdTrip: CreatedTrip }
  | { ok: false; error: string };

export function createSharedTrip(trip: Trip): Promise<CreateTripResult>;

// lib/trip.ts — new
export type SubmitSharedTripResult =
  | { status: "invalid"; errors: TripValidationResult["errors"] }
  | { status: "saved"; trip: Trip; createdTrip: CreatedTrip }
  | { status: "server-error"; error: string };

export function submitSharedTripSetup(
  values: TripFormValues,
  deps: {
    getCurrencyForCountry: (country: string) => string | null;
    createSharedTrip: (trip: Trip) => Promise<CreateTripResult>;
  }
): Promise<SubmitSharedTripResult>;

// lib/storage.ts — additions
// STORAGE_KEYS.createdTrips = "travel-expense:created-trips"
export function getCreatedTrips(): CreatedTrip[];
export function saveCreatedTrips(trips: CreatedTrip[]): SaveResult;

// lib/tripSwitcher.ts — signature change
export function getSwitcherEntries(
  trip: Trip | null,
  sharedLink: SharedTripLink | null,
  joined: JoinedTrip[],
  created: CreatedTrip[]
): SwitcherEntry[];

// components/SharedTripView.tsx — ViewState addition
type ViewState =
  | { status: "loading" }
  | { status: "offline" }
  | { status: "gone" }
  | { status: "found"; joinedTrip: JoinedTrip }
  | { status: "found-as-creator"; createdTrip: CreatedTrip }; // new
```

### 2.6 Non-functional notes

- **Mobile-first**: `CreatedTripSummary`'s link paragraph reuses `font-mono break-all`, the same
  class combination `ShareTripLink.tsx` already uses for exactly this legibility requirement
  (BR-023-18).
- **Offline**: no offline path exists or is added (BR-023-19); every network call in this feature's
  design already goes through the collapsed thrown-fetch-or-non-2xx → one friendly-error shape every
  sibling client module uses, so "unreachable" and "offline" are the same code path by construction.
- **Error copy**: `lib/tripCreation.ts` keeps its own local `FRIENDLY_ERROR` string literal rather
  than importing `lib/sharedTrip.ts`'s copy — this duplicates one string, matching the existing
  per-module convention (`lib/participants.ts`, `lib/sharedExpenses.ts`, `lib/balances.ts` each keep
  their own copy today) rather than introducing a new shared constant this feature wasn't asked for.
- **Next.js check**: this feature introduces no new dynamic route segment — it reuses `/`,
  `/trip/new`, and `/trips/[token]` verbatim, so the "brand-new route needs a build before `tsc`
  passes clean" gotcha (`REFERENCE.md` §5) does not apply here. Confirmed by reading
  `node_modules/next/dist/docs/01-app/01-getting-started/03-layouts-and-pages.md`'s routing section:

## 7. Open questions & risks

1. **TS-023-12 — extend creator-role recognition into features 019–022, or accept a temporary gap?**
   Without it, a device that creates a trip via this feature can create it, see its link, and switch
   to it — but cannot record an expense, view balances, or manage participants for it, because those
   four already-shipped screens only recognize `sharedTripLink` (the v1-trip-got-a-link case), never
   `createdTrips`. No feature in the 023–031 build order explicitly names closing this gap. Options:
   (a) include TS-023-12 in this feature's implementation plan — small, additive, but touches four
   already-shipped feature files; (b) ship 023 without it and treat "a created trip is functionally
   unusable for anything beyond viewing its own summary and link" as a known, temporary limitation
   until a specific follow-up closes it; (c) revisit `doc/requirements/2026-09-20-retire-v1-local-trips.md`'s
   slice breakdown to add an explicit feature for this. **Needs a decision before `/writing-plans`
   runs**, since it changes the task list materially.
2. **`/trip/new`'s repurposing (confirmed) leaves `features/003.create-new-trip.md` and
   `OVERVIEW.md` describing a UI path that no longer exists once 023 ships**, ahead of feature 031's
   formal v1 removal. This spec doesn't edit either file (out of this skill's scope — only the target
   feature file's own directory is written here). Recommend a short editorial pass on `OVERVIEW.md`
   and/or `features/003.*.md` when 023 actually lands, or accepting the drift until 031 corrects it
   wholesale.
3. **No discoverable in-app link to `/trip/new` exists for a device with exactly one trip.** The
   trip switcher only renders at ≥2 entries (feature 018's existing rule, unchanged by this spec),
   and no other nav surface points at the additive creation flow after 023 repurposes it away from
   `TripEditForm.tsx`'s old "Start a new trip" link (that link still resolves to `/trip/new`, so it
   technically still works as an entry point for a device that already has a **v1** trip — but there
   is no equivalent entry point for a device whose only trip is itself 023-created or joined). AC-023-07
   is satisfiable and tested via direct navigation regardless. Recommend deciding whether 023 or a
   later feature (e.g. 025) adds a visible "Create another trip" affordance.
4. **The redirect tie-break in TS-023-06** (when a device has both created and joined trips, land on
   the most recent created trip) is an implementer default with no basis in the approved feature
   file, since bare `/` never had to make this choice before. Low risk — every trip remains reachable
   via the switcher regardless of which one `/` happens to land on first — but worth a sentence in
   the plan so an implementer doesn't invent a different tie-break.
5. **`app/expenses/new/page.tsx` was confirmed unaffected** — it's gated entirely behind a local
   `getTrip() !== null` check, which a 023-created trip (no local `Trip`) never satisfies, so it's
   simply unreachable for such a trip today. This is consistent with item 1 above (023-created trips
   have no expense-recording path yet) and not a separate gap.
