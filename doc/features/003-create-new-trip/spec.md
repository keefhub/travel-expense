## 1. Business analysis — BA

### 1.1 Purpose

A traveller finishing one trip wants to start tracking a new one without the old trip's expenses
and rates bleeding into the new trip's numbers. This feature lets the user deliberately replace the
single active trip: they're warned exactly what will be lost, must explicitly confirm, then go
through the same setup they used the first time — and only on a successful save does the old data
actually disappear.

### 1.2 Actors & preconditions

- **Actor:** the traveller.
- **Precondition:** an active trip already exists (Scenario 1's "Given the user already has an
  active trip"). If none exists, there is nothing to replace — the user is already on the first-time
  setup form (feature 001), not this flow.

### 1.3 Business rules

| ID | Rule | Source |
|---|---|---|
| BR-003-01 | Choosing to create a new trip while an active trip exists shows a warning that the current trip and its related data will be deleted. | Scenario "User starts creating a new trip while another trip exists" |
| BR-003-02 | The user must explicitly confirm before proceeding past that warning. | Same scenario |
| BR-003-03 | Cancelling at the warning leaves the existing trip, its expenses, and its exchange rates completely unchanged, and does not proceed to a new-trip setup form. | Scenario "User cancels new trip creation" |
| BR-003-04 | After confirming, the user is taken to a new-trip setup flow with the same fields and validation as first-time setup (destination country, start date, end date, optional budget). | Scenario "User confirms new trip creation" ("completes the new trip setup") + dependency on feature 001 |
| BR-003-05 | Completing that setup with valid input deletes the previous trip's `Expense` records from storage. | Scenario "User confirms new trip creation" + OVERVIEW §1 ("previous trip and its related data will be deleted") |
| BR-003-06 | Completing that setup with valid input deletes the previous trip's `ExchangeRate` records from storage. | Same |
| BR-003-07 | Completing that setup with valid input saves the new trip's data to storage, replacing the previous trip record. | Scenario "User confirms new trip creation" |
| BR-003-08 | On a successful save, the app redirects to the home dashboard. | Same scenario |
| BR-003-09 | An invalid submission on the new-trip form (unsupported/blank country, invalid date range, invalid budget) shows a validation message and deletes nothing — neither the old trip's data nor a partial new trip is written. | [derived] Same non-destructive-on-invalid principle already established for feature 001/002's shared validation (`validateTripForm`); the Gherkin doesn't restate it here but nothing suggests this flow should behave more destructively than editing does. |
| BR-003-10 | If a storage failure occurs while clearing the old trip's data or saving the new one, the app shows a friendly error, and the previous trip's own record is not deleted unless the new trip was actually saved successfully. | [derived] OVERVIEW §2 "Local storage errors should show a user-friendly error message"; a partial delete-without-save would leave the user with no trip at all, which is worse than the failure it was trying to report. |
| BR-003-11 | The "start a new trip" entry point is reachable only from a screen that already requires an active trip. | [derived] Mirrors Scenario 1's precondition — the action doesn't exist to be chosen when there's no trip to replace. |

### 1.4 Data touched

- **Deletes:** all `Expense` records, all `ExchangeRate` records (both are flat lists scoped to
  "the" one active trip, since the app supports exactly one trip at a time — REFERENCE.md §1).
- **Replaces:** the single `Trip` record.
- **Does NOT touch:** `Category` records — see the open assumption in §7.

### 1.5 Edge cases & negative paths

- Zero expenses and/or zero exchange rates already recorded — the delete step is a no-op and the
  flow proceeds identically. `[derived]`
- The new-trip form is reached (post-confirmation) but the page is refreshed before submitting —
  the confirmation must be asked again on next visit; nothing about "having confirmed" should
  survive a reload, since no data has changed yet and re-asking costs nothing. `[derived]`
- The user navigates directly to the "create new trip" flow's URL when no trip exists at all (e.g.
  a stale bookmark) — there is nothing to warn about replacing, so the flow should behave like the
  no-trip case elsewhere in the app (send the user to ordinary first-time setup) rather than show a
  warning about deleting data that doesn't exist. `[derived]`
- Storage failure specifically between deleting old data and saving the new trip (BR-003-10) — the
  user must not be left with neither an old trip nor a new one. `[derived]`

### 1.6 Out of scope

- Migrating or carrying over any of the old trip's expenses into the new trip — they are deleted,
  not moved.
- Deleting or resetting `Category` records — out of scope per the assumption in §7; that's closer to
  feature 013's (reset-app-data) territory if ever broadened.
- Any standalone "delete my data" action decoupled from creating a new trip — that's feature 013.
- Editing the newly created trip afterward — that's feature 002, already built, and needs no change
  here.

## 2. Technical specification — SA

### 2.1 Approach

Reuse feature 001's validation and currency-derivation logic exactly as feature 002 already did,
rather than duplicating it a second time. The only genuinely new domain behavior is the destructive
"clear expenses and exchange rates, then save" sequence, which becomes a new function,
`submitNewTrip`, sharing its trip-construction internals with the existing `submitTripSetup` via a
small private helper so the two can never drift apart on how a `Trip` is built from `TripFormValues`.
On the UI side, `TripSetupForm` (feature 001, unchanged fields/markup) is reused for the actual new
trip form by making which submit function it calls injectable via an optional prop — avoiding a
third near-duplicate form component, since the field set and validation are identical to first-time
setup, not to `TripEditForm`'s pre-filled/derived-fields shape. A new route, `/trip/new`, hosts a
two-step screen: an in-page confirmation warning first, then (only after confirming) the form. The
entry point into that route is a new secondary action on `/trip/edit` (feature 002's trip-settings
screen), since that is the only "manage my trip" surface that exists before feature 009's dashboard.

Is this safe to build against without asking the user? | The literal OVERVIEW text ("the previous trip **and its related data**") is genuinely ambiguous about whether categories count as "related data." | 3 | SA | Is a full-screen confirmation *route* (`/trip/new` initially showing only the warning) over-engineered compared to a same-page `window.confirm()` on `/trip/edit`'s "Start a new trip" button? | Rejected — `window.confirm()` is a native browser dialog with no styling, and this repo's design system (`design.md` §6) has already established in-app confirmation panels as the pattern this app uses (e.g. feature 002's error/warning text patterns). A dedicated route also gives the "no trip exists" edge case (AC-003-06) somewhere well-defined to redirect from. | Rejected |
| 4 | BA | Extracting `buildAndSaveTrip` out of `submitTripSetup` (TS-003-01) touches feature 001's already-shipped, already-reviewed code. | 5 | SA | BR-003-10's ordering (clear expenses → clear rates → save trip) means if `saveTrip` itself fails after both clears succeeded, the user is left with **no trip at all** but also no old expenses — worse than before. ## 7. Open questions & risks

1. **(Challenge 1)** Confirm whether `Category` records (default and custom) should be preserved or
   cleared when creating a new trip. This spec proceeds on **preserved** — categories are a
   user-maintained taxonomy independent of any single trip (feature 010 never scopes a category to a
   trip), and OVERVIEW's "related data" most naturally reads as trip-scoped records (expenses, rates)
   rather than app-wide settings. If wrong, `submitNewTrip`'s `deps` would need `saveCategories([])`
   (or a defaults-reset) added — a small, isolated change if this assumption is overturned later.
2. **(Challenge 5)** No atomic multi-key storage transaction exists in this repo (`lib/storage.ts`,
   feature 012). A failure between clearing old data and saving the new trip can leave the user with
   neither. This spec accepts the ordering in TS-003-02 (clear expenses → clear rates → save trip) as
   the least-bad option available without redesigning `lib/storage.ts`'s single-key-write model, and
   surfaces the friendly error BR-003-10 requires either way. A true fix (e.g. a single combined
   storage write) is out of scope for this feature and would need its own spec if the risk proves
   unacceptable in practice.
