## 1. Business analysis — BA

### 1.1 Purpose

A traveller who is done with a trip, or who wants to discard everything and start clean, needs a
single action that wipes all stored trip and expense data and returns the app to its first-launch
state. Unlike "Create new trip" (feature 003), which replaces the trip while preserving custom
categories, "Reset app data" is the full wipe: nothing survives except the app shell itself.

### 1.2 Actors & preconditions

- **Actor:** the traveller, using the app on their own device (all data is local to the browser).
- **Precondition:** an active trip exists. The feature's only entry point (see §2.2) is a page that
  already requires a trip to be reachable — `app/settings/page.tsx` redirects to `/` when no trip is
  saved (verified: `app/settings/page.tsx:37-41`) — so "the user has saved trip or expense data"
  (Scenario 1's Given) is guaranteed by simply being able to reach the reset action; no separate
  check is needed.

### 1.3 Business rules

| ID | Rule | Source |
|---|---|---|
| BR-013-01 | Selecting "reset app data" shows a confirmation warning before anything is deleted. | `features/013.reset-app-data.md:9-12` (Scenario: User chooses to reset app data) |
| BR-013-02 | Confirming the reset deletes all trip data (including budget, which is a field on the trip record), expense data, custom category data, and exchange-rate data from local storage. | `features/013.reset-app-data.md:14-18` (Scenario: User confirms reset) |
| BR-013-03 | After a confirmed reset, the app returns to the travel setup screen. | `features/013.reset-app-data.md:18` |
| BR-013-04 | Cancelling the reset leaves all app data unchanged — no storage write occurs. | `features/013.reset-app-data.md:20-23` (Scenario: User cancels reset) |
| BR-013-05 | If the reset cannot complete because local storage is unavailable or fails, the app shows a user-friendly error message rather than silently failing or crashing, and does not claim the reset succeeded. | OVERVIEW §2 confirmed requirement: "Local storage errors should show a user-friendly error message." — `[derived]`, applying an app-wide requirement to this feature's write path |

### 1.4 Data touched

- **Trip** (including its optional budget field) — deleted entirely (not replaced), so the app has
  no active trip afterward.
- **Expenses** — all deleted.
- **Categories** — custom categories deleted. Default categories (Food, Transport, Accommodation,
  Shopping, Activities, Others) are not stored data at all — they're a fixed list the code always
  provides (verified: `lib/categories.ts:12-23`, `DEFAULT_CATEGORIES`) — so they are unaffected by
  definition, not "kept" by any special-case logic in this feature.
- **Exchange rates** — all deleted.

### 1.5 Edge cases & negative paths

- **Reset while local storage is unavailable/fails mid-write** `[derived]` — BR-013-05. The app must
  not report success, leave the user on the confirmation panel (or otherwise make it obvious the
  reset didn't happen), and must not partially delete some data types but not others in a way that
  leaves the app in a confusing state.
- **Zero expenses/no custom categories/no exchange rates at reset time** `[in spec, implied]` — the
  Gherkin's Given ("saved trip or expense data") only requires a trip OR expenses to exist; the
  other two data types may already be empty. Resetting must succeed identically whether or not there
  was anything to clear in each category — there is no "nothing to delete" error state.
- **Cancelling, then immediately reopening the confirmation** `[derived]` — cancelling must be fully
  reversible with no side effect, so a user can cancel and reopen the same confirmation any number of
  times before ever confirming.

### 1.6 Out of scope

- **Partial reset** (e.g., "clear only expenses") — not requested; the feature is an all-or-nothing
  wipe.
- **Undo/restore after a confirmed reset** — not requested. This mirrors feature 003's "Create new
  trip" precedent, which is also an irreversible, confirmed delete.
- **The in-progress, unrelated dark-mode/theme-preference work** currently sitting uncommitted in
  the working tree (`lib/theme.ts`, `components/ThemeToggle.tsx`, `components/DateField.tsx`, and
  edits to `globals.css`/`layout.tsx`/several components) — a theme preference is not "trip, expense,
  category, budget, and exchange rate data" per the feature's own title and Scenario 2's exact
  wording, so this feature must not read, write, or reference any of those files, tokens, or
  classes.
- **Any change to how `/settings` currently manages exchange rates** — `ExchangeRateForm` is
  untouched; this feature only adds a new, separate action to the same page.

## 2. Technical specification — SA

### 2.1 Approach

Three small pieces: (1) a new storage-layer function that deletes all four `STORAGE_KEYS` entries in
one call, since no existing function can null out the trip or clear all four keys at once; (2) a
plain confirmation-panel component, mirroring the already-committed `components/NewTripConfirm.tsx`
pattern exactly (same props shape, same "danger action + cancel" layout, same styling — see the
verified-against-HEAD note in §2.2); (3) a small addition to the existing `app/settings/page.tsx`
route that toggles between its normal content and the confirmation panel, and on confirm calls the
new storage function and navigates home. No new route is added — Settings is already the page
`app/settings/page.tsx` uses for the other data-management action this app has (exchange rates), and
reaching it already guarantees an active trip exists (§1.2), so it is the natural, lowest-risk home
for this one too.

### 2.2 Design elements

- **TS-013-01** (satisfies BR-013-02, BR-013-03, BR-013-05) — add to `lib/storage.ts`:
  ```ts
  export function resetAppData(): SaveResult
  ```
  Removes all four `STORAGE_KEYS` entries (`trip`, `expenses`, `categories`, `exchangeRates`) via
  `window.localStorage.removeItem`, guarded the same way `safeSetItem` already guards writes
  (`isStorageAvailable()` check plus a try/catch around the removal), returning `{ ok: true }` on
  success or `{ ok: false, error: SAVE_ERROR_MESSAGE }` (the same message constant already used by
  every other storage failure in this file) on failure. After a successful call, `getTrip()` returns
  `null`, and `getExpenses()`/`getExchangeRates()` return `[]` — the same fallback values these
  getters already return for "key never existed" (verified: `lib/storage.ts:47-77`), so no other
  module needs to change to observe the reset.

- **TS-013-02** (satisfies BR-013-01) — add `components/ResetAppDataConfirm.tsx`:
  ```ts
  export default function ResetAppDataConfirm(props: {
    onConfirm: () => void;
    onCancel: () => void;
  }): JSX.Element
  ```
  A plain component (no `'use client'` — it has no hooks or event handlers of its own, matching
  `NewTripConfirm.tsx`'s existing precedent), rendering a heading, a `role="alert"` warning
  paragraph naming what will be deleted (trip, expenses, categories, exchange rates) and that it
  cannot be undone, a danger-styled confirm button calling `onConfirm`, and a cancel button calling
  `onCancel`. **Verified against the committed baseline, not the working tree:** `git show
  HEAD:components/NewTripConfirm.tsx` uses `className="text-[var(--danger)]"` on the confirm button
  and no class at all on cancel — the `.btn-danger`/`.btn-secondary` component classes visible in the
  *current uncommitted working tree* belong to the unrelated, not-yet-landed theming refactor (its
  diff on this exact file confirms it: `git diff components/NewTripConfirm.tsx` shows those classes
  being *introduced* by that refactor, not present at HEAD). This component must match the
  committed pattern (`text-[var(--danger)]`, no class on cancel), the same discipline features
  005–009 already followed.

- **TS-013-03** (satisfies BR-013-01, BR-013-03, BR-013-04, BR-013-05) — modify
  `app/settings/page.tsx`: add local state `const [confirmingReset, setConfirmingReset] =
  useState(false)` and `const [resetError, setResetError] = useState<string | null>(null)`. When
  `confirmingReset` is `true`, render `<ResetAppDataConfirm onConfirm={...} onCancel={...} />`
  (plus the error message, `role="alert"`, if `resetError` is set) in place of the page's normal
  content; otherwise render the existing heading/currency line/`ExchangeRateForm` plus a new
  "Reset app data" trigger button below them that sets `confirmingReset` to `true`. `onCancel` sets
  `confirmingReset` back to `false` and clears `resetError` (BR-013-04 — no storage call on this
  path). `onConfirm` calls `resetAppData()`: on `{ ok: true }`, calls `router.push("/")` (mirrors
  `app/trip/new/page.tsx:61`'s existing `onSaved={() => router.push("/")}` precedent — a fresh
  mount of `app/page.tsx` re-reads storage from scratch via its own `useSyncExternalStore` store, so
  no manual cache invalidation is needed for BR-013-03 to hold); on `{ ok: false, error }`, sets
  `resetError` to that message and leaves `confirmingReset` at `true` (BR-013-05 — the panel stays
  up, the user sees why, nothing is silently swallowed).

### 2.3 Data model

No new persisted shape. `resetAppData()` returns the existing `SaveResult` type
(`lib/storage.ts:10`); no new interface is introduced.

### 2.6 Non-functional notes

## 6. Contrarian review — BA ↔ SA

| # | Raised by | Challenge | Resolution | Outcome |
|---|---|---|---|---|
| 1 | SA → BA | BR-013-01's precondition claim ("guaranteed by reaching Settings") is doing a lot of work — what if a future feature adds another way to reach the reset action that *doesn't* go through the trip-gated `/settings` route? Then Scenario 1's Given would no longer hold automatically. | Accepted as a documented constraint, not fixed by adding redundant logic: TS-013-03 places the action only inside `app/settings/page.tsx`, which is explicitly the only design element that renders it (§2.2/§2.4). If a future feature adds a second entry point, that feature's own spec is responsible for re-establishing the precondition, not this one. Noted in §1.2's wording ("the feature's only entry point"). | Accepted |
| 2 | BA → SA | TS-013-03's design lets a storage failure on `resetAppData()` leave data in a *partially* deleted state — `removeItem` is called four times; if the third call throws, the first two keys are already gone while the fourth isn't. Is a failure ever actually partial in practice, and does BR-013-05 require all-or-nothing atomicity? | Rejected, with reason: `localStorage.removeItem` in every real browser either succeeds instantly and synchronously or the storage is unavailable/blocked entirely (private-mode Safari with storage disabled, quota-exceeded errors are a *write*-size problem that doesn't apply to deletion) — a failure partway through this app's four `removeItem` calls is not a realistic failure mode this app can distinguish from "some keys already didn't exist." BR-013-05's actual intent (confirmed by re-reading the source AC and OVERVIEW's own justification) is "don't claim success when a write genuinely failed and don't crash," not "guarantee cross-key transactional atomicity" — no other storage function in this app (e.g. feature 010's `renameCategory` two-write cascade) provides true atomicity either, and this task doesn't need to be the first to invent it. | Rejected |
| 3 | SA → BA | AC-013-07 ("default categories still available after reset") reads as testing `lib/categories.ts` behavior that this feature doesn't change at all — is this orphan/scope creep the BA smuggled in? | Rejected, with reason: it's a genuine regression-risk edge case worth specifying explicitly (§1.5), not scope creep — `resetAppData()` (TS-013-01) clears the *stored* categories key, and the only thing that keeps defaults available afterward is that they were never stored in the first place (`lib/categories.ts:12-23`). Without this AC, an implementer could "fix" a perceived bug by re-seeding `DEFAULT_CATEGORIES` into storage on reset, which would be redundant and inconsistent with how defaults work everywhere else in the app. The AC exists to prevent that miscorrection, not to re-test unrelated code. | Rejected |
| 4 | BA → SA | TS-013-02 mandates matching the *committed* `NewTripConfirm.tsx` styling (`text-[var(--danger)]`, no class on cancel) rather than the nicer `.btn-danger`/`.btn-secondary` classes visible in the current working tree. Isn't this needlessly worse UI, given the tokens obviously exist somewhere and will presumably land eventually? | Rejected, with reason: this repo's own established, repeatedly-applied practice (features 005 through 009, each independently) is to build against the committed baseline, not an uncommitted, unowned, unlanded refactor sitting in a shared working tree — building against it would silently couple this feature's correctness to another feature's completion, in the wrong order, with no dependency declared anywhere. When the theming refactor actually lands and is committed, restyling this one component to use its classes is a trivial, isolated follow-up, not a reason to violate this repo's verified-state discipline now. | Rejected |
