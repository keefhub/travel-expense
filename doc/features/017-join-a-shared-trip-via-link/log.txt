Key Decisions:
  None beyond what the plan already specified — implementation matched
  the contract exactly.

Deviations:
  None.

Known limitation (accepted, not fixed — Gate B PASSed with this noted,
did not FAIL):
  resolveTripByToken's try/catch wraps both the fetch call and the
  response.json() parse. If a nominally-2xx response has a malformed
  body, the parse throw is caught by the same catch as a genuine
  network failure and mapped to reason: "offline" instead of a more
  accurate category. Low severity (requires a working network plus a
  corrupted server response) and not exercised by any AC/E2E test in
  this feature. Revisit if it ever surfaces in practice — the fix is a
  straightforward split of the fetch-try from the parse-try.

Post-completion fix: resolveTripByToken offline/not-found miscategorization
Completed: 2026-09-18
Commit: 15cf3c8

Summary:
  Fixed the known, accepted gap noted in Task 5's log entry (malformed
  JSON on a 200 GET /api/join/[token] response was miscategorized as
  reason: "offline" instead of "not-found") on explicit user request
  after the plan was already marked Complete. Split resolveTripByToken's
  single try/catch into two: one around the fetch call (genuine network
  failure -> "offline"), one around response.json() (a parse failure on
  an otherwise-successful response -> "not-found", the same bucket a
  404 already falls into).

Key Decisions:
  - Mapped a parse failure to "not-found" rather than adding a third
    ResolveResult reason, since the UI's existing invalid-link message
    ("This link isn't valid...") is an honest enough description of "the
    server responded but not with something usable" and this keeps
    lib/types.ts, the API contract, and components/JoinTrip.tsx
    untouched — a minimal, root-cause fix rather than a new branch.

Deviations:
  None from the fix itself. This is a deviation from the plan's own
  Completion Summary, which had listed this as an accepted follow-up
  not in scope — superseded by this fix.
