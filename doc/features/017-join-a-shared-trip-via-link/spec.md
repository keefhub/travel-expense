## 1. Business analysis — BA

### 1.1 Purpose

Feature 016 gave a trip creator a shareable link but nothing yet reads it — a link is a dead end
until someone can open it and actually become part of the trip. This feature is the other side of
that handoff: a friend opens the link, types their name, and becomes a named participant on the
creator's trip, so that later features (020 attribution, 021 balances) have someone real to
attribute an expense to or split a cost with. It also has to behave sensibly when the link is no
longer good (regenerated, the trip is gone, or the URL was never valid), and it must never disturb
the joining device's own separate solo trip, since a device can hold both at once.

### 1.2 Actors & preconditions

- **Actor:** a friend — any browser that opens a `/join/{token}` URL. Unlike feature 016 (single
  actor: the creator), this is the first feature where a second kind of user exists in the product.
- **Precondition (all scenarios):** a shared trip exists server-side with a `shareToken` — i.e.
  feature 016 has already run for some trip. This feature does not create that precondition; it
  only consumes it.
- **Precondition (NOT required):** unlike every other route in this app (REFERENCE.md §4), this
  feature's route does **not** require the visiting device to already have a local solo trip
  (`getTrip()`). A friend with no trip of their own must still be able to join. See BR-017-08 and
  TS-017-08.

### 1.4 Data touched

- **Trip** (server entity, read-only here): the same row feature 016 creates. This feature reads it
  by `shareToken` to resolve the link and never writes to it.
- **Participant** (new server entity): a name plus a private per-device credential, scoped to one
  trip. Does not exist anywhere in the app today.
- **Joined-trip pointer** (new local concept, this device's browser only): remembers which shared
  trips this device has joined and as which participant, so BR-017-09/15 can be satisfied without a
  login system. Distinct from feature 016's `sharedTripLink` (that is the *creator's* pointer to a
  trip it made; this is a *joiner's* pointer to a trip it joined — a device could plausibly hold
  both for different trips, or even the same trip if a creator joined their own link, which no
  scenario exercises and is left alone).

### 1.5 Edge cases & negative paths

- Genuine server error (5xx) while resolving the link on open, as opposed to a clean 404 →
  **[derived]** — treated identically to "link isn't valid" (BR-017-06); the Gherkin gives no
  distinct copy for "something went wrong" vs. "this specific link is dead," and inventing a third
  message class isn't asked for.
- The link is valid on page load but becomes invalid before the name is submitted (creator
  regenerates mid-visit) → **[derived]** — the join `POST` independently re-resolves the token and
  404s exactly as the initial `GET` would; the friend sees the same "server unreachable/could not
  join" friendly error as BR-017-11's path, since from the friend's device this is indistinguishable
  from any other failed join attempt.
- A name of exactly 50 characters → **[derived]** — must be accepted, not rejected; BR-017-05 limits
  what can be *typed*, it does not shrink the usable ceiling below 50.
- A name with leading/trailing whitespace around otherwise valid characters (e.g. `"  Sam  "`) →
  **[derived]** — trimmed before the blank check and before it is stored/sent, consistent with every
  other text-entry rule already in this codebase (`lib/trip.ts`, `lib/categories.ts`).
- `resetAppData()` (013) and a device that has joined one or more shared trips → **[derived]** — the
  local joined-trip pointer must be cleared by a full reset the same way feature 016 extended
  `resetAppData()` for `sharedTripLink` (TS-016-07); no Gherkin scenario in this feature or in 013
  exercises "reset" directly, so this is applied as a design element, not asserted by a new AC —
  same precedent 016 already established for the sibling key.
- The local write that remembers a successful join fails (storage full/unavailable) even though the
  server-side join already succeeded → **[derived]** — the friend already exists as a participant
  server-side; the UI still shows them the joined trip view for the current page load (using the
  in-memory join result, not a fresh storage read) plus a non-blocking notice that this device may
  not remember them next time, rather than claiming the join itself failed. No dedicated AC/test —
  same class of accepted gap as 016's Open Questions #4/#5 (server succeeds, local bookkeeping is
  the part that can lag).
- A device with **no local solo trip at all** opens a join link → **[derived]** — must still work;
  see §1.2. This is the reason the join route cannot reuse the existing `getTrip()`-gated route
  pattern every other screen in this app uses.

### 1.6 Out of scope

(carried verbatim from the feature file, since the BA must not re-litigate scope already settled there)

- Viewing or managing the list of participants who have joined — feature 019.
- Attributing expenses to a payer or a split among participants — feature 020.
- Leaving a trip or being removed from it — feature 019.
- Any authentication, password, or account system for participants.
- Native OS share-sheet integration for receiving the link (carried over from feature 016's scope).
- A cap on participants per link, and letting a joined participant edit their own name after joining
  (both explicitly deferred, per the feature file's Deferred section).

Additionally, out of scope **by this analysis** (not stated in the feature file, but excluded
because no scenario in it exercises them):

- Wiring a joined shared trip into the app's home route (`/`), bottom navigation, or any
  multi-trip switcher — that integration is explicitly feature 018's job ("Switch Between Multiple
  Trips"; its own ordering rationale in CLAUDE.md says membership "only exists once joining is
  possible," implying 017 supplies the membership record and 018 supplies the switcher UI around
  it). See §2.1 and Contrarian Review #1/#2.
- Any expense, budget, or category data for a shared trip — none of that exists for shared trips
  until feature 020, so "the trip's dashboard" in this feature's scenario is necessarily a smaller
  view than `components/Dashboard.tsx` (see §2.1 and Contrarian Review #1).
- Rate-limiting or abuse protection on the new public join endpoint — see Open Questions.

## 2. Technical specification — SA

### 2.1 Approach

Add one Prisma model (`Participant`, cascade-deleted with its `Trip`) and one new Route Handler
file that owns both HTTP verbs this feature needs: `GET /api/join/[token]` resolves a share token to
public trip fields (or 404s), and `POST /api/join/[token]` creates a participant for that trip (or
404s/400s). A single file with two exports is standard for this Next.js version (confirmed: see
§2.6) and keeps the whole join surface in one place, distinct from feature 016's creator-only
`app/api/trips/*` routes.

On the client, a new page `app/join/[token]/page.tsx` — the first route in this app that does
**not** gate on `getTrip()` (see §1.2) — mounts a single component, `components/JoinTrip.tsx`, that
owns four states: resolving, invalid link, join form, and joined. "Joined" is deliberately a small,
honest view (destination, dates, "Joined as {name}.", a link back home) rather than a reuse of
`components/Dashboard.tsx` — that component's actual content (total spend, budget, category pie
chart) is computed entirely from *local* `localStorage` expenses/exchange rates belonging to the
solo trip, none of which exist for a shared trip until feature 020 gives shared trips their own
expense data. Reusing it here would either silently show the wrong (solo-trip) numbers under a
shared trip's heading, or require inventing a parallel expense-fetching path this feature's Gherkin
never asks for. See Contrarian Review #1.

Device identity (BR-017-15) is a new local storage key, `joinedTrips`, holding an array of
`JoinedTrip` records — one per shared trip this device has joined, each carrying its own
`participantToken` (the credential proving "this device is participant X on trip Y") and a snapshot
of the trip's display fields, so reopening a link (BR-017-09) can show the joined view without a
second network round trip. This mirrors `sharedTripLink`'s shape (016) but is deliberately a
different key: one is the creator's single pointer to a trip it made, the other is a list because a
device can join any number of shared trips (OVERVIEW.md §2, "any number of shared trips").

Double-submission (BR-017-13) is handled the same way feature 016 handles it: a `useRef` in-flight
guard in `JoinTrip.tsx`, not a server-side idempotency key. The reasoning is identical to 016's
Contrarian Review #3 (accepted there, not re-litigated here): the source scenario is a single-device
double-tap gesture, not a multi-tab or retry scenario, so a client-side guard fully satisfies it.
Concurrent joins from two different friends (BR-017-14) need no special handling at all — each
`POST` is an independent `Participant` insert with no shared unique constraint between different
people's rows (names are explicitly allowed to collide, BR-017-04), so there is nothing to
serialize.

### 2.3 Data model

```ts
// lib/types.ts — additions
export interface SharedTripSummary {
  id: string;
  destinationCountry: string;
  currency: string;
  startDate: string;
  endDate: string;
  budget?: number;
}

export interface JoinedTrip {
  tripId: string;
  shareToken: string;
  participantId: string;
  participantToken: string;
  participantName: string;
  trip: SharedTripSummary;
}
```

```prisma
// prisma/schema.prisma — additions
model Trip {
  // ...existing fields unchanged...
  participants Participant[]
}

model Participant {
  id               String   @id @default(cuid())
  tripId           String
  trip             Trip     @relation(fields: [tripId], references: [id], onDelete: Cascade)
  name             String
  participantToken String   @unique
  createdAt        DateTime @default(now())
}
```

```ts
// lib/join.ts — additions
export type ResolveResult =
  | { ok: true; trip: SharedTripSummary }
  | { ok: false; reason: "not-found" }
  | { ok: false; reason: "offline" };

export type JoinResult =
  | { ok: true; joined: JoinedTrip; persisted: boolean }
  | { ok: false; error: string };
```

### 2.6 Non-functional notes

- Mobile-first: `JoinTrip.tsx`'s form follows the same `flex flex-col gap-1` label-above-input
  pattern as `TripSetupForm.tsx` (design.md §6); its joined view follows the same
  section-with-heading rhythm as `ShareTripLink.tsx`.
- Offline: per BR-017-17, both opening the link and submitting the join form are allowed to fail
  outright when offline; no offline queueing or optimistic local state. A thrown `fetch` (network
  error) is caught and mapped to a distinct "offline" branch (BR-017-12) separate from a clean `404`
  ("not-found," BR-017-06) — the two need different copy, so they cannot collapse into one error
  branch the way 016's generate/regenerate failures could.
- Local-storage failure modes: `joinedTrips` follows the exact fallback/error conventions already in
  `lib/storage.ts`; the one new nuance (a successful server join whose local save fails) is handled
  per §1.5's derived edge case via `JoinResult.persisted`, not a new failure-mode class.
- **Next.js check**: confirmed against `node_modules/next/dist/docs/01-app/01-getting-started/15-route-handlers.md` —
  a single `route.ts` may export more than one HTTP method handler (`GET` and `POST` side by side in
  the same file is the documented convention, not a workaround), and "there cannot be a `route.js`
  file at the same route segment level as `page.js`" is not violated here since `app/api/join/[token]/route.ts`
  and `app/join/[token]/page.tsx` sit under different top-level segments (`api/join` vs. `join`).
  Dynamic segment params remain a `Promise` (`PageProps<"/join/[token]">`, `use(props.params)`),
  consistent with `app/expenses/[id]/page.tsx` and REFERENCE.md §5.

- AC-017-01 drops the source's second `Then` clause ("I see the trip's dashboard as a participant")

  but the wording no longer implies reuse of the solo-trip `Dashboard.tsx` component, which §2.1 and
  Contrarian Review #1 establish is not what this feature builds. The BA's job is the observable
  outcome (a confirming view exists), not which component renders it.
- AC-017-06 rewrites the source's "both my solo trip and the shared trip remain available to me"
  into two independently checkable clauses (solo trip's stored data unchanged; shared trip also
  available), since "remain available" bundled two different storage locations behind one assertion
  (G3 requires splitting scenarios that assert two independent things).
- AC-017-08/09/11 make the source scenarios' implicit network-call assertions explicit ("no join
  request is made", "I am not shown as joined", "only one join request is made") instead of leaving
  the mechanism unobservable, mirroring how 016's AC-016-09 was tightened the same way.
- AC-017-13 and AC-017-14 are `[derived]` additions for the two boundary/whitespace edge cases from
  §1.5 that the source Gherkin's "long name" and general "name" scenarios don't themselves cover
  (over-limit truncation is covered by the source; the limit's own inclusiveness and whitespace
  trimming are not).

## 7. Open questions & risks

1. **No rate-limiting or abuse protection on the new public `POST /api/join/[token]` endpoint**
   (Challenge #4). Acceptable for v2 per the product's explicit "no cap" stance, but worth a
   hardening pass once this endpoint sees real traffic — same category of accepted-risk-for-now as
   016's Open Question #3 (no server-side idempotency beyond the client guard).
2. **`findJoinedTrip` matches by `shareToken`, not `tripId`** (Challenge #5) — a participant who
   rejoins via a regenerated link they already used under the old token will be prompted to join
   again rather than recognized, potentially creating a second `Participant` row for the same
   person. No scenario in 016 or 017 describes this sequence; left for 018/019 to resolve when they
   define how a device's set of joined trips is actually managed and deduplicated.
3. **The "joined" view's scope** (Challenge #1) is intentionally smaller than "dashboard" in the
   literal sense of `components/Dashboard.tsx`. This is a deliberate, documented interpretation, not
   an oversight — but it is the single biggest judgment call in this document, since the source
   Gherkin's own wording invited the larger reading. Revisit once feature 020 gives shared trips
   real expense data to show.
