Task 3: [Domain] — lib/balances.ts
Completed: 2026-09-19
Commit: b35e869

Summary:
  Added lib/balances.ts: BalanceExpenseInput, getTripBalances (pure integer-cents netting, per-expense
  currency conversion, last-share-absorbs-remainder, greedy largest-creditor/largest-debtor
  reduction), TripBalancesFetchResult and fetchTripBalances (GET /api/trips/[id]/balances with the
  x-creator-token / x-participant-token header, collapsed friendly error). REFERENCE.md §4 gained the
  module's line.

Key Decisions:
  THE QUALITY GATE FAILED THE PLAN'S LITERAL CODE, so the committed implementation deviates from it
  in three places. The plan's Task 3 Step 1 gives getTripBalances verbatim and says "exactness
  matters", so each deviation is recorded here deliberately:
  1. `originalTotalCents === 0` guard on the non-last share's division. Reachable through the app's
     own validation: an amount of 0.004 passes `amount > 0`, calculateEvenSplit yields two zero-cent
     shares whose cent-sum equals Math.round(0.004 * 100) === 0, and both expense routes accept
     share.amount >= 0. The literal `0/0` produced NaN for BOTH shares, and because NaN is sticky and
     fails the `cents > 0` / `cents < 0` filters, every net that participant appeared in later was
     dropped — the whole trip silently reported settled up while isComplete stayed true.
  2. The rate lookup now treats a stored rate that is non-finite or <= 0 as unusable, so such a
     currency lands in missingCurrencies with isComplete false instead of converting at 0 or at
     Infinity. Explicitly NOT reachable through this app's own writes (the Task 5 route validates
     finite && > 0, and JSON cannot carry Infinity), so this is defence in depth; it also removes a
     genuine non-termination case (Infinity net on both sides -> Math.min never advances a pointer ->
     unbounded push). Rule mirrors lib/currency.ts:37-39 for per-device rates.
  3. The matching loop advances on `!(cents > 0)` rather than `cents === 0` — behaviourally identical
     for integer cents, but it guarantees progress on a non-finite value.
  Everything else in the file is the plan's literal code. Both gates re-ran on the fixed revision and
  PASSed; the re-run gate A judged all three amendments correct, and the re-run gate B independently
  probed the 0.004 case, all four bad-rate cases, the happy paths (values unchanged), two-null-id
  shares, payer-is-also-shareholder, the chain case, net-sum zero, line reconciliation and
  determinism (25 runs, 1 distinct output).
  Left unfixed and recorded as non-findings by both gates: an expense with an empty shares array
  (unreachable — both writers reject shares.length === 0) and the `shares[].id` vs `participantId`
  naming (spec-dictated).
  REFERENCE.md's phrase "the minimum number of settlement lines" was flagged by both gates as
  optimistic (greedy largest-first is not provably minimal for every net vector). Left as written
  because it mirrors the spec's and the plan's own wording for this mandated algorithm; changing the
  doc's claim about an algorithm the spec prescribes is a spec-level call, not a Task 3 fix.

Deviations:
  The three amendments above, all inside getTripBalances and all judged contract-preserving by both
  gates. The plan's Task 3 Step 1 now carries a pointer note to this entry.

Task 4: [Route] — GET /api/trips/[id]/balances
Completed: 2026-09-19
Commit: 2c84950

Summary:
  Added app/api/trips/[id]/balances/route.ts. It looks the trip up (404 "Trip not found."), runs the
  participants-GET auth shape (x-creator-token matching the row, else an x-participant-token
  belonging to that trip, else 403), then loads the trip's expenses with their shares and its
  exchange rates, maps them through the snapshot columns into BalanceExpenseInput[], delegates to
  lib/balances.ts's getTripBalances, and responds 200 { balances, tripCurrency }. REFERENCE.md §4
  gained the route's line.

Key Decisions:
  `orderBy: { id: "asc" }` on the nested shares include is load-bearing rather than cosmetic:
  getTripBalances gives the rounding remainder to the LAST share of the array it receives, so without
  a stable ORDER BY the leftover cent could land on a different participant between two identical
  requests. Both gates confirmed the order is a total order on the unique cuid.
  Reads payerParticipantIdSnapshot / participantIdSnapshot rather than the live FKs, matching
  app/api/trips/[id]/expenses/[expenseId]/route.ts's serialize helper, because a departed member's FK
  is null while the snapshot survives. A creator's own share (snapshot null) maps to
  BalanceExpenseInput's null id, which lib/balances.ts turns back into TRIP_CREATOR_ID — the same
  identity the POST route writes on create.
  The 200 body carries only { balances, tripCurrency }: neither creatorToken nor shareToken is ever
  returned, and no raw Expense row is spread into the response.
  The inline auth block is duplicated from the participants GET rather than extracted into a shared
  helper — that is the deliberate pattern all seven existing app/api handlers follow (there is no
  server-side auth helper in lib/participants.ts), so this task did not introduce the duplication.

Deviations:
  None. Two explanatory comments were added (the orderBy rationale and the snapshot-vs-FK rationale);
  the plan gave both as prose in the task and the sibling handlers carry the same style.

Summary:
  Added app/api/trips/[id]/exchange-rates/route.ts. The body is parsed in its own try/catch into an
  `unknown` (400 "Invalid exchange rate." on malformed JSON) before the main try begins, then the
  handler awaits params, 404s on a missing trip, runs the participants-GET auth check, validates
  currency (non-blank string after trim) and rate (finite, > 0) in that fixed order with an immediate
  400 each, and upserts on the (tripId, currency) compound unique, responding 200 with an explicit
  { id, tripId, currency, rate } projection. REFERENCE.md §4 gained the route's line and the
  ExchangeRate schema line lost its now-stale "(021, in progress)" marker.

Key Decisions:
  No client component calls this endpoint in this feature, by explicit product decision recorded in
  the plan and spec §2.1/§7: the route is real infrastructure (this feature's Playwright fixtures use
  it) that avoids a second schema change when a later feature adds the entry screen. The task text
  and the shipped comment make that explicit so a future reader does not treat it as dead code.
  The compact single-line response projection avoids returning the raw Prisma row (which carries
  createdAt) — consistent with the participants GET's explicit { id, name } mapping.
  Gate B confirmed the parse try/catch sits genuinely outside the main try, so a malformed body can
  never be reported as a server failure and vice versa; that the trimmed `currency` binding is used
  by both the upsert's `where` and its `create`, so a create/where mismatch is impossible; that
  `update: { rate }` never rewrites the compound key, so a repeat PUT updates instead of duplicating;
  and that no unauthenticated caller can write (empty-string headers and cross-trip tokens were each
  traced against the sibling handlers).
