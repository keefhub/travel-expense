## 1. Business analysis — BA

### 1.1 Purpose

A shared trip's expenses (feature 020) record who paid and how each expense was split, but nobody
currently sees the *net* result of that history — who, on balance, owes whom. This feature adds a
read-only balances view that nets every recorded expense down to the minimum set of settlement
lines, converted into the trip currency, so a participant can tell at a glance how to square up
with the group. It also closes the gap 020's spec flagged (§7 item 1 of
[doc/features/020-attribute-an-expense-to-payer-and-split/spec.md](../020-attribute-an-expense-to-payer-and-split/spec.md)):
a shared trip currently has no aggregate view of its own expense data at all.

### 1.2 Actors & preconditions

- **Actor**: any current member of a shared trip — the trip creator, or a participant who joined
  via the trip's share link (feature 017). Identity is device-bound, exactly as in features
  016–020; no login exists.
- **Preconditions**: an active shared trip exists (a share link has been generated, feature 016);
  the viewing device is either the creator or a joined participant of that specific trip;
  connectivity is available, since balances are computed from server-side data.
- **Non-actor**: a device that is neither the trip's creator nor one of its joined participants
  cannot view that trip's balances — same stray-device boundary features 019 and 020 already
  enforce for their own screens.

### 1.3 Business rules

| ID | Rule | Source |
| --- | --- | --- |
| BR-021-01 | Opening the balances view shows a simplified list of who owes whom and how much, derived from every expense's payer and split data. | Scenario "I view the trip's simplified balances" |
| BR-021-02 | Every amount shown is converted into the trip currency, using the exchange rate on file for each non-trip currency used in the trip's expenses. | Scenario "Balances convert multi-currency expenses…"; Assumption 1 |

### 1.4 Data touched

- **Trip** (read) — trip currency, for conversion and for the balances view's own identity.
- **Participant** (read) — id and name, including participants who have since left or been
  removed (feature 019's `onDelete: SetNull` behavior; their name survives on past expenses).
- **Expense** / **ExpenseShare** (read, feature 020) — `amount`, `currency`,
  `payerParticipantIdSnapshot`/`payerName`, and each share's
  `participantIdSnapshot`/`name`/`amount` — the snapshot columns, not the live foreign keys, since
  a departed member's FK is null but their snapshot id and name survive (see
  [REFERENCE.md](../../../REFERENCE.md) §4's note on `prisma/schema.prisma`).
- **Exchange rate for a shared trip** (read, and — new in this feature — write) — does not exist
  in the data model yet. See §2.1 "Approach" for why this feature adds it.

### 1.5 Edge cases & negative paths

- No expenses recorded → "everyone settled up," no lines. **[in spec]**
- A pair's net balance is exactly 0 → that pair's line is omitted, even though other pairs may
  still owe each other. **[in spec]**
- A currency used in the trip's expenses has no exchange rate on file → the whole view is
  incomplete, not a partial number. **[in spec]**
- A departed/removed participant still has a balance → shown under their retained name. **[in
  spec]**
- Device offline when opening the view → friendly connectivity message. **[in spec]**
- Server unreachable when opening the view → friendly error message. **[in spec]** — in this
  app's existing architecture (see §2.1) this is the *same underlying failure* (a rejected fetch)
  as the offline case above; both scenarios are honored by one error-handling code path emitting
  one friendly message, consistent with `lib/participants.ts`'s established precedent (see
  [REFERENCE.md](../../../REFERENCE.md) §4).
- Uneven splits produce fractional-cent amounts after currency conversion → each displayed amount
  is rounded to 2dp, and the group's total owed equals total owing exactly. **[in spec]**
- **[derived]** A trip where only the creator has ever paid (no one else on the trip has recorded
  an expense) → same as the no-expenses case: nothing to net, "everyone settled up."
- **[derived]** A stray device (neither creator nor a joined participant of this specific trip)
  must not see this trip's balances — redirected home, mirroring `components/ManageParticipants.tsx`'s
  and `components/SharedExpenseForm.tsx`'s existing guard.
- **[derived]** A trip whose expenses are entirely in the trip's own currency needs no conversion
  and is trivially "complete" — `isComplete` must not default to `false` just because no
  non-trip-currency expense exists.
- **[derived]** Raw pairwise debts that chain through a third person (A owes B, B owes C the same
  amount) must simplify to a single direct line (A owes C), not two lines — this is the specific
  case the feature file's own "minimum number of settlements" scenario names.

### 1.6 Out of scope

- Marking any balance as settled (feature 022).
- Editing or correcting an expense from the balances view.
- Any per-currency (non-converted) balance display.
- Notifying participants of their balance outside the app.
- A full shared-trip "dashboard" (total spend, budget, category breakdown) equivalent to the solo
  trip's `components/Dashboard.tsx`. This feature only adds a balances view and its entry points —
  see §7 Open Question 3 for the scope boundary against 020's flagged "dashboard gap."
- A user interface for entering a shared trip's exchange rates. See §2.1 and §7 Open Question 1:
  this feature adds the server-side storage and a write endpoint so the data can exist at all, but
  ships no entry screen, per an explicit product decision (2026-09-19) to keep this feature's own
  scope to reading and displaying balances.
- A shared-trip equivalent of `lib/expenses.ts`'s browsable expense list — 020's spec (§7 item 3)
  raised this as an open question for 021 to resolve; this feature does not add one, since no
  scenario in `features/021.view-trip-balances.md` asks for a list, only for computed balances.

## 2. Technical specification — SA

### 2.1 Approach

Balances are computed from data that already lives in Postgres (`Expense`, `ExpenseShare`,
feature 020) plus one piece of data that currently has nowhere to live: a shared trip's exchange
rates. `lib/currency.ts`'s exchange-rate model is per-device `localStorage`
(`STORAGE_KEYS.exchangeRates`), which cannot back a value every participant must see identically.
This feature therefore adds a small `ExchangeRate` Prisma model scoped to a trip, plus a write
endpoint so that data can exist — **by explicit product decision (2026-09-19), no entry UI ships
in this feature**; the endpoint exists so the write path is real (not a shape fabricated only for
tests) and so a follow-up feature can add the actual entry screen without another schema change.
See §7 Open Question 1.

The balances computation itself is a new pure module, `lib/balances.ts`, that nets every expense's
payer/share amounts per identity (trip creator or participant, keyed by the same
snapshot-id-or-`TRIP_CREATOR_ID` pattern feature 020 already established) and then simplifies the
net positions to a minimum set of settlement lines with a greedy largest-creditor/largest-debtor
match — the same approach used by comparable expense-splitting apps. All arithmetic after currency
conversion is done in integer cents so that rounding happens exactly once, at the point a line is
formatted for display, guaranteeing the "reconciles exactly" requirement (BR-021-10) without an
epsilon comparison anywhere.

A new Route Handler, `GET /api/trips/[id]/balances`, loads the trip, its expenses (with shares),
and its exchange rates, and returns the computed result. A new client screen,
`components/TripBalances.tsx`, mounted at `/trips/[token]/balances`, resolves the viewing device's
role from local storage exactly as `components/ManageParticipants.tsx` and
`components/SharedExpenseForm.tsx` already do, then renders the result. Two existing components
gain a "View balances" entry link: `components/ShareTripLink.tsx` (the creator's path, at
`/settings`, alongside the existing "Manage participants" link) and
`components/JoinedTripSummary.tsx` (the joined-participant's path, alongside "View participants"
and "Add expense").

### 2.3 Data model

```ts
// lib/types.ts additions

export interface SharedExchangeRate {
  id: string;
  tripId: string;
  currency: string;
  rate: number;
}

export interface BalanceLine {
  fromId: string;   // TRIP_CREATOR_ID or a Participant id (snapshot id if departed)
  fromName: string;
  toId: string;
  toName: string;
  amount: number;    // trip-currency, rounded to 2 decimal places
}

export interface TripBalancesResult {
  lines: BalanceLine[];
  isComplete: boolean;
  missingCurrencies: string[]; // non-trip currencies used in expenses with no rate on file
}
```

```ts
// lib/balances.ts

export interface BalanceExpenseInput {
  amount: number;
  currency: string;
  payerId: string | null;   // null => trip creator, mirrors Expense.payerParticipantIdSnapshot
  payerName: string;
  shares: { id: string | null; name: string; amount: number }[];
}

export function getTripBalances(
  expenses: BalanceExpenseInput[],
  tripCurrency: string,
  rates: { currency: string; rate: number }[]
): TripBalancesResult;
```

```prisma
// prisma/schema.prisma addition
model ExchangeRate {
  id        String   @id @default(cuid())
  tripId    String
  trip      Trip     @relation(fields: [tripId], references: [id], onDelete: Cascade)
  currency  String
  rate      Float
  createdAt DateTime @default(now())
  @@unique([tripId, currency])
  @@index([tripId])
}
// Trip model gains: exchangeRates ExchangeRate[]
```

### 2.6 Non-functional notes

- **Offline / connectivity**: shared trips already require connectivity for every existing screen
  (`OVERVIEW.md` §2 v2 amendment); this feature adds no offline fallback, consistent with that.
- **Mobile-first layout**: the balances list follows `design.md`'s list/row patterns (read at
  implementation time, per `CLAUDE.md`); no new interaction pattern is introduced — it is a
  read-only list, most similar in shape to `components/ManageParticipants.tsx`'s participant rows
  minus any action controls.
- **Error handling**: every friendly-error and empty-state message is a plain string rendered with
  `role="alert"` (errors) or `role="status"` (informational), matching every other shared-trip
  screen's convention — no new pattern introduced.
- **Next.js**: no Next.js API is used here beyond what features 016–020 already established
  (`params` as a `Promise`, a dynamic Route Handler segment, a Client Component island under a
  Server Component route file) — confirmed against `REFERENCE.md` §5, which this repo's prior
  features already verified against `node_modules/next/dist/docs/`. No new doc read was required.

## 7. Open questions & risks

1. **No entry UI for shared-trip exchange rates ships in this feature** (Challenge #1/#4). The
   `ExchangeRate` model and its write endpoint (TS-021-01, TS-021-05) exist so the data can be
   real, but until a follow-up feature adds an actual entry screen, a real shared trip with
   multi-currency expenses will always show "incomplete" balances in production — only Playwright
   fixtures can currently produce a "rate entered" state. Recommend the next `/feature-discovery`
   pass consider a small feature (or an extension of 007) that lets any trip member enter a
   shared trip's exchange rates.
2. **Debt-simplification algorithm is a greedy heuristic, not a formally minimal solver**
   (Challenge #2). Correct for every scenario this feature specifies; flagged in case a much
   larger or more tangled multi-party trip later needs a stronger guarantee.
3. **Scope boundary against 020's "dashboard gap"**: 020's spec (§7 item 1) recommended 021 "own
   closing" the gap that a shared trip has no aggregate view at all. This feature closes it with a
   balances view and two entry points, but does **not** build a full dashboard (total spend,
   budget, category chart) — no scenario in `features/021.view-trip-balances.md` asks for one.
   Flagging so the user can confirm this partial closure is sufficient, or file a further feature
   for the rest.
4. **Conversion philosophy diverges from the solo dashboard's**: this feature's "incomplete"
   behavior (BR-021-06) is all-or-nothing (mirrors the remaining-budget precedent), while
   `lib/currency.ts`'s `getConvertedTotals` (used by the solo `Dashboard.tsx`) computes a partial
   total that excludes only the missing currency. Both are individually justified by their own
   precedent, but the app now has two different "missing rate" philosophies live at once — noting
   this in case the user wants them reconciled later.
