## 1. Business analysis — BA

### 1.1 Purpose

A traveller needs to log what they spend as they go, so their trip's total and per-category
breakdown (built in later features) are accurate. This feature is the one place a new `Expense`
record gets created: a form covering amount, currency, category, date, payment method, location,
and an optional description, saved against the single active trip.

### 1.2 Actors & preconditions

- **Actor:** the traveller.
- **Precondition:** an active trip exists (Scenario "User opens the record expense page": "Given the
  user has an active trip"). If none exists, there is nothing to record an expense against.

### 1.3 Business rules

| ID | Rule | Source |
|---|---|---|

### 1.4 Data touched

- **Reads:** the active `Trip` (for the default currency and the trip-period warning check), the
  combined default + custom `Category` list (feature 010), the existing `Expense` list (to append
  to, not replace).
- **Writes:** the `Expense` list — appends exactly one new `Expense` record per successful
  submission. Does not touch `Trip`, `Category`, or `ExchangeRate` storage.

### 1.5 Edge cases & negative paths

- No active trip when the page is opened directly (stale bookmark, direct URL entry) — there is
  nothing to attach an expense to. `[derived]`
- This is the very first expense ever recorded for the trip (the stored expense list is empty) — the
  append must still work correctly against an empty array. `[derived]`
- A storage failure on save (local storage full/unavailable, feature 012's `SaveResult` contract) —
  must show a friendly error and preserve the user's entered values so they don't have to retype them
  (matching the precedent already established for trip edit/create in features 002/003). `[derived]`
- Whitespace-only entry in a mandatory text field (e.g. location `"   "`) must be treated as blank,
  not accepted — matching `validateTripForm`'s existing trim-then-check pattern. `[derived]`
- A blank description is saved as genuinely absent (the `description` key omitted), not as an empty
  string — matching how an absent `Trip.budget` is handled in feature 001/002, not `""`. `[derived]`
- The expense date exactly equals the trip's start or end date — this is **inside** the trip period,
  not outside it, so no warning should fire at the boundary itself. `[derived]`

### 1.6 Out of scope

- Editing or deleting a saved expense — no scenario describes this; feature 009's dashboard mentions
  a "view-only" detail tap-through (OVERVIEW §3, Assumption 5), not an edit path here.
- Any conversion between the expense's currency and the trip's currency — that arithmetic is feature
  006 (multi-currency-expense-tracking), not this one. This feature only records the amount and
  currency as entered.
- A follow-up free-text field to elaborate on a payment method of "Other" — the assumption this
  feature relies on (OVERVIEW §3, Assumption 6) only asks for a dropdown with an "Other" choice, not
  a way to specify what "other" means.
- The unsaved-input browser warning (`beforeunload`) — that is feature 011, built explicitly as an
  extension of this form.
- Displaying the recorded expense anywhere (a list, a dashboard, a total) — that's feature 009.
- Receipt/photo attachment — explicitly not required per OVERVIEW §2.

## 2. Technical specification — SA

### 2.1 Approach

A new pure domain module, `lib/expenses.ts`, mirrors the shape `lib/trip.ts` already established:
form-values type, a validation function returning both blocking `errors` and non-blocking
`warnings`, and a `submitExpense` function that validates, then appends to the existing expense list
and saves. `lib/countries.ts` gains one small addition — a derived, deduplicated list of supported
currency codes — reusing feature 004's existing country data rather than introducing a second
currency source. A new `ExpenseForm` component renders all seven fields, pre-filled via a
`getInitialExpenseFormValues` helper (today's date, the trip's currency), and displays the live
trip-period warning the same way `TripEditForm` already displays its live-derived fields. A new
route, `app/expenses/new/page.tsx`, replaces the feature-015 placeholder with the same
hydration-safe trip-load-and-redirect-if-none pattern already used by `/trip/edit` and `/trip/new`.
The "success message" requirement is satisfied via a one-time `sessionStorage` flag set by the form
right before navigating home and read once by `app/page.tsx` — not `useSearchParams`, because the
vendored Next.js docs (confirmed below) require wrapping any `useSearchParams` caller in a `Suspense`
boundary on a statically-prerendered page, which is unnecessary complexity for a message this simple.

### 2.3 Data model

No changes to `lib/types.ts` — `Expense` already has every field this feature needs
(`id`, `amount`, `currency`, `category`, `date`, `paymentMethod`, `location`, `description?`).

```ts
// lib/expenses.ts — new file
export interface ExpenseFormValues {
  amount: string;
  currency: string;
  category: string;
  date: string;
  paymentMethod: string;
  location: string;
  description: string;
}

export const PAYMENT_METHODS: readonly string[] = [
  "Cash",
  "Credit Card",
  "Debit Card",
  "Mobile Payment",
  "Other",
];

export const EXPENSE_SAVED_FLAG_KEY = "travel-expense:expense-saved";

export function getInitialExpenseFormValues(trip: Trip, today: string): ExpenseFormValues;

export interface ExpenseValidationResult {
  errors: Partial<Record<keyof ExpenseFormValues, string>>;
  warnings: Partial<Record<keyof ExpenseFormValues, string>>;
}

export function validateExpenseForm(
  values: ExpenseFormValues,
  trip: { startDate: string; endDate: string }
): ExpenseValidationResult;

export type SubmitExpenseResult =
  | { status: "invalid"; errors: ExpenseValidationResult["errors"] }
  | { status: "saved"; expense: Expense }
  | { status: "storage-error"; error: string };

export function submitExpense(
  values: ExpenseFormValues,
  trip: { startDate: string; endDate: string },
  deps: {
    getExpenses: () => Expense[];
    saveExpenses: (expenses: Expense[]) => SaveResult;
    generateId: () => string;
  }
): SubmitExpenseResult;
```

### 2.6 Non-functional notes

- **Hydration safety:** `app/expenses/new/page.tsx` never reads `localStorage` during render, per
  REFERENCE.md §5 — it follows the same pattern as `/trip/edit`/`/trip/new`.
- **Mobile-first form:** `ExpenseForm` follows `design.md` §6 (label above input, `role="alert"`
  errors below each field, `gap-1`/`gap-4` spacing) and reuses the input types already established
  by `TripSetupForm`/`TripEditForm` (`<select>` for closed sets, `type="date"`, a decimal text input
  for the amount).
- **Warning vs. error distinction:** the trip-period warning uses `role="status"` (a polite,
  non-interrupting live region) rather than `role="alert"` (assertive, reserved for blocking
  validation errors elsewhere in this codebase) — a deliberate distinction since BR-005-08b requires
  the warning to never block saving.
- **Next.js check:** confirmed via
  `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/use-search-params.md` ("Behavior
  > Prerendering"): "a static page that calls `useSearchParams` from a Client Component must be
  wrapped in a `Suspense` boundary, otherwise the build fails." `app/page.tsx` is currently
  statically prerendered (its route table entry shows `○ (Static)`). Rather than introduce a new
  `Suspense` boundary and a second client subtree just to read one query flag, TS-005-11 uses
  `sessionStorage` plus a plain `useEffect` instead — no new Next.js API surface, and consistent with
  how this app already avoids anything beyond what REFERENCE.md §2 lists as installed.
- **Offline:** no network calls; unaffected by the offline requirement.

## 6. Contrarian review — BA ↔ SA

| # | Raised by | Challenge | Resolution | Outcome |
|---|---|---|---|---|
| 1 | SA | BR-005-10/11 (currency and category must come from closed sets) are BA rules asserting an implementation detail ("selected from a set") the Gherkin never states — it only says "selects a currency"/"selects a category," which could equally describe free-text entry with autocomplete. Is this an assumption dressed up as a requirement? | Accepted as a labeled `[derived]` assumption, not silently treated as spec text — reworded in §1.3 to cite the actual reasoning (feature 004/010 are this app's only sources of currency/category values; nothing else in the app supports free-text currency codes or ad hoc categories) rather than claiming the Gherkin requires it. If this assumption is wrong, the fix is small (loosen the two `<select>` elements to text inputs) and doesn't touch `submitExpense`'s save logic. | Accepted |
| 2 | BA | The SA's design for the trip-period warning (TS-005-05) computes it as part of `validateExpenseForm`'s return value alongside blocking `errors`, then `submitExpense` (TS-005-07) explicitly ignores `warnings` when deciding whether to save. Is bundling a non-blocking concern into the same function as blocking validation over-engineered — should warnings be a wholly separate function so `submitExpense` can't accidentally start checking them later? | Rejected — the alternative (two separate functions, one for errors and one for warnings) would mean computing the same date-comparison logic in two places or awkwardly sharing internal state between two exported functions for no behavioral benefit. A single `ExpenseValidationResult` with two distinct keys (`errors`/`warnings`) makes the non-blocking nature explicit in the type itself, and `submitExpense`'s use of only `.errors` is a one-line, easily-reviewed decision, not a hidden coupling. | Rejected |
| 3 | SA | AC-005-01, as originally drafted from the raw Gherkin, said "the app should display the expense form" — untestable prose with no way to assert pass/fail. | Tightened to name every specific field shown, matching the pattern already used for feature 002/003's ACs. | Accepted |
| 4 | BA | The SA's TS-005-11 (a `sessionStorage` success-message flag) modifies `app/page.tsx` — a file three prior features (001, 002, 003) have already each added a small piece to. Is stacking a fourth unrelated concern onto that one file scope creep, or should the success message instead live in a new dedicated component? | Rejected — the message is one `useEffect` and a few lines of conditional JSX, not a new subsystem; introducing a separate component and passing state into `app/page.tsx` for it would be more code for a smaller and less discoverable result. This mirrors the same "additive, small, in the existing placeholder" pattern features 002/003 already used for their own `app/page.tsx` additions ("Edit trip" and "Start a new trip" links), not a new pattern. | Rejected |
| 5 | SA | Is `generateId` really worth injecting as a dependency of `submitExpense`, given no other function in this codebase injects a clock/ID generator, and the real implementation will always just be `() => crypto.randomUUID()`? ## 7. Open questions & risks

1. **(Challenge 1 / Challenge 5)** Two low-stakes design choices — closed-set currency/category
   selection (§1.3, BR-005-10/11) and dependency-injecting `generateId` (§6, Challenge 5) — are
   documented assumptions/decisions, not confirmed requirements. Both are cheap to reverse if wrong
   and don't affect any other feature's contract.
2. **Payment-method list contents** (`PAYMENT_METHODS` in §2.3) are an SA-authored list
   (`Cash`/`Credit Card`/`Debit Card`/`Mobile Payment`/`Other`) — OVERVIEW's Assumption 6 confirms
   only "a dropdown with an Other option," not these specific four non-"Other" values. If the user
   wants a different set, this is a one-array edit with no other ripple effect.
