## 1. Business analysis — BA

### 1.1 Purpose

A traveller who has started filling in the record-expense form should not lose that work by
accident. This feature warns before the two ways in-progress input can be lost — a browser
refresh/close and navigating to another page in the app — but only when there is actually
something to lose, and never blocks the save flow itself (submitting the form is not "leaving with
unsaved input").

### 1.2 Actors & preconditions

- **Actor:** the traveller, while on the record-expense page (`/expenses/new`).
- **Precondition:** feature 005 (record-expense) is complete — this feature extends its form and
  route; verified present in the working tree (`components/ExpenseForm.tsx`,
  `app/expenses/new/page.tsx`, both committed under `feat(005)`).

### 1.3 Business rules

| ID | Rule | Source |
|---|---|---|
| BR-011-01 | Refreshing the record-expense page while the form is empty (unchanged from its initial state) does not show a warning. | Scenario "User refreshes record expense page with empty form" |
| BR-011-02 | Refreshing the record-expense page while the form has unsaved input shows the browser's standard refresh-confirmation warning. | Scenario "User refreshes record expense page with unsaved input" |
| BR-011-03 | Confirming that refresh reloads the page, and the previously-entered input is gone (nothing in this app persists draft input — it was never saved). | Scenario "User confirms refresh" |
| BR-011-04 | Cancelling that refresh keeps the user on the page with their entered input still visible. | Scenario "User cancels refresh" |
| BR-011-05 | Attempting to navigate away from the record-expense page (in-app, not a refresh) while the form has unsaved input shows a warning that unsaved input will be discarded. | Scenario "User navigates away with unsaved input" |
| BR-011-06 | Confirming that navigation leaves the record-expense page and discards the input. | Scenario "User confirms navigation away" |
| BR-011-07 | Cancelling that navigation keeps the user on the record-expense page with their input still visible. | Scenario "User cancels navigation away" |
| BR-011-08 | "Unsaved input" means the form's current values differ from what the form showed when it was first displayed — not "any field is non-blank." | BR-011-10 | Warned or not, discarding on confirm never re-saves or restores input on a subsequent visit — refreshed/navigated-away input is simply gone, matching OVERVIEW's "Unsaved input is discarded on refresh." | OVERVIEW §2: "Unsaved input is discarded on refresh." |

### 1.4 Data touched

- **Reads:** none. This feature reads no persisted data — it only observes the record-expense
  form's own in-memory state (feature 005's `ExpenseFormValues`).
- **Writes:** none. No new storage key, no change to any existing one. This is a pure UI-behavior
  feature layered on top of feature 005's existing form.

### 1.5 Edge cases & negative paths

- The user changes a field and then changes it back to its original value before attempting to
  leave — the form is, by BR-011-08's definition, no longer dirty, so no warning should fire.
  `[derived]`
- The user clicks a `BottomNav` link that points to the page they're already on (e.g. clicking "Add
  Expense" while already on `/expenses/new`) — this is not "leaving" the page, so no warning should
  fire even with unsaved input present. `[derived]`
- The user has unsaved input and clicks "Save expense," but the submission fails validation
  (`SubmitExpenseResult.status === "invalid"`) — the user is still on the page with the same
  unsaved input; no navigation occurred, so this isn't a "leaving" event and no warning is relevant
  here (BR-011-09 only concerns a *successful* save's navigation). `[derived]`
- The user has unsaved input and clicks "Save expense," but the save fails with a storage error
  (`status === "storage-error"`) — same reasoning as above: no navigation occurred. `[derived]`
- The browser's native refresh-confirmation dialog's exact wording is not controllable by
  application code in any modern browser (see §2.6) — BR-011-02's "standard browser refresh
  warning" is the only literal thing the app can produce; it cannot itself state "unsaved changes
  may be lost" as custom text, only trigger the browser's own generic prompt. Flagged as a
  spec-vs-platform-reality gap, not silently reworded. `[in spec, constrained by platform — see §2.6
  and §7]`

### 1.6 Out of scope

- Auto-saving draft input so it survives a refresh — OVERVIEW explicitly states "Unsaved input is
  discarded on refresh," i.e. the warning exists so the user can *choose* to stay, not so the app
  can recover the input for them.
- Warning anywhere other than the record-expense page — no other form in this app (trip setup,
  trip edit, category management, exchange rates) is in this feature's scope; OVERVIEW's bullet and
  every Gherkin scenario name only the record-expense page.
- Warning on the browser back/forward button specifically as a distinct mechanism from "navigate
  away" — the Gherkin doesn't distinguish back/forward from any other in-app navigation, and no
  Next.js API in this version exposes a back/forward-specific hook (see §2.6); this spec treats all
  in-app navigation away from the page uniformly.
- Any change to what feature 005 already validates, saves, or displays — this feature only adds
  dirty-tracking and warning behavior around the existing form.

## 2. Technical specification — SA

### 2.1 Approach

A new custom hook, `hooks/useUnsavedChangesWarning.ts` (a new `hooks/` directory — this repo has
none yet; verified via `git ls-files` and a directory listing, no existing `hooks/` folder), takes a
single `isDirty: boolean` and, only while `isDirty` is `true`, registers two things for the
component's lifetime: a native `window` `beforeunload` listener (covers refresh and tab/window
close — BR-011-02 through 04) and a `document`-level, capture-phase `click` listener that detects a
click on an in-app `<a href>` element pointing to a different path than the current one, intercepts
it with `event.preventDefault()`, and shows `window.confirm(...)` (BR-011-05 through 07). Both are
standard Web Platform APIs — no new dependency, matching REFERENCE.md §2's "no UI/animation
dependencies without asking" constraint and this repo's established "hand-roll it" precedent for
anything not already installed. `ExpenseForm` computes `isDirty` by comparing its current `values`
against a `useRef`-captured snapshot of the initial values (captured once, on mount, from the same
call to `getInitialExpenseFormValues` that seeds `values` itself) and clears/bypasses the dirty
check immediately before its own successful-save navigation (BR-011-09), so the hook never has to
special-case "did we just save."

### 2.2 Design elements

| ID | Element | Satisfies |
|---|---|---|
| TS-011-01 | `hooks/useUnsavedChangesWarning.ts` — `export default function useUnsavedChangesWarning(isDirty: boolean): void`. A `'use client'`-only hook (no directive of its own needed since it's not a component, but it uses `useEffect` and browser globals, so every caller must already be a Client Component — `ExpenseForm` already is). | Groundwork for TS-011-02/03 |
| TS-011-02 | Inside the hook, one `useEffect` keyed on `[isDirty]`: when `isDirty` is `true`, adds a `beforeunload` listener that calls `event.preventDefault()` (the standards-track way to trigger the browser's native confirmation — see §2.6) and, for older-engine compatibility, also sets `event.returnValue = ""`; the effect's cleanup removes the listener. When `isDirty` is `false`, no listener is added (nothing to clean up). | BR-011-01, 02 |
| TS-011-03 | A second `useEffect`, also keyed on `[isDirty]` and only active while `isDirty` is `true`: attaches a capture-phase `click` listener on `document`. On each click, it walks up from `event.target` to find the nearest ancestor `<a>` element (`(event.target as HTMLElement).closest("a[href]")`); if none is found, does nothing. If found, resolves the link's `href` to a same-origin pathname and compares it to `window.location.pathname`; if they're equal (BR-011's "same page" edge case, §1.5), does nothing. Otherwise calls `event.preventDefault()` and `event.stopImmediatePropagation()` (so Next.js's own `<Link>` click handler, registered later in bubble order, never fires client-side navigation for the intercepted click), then shows `window.confirm("Leaving this page will discard your unsaved expense. Continue?")`; if the user confirms, it performs the navigation itself via `window.location.assign(href)` (a full navigation, not a Next.js client-side transition — chosen because this hook has no access to the App Router's `router` instance without becoming component-coupled, and a full navigation is an acceptable cost for a rarely-taken confirmed-discard path). If the user cancels, nothing further happens (the click was already prevented, so the user stays). | BR-011-05, 06, 07, and the same-page edge case from §1.5 |
| TS-011-04 | `components/ExpenseForm.tsx` — add `const initialValuesRef = useRef(values);` immediately after the existing `useState<ExpenseFormValues>` initialization (capturing the same object `getInitialExpenseFormValues` produced, once, via the ref's lazy-nothing default since `useRef(values)` reads `values` only on the initial render). Compute `const isDirty = JSON.stringify(values) !== JSON.stringify(initialValuesRef.current);` and call `useUnsavedChangesWarning(isDirty);` once, unconditionally, near the top of the component body (before `handleSubmit`). | BR-011-08, TS-011-01 |
| TS-011-05 | `components/ExpenseForm.tsx`'s `handleSubmit`, on the `"saved"` branch only: before calling `router.push("/")`, no additional code is needed — the component is about to unmount (navigating away via the App Router's own client-side transition, not a `<a>` click), so `useUnsavedChangesWarning`'s click-listener never sees this navigation at all (it only intercepts anchor clicks) and its `beforeunload` listener only fires on an actual document unload, which `router.push` alone does not trigger. This satisfies BR-011-09 with no special-case code — confirmed by tracing exactly how each of the two listeners could possibly fire, and neither does for a `router.push` call. | BR-011-09 |

### 2.6 Non-functional notes

- **`beforeunload` text is not customizable.** Confirmed against the standards-track behavior this
  repo's own target browsers implement: every modern browser (Chrome, Firefox, Safari, Edge) ignores
  any custom string passed via `event.returnValue` or shown in a dialog and instead displays its own
  fixed, browser-controlled message — this has been the case since roughly 2016, specifically to
  prevent this exact API being used for phishing-style fake dialogs. The Gherkin's "the warning
  should indicate that unsaved changes may be lost" (BR-011-02) is satisfied by the *fact* that a
  warning appears, not by the app supplying that literal wording — no app code can supply it. This
  is stated explicitly rather than silently building toward an AC that can never literally pass.
- **No App Router navigation-blocking API exists in this Next.js version.** Checked
  `node_modules/next/dist/docs/01-app/` for any `beforeunload`, route-change, or navigation-blocking
  guidance (`grep -rl beforeunload node_modules/next/dist/docs/` returns no files) and confirmed
  `<Link>` "extends the HTML `<a>` element" per
  `node_modules/next/dist/docs/01-app/03-api-reference/02-components/link.md` — i.e., it renders a
  real anchor tag, which is what makes the click-interception approach in TS-011-03 possible at all.
  There is no `useBlocker`/`usePrompt`-equivalent hook in App Router (that was a React Router/Pages
  Router pattern); this is a known, documented gap in the framework, not an oversight in this spec.
- **`window.location.assign` (a full page reload) rather than client-side routing for a confirmed
  discard-and-leave.** This trades away the App Router's fast client-side transition for exactly one
  path — a user who already chose to discard their input and leave — which is an acceptable,
  infrequent cost, not a general regression to full-page navigation across the app.
- **Mobile-first / offline:** no network calls; this feature is pure client-side event handling and
  works identically offline.
- **No new dependency:** both mechanisms (`beforeunload`, anchor-click interception) are Web
  Platform standards already available in every browser this app targets — nothing added to
  `package.json`.

## 7. Open questions & risks

1. **(Challenge 3)** Whether `window.location.assign`'s full-page reload is acceptable for the
   confirmed-discard-and-leave path given this app's offline-capable requirement is not resolved by
   this spec — genuinely low-stakes (affects only an explicit-discard click while offline) and cheap
   to revisit (swapping in a router-based navigation later, once a way to reach the App Router
   instance from outside a component is worked out, would not change this feature's business rules
   or ACs at all).
2. **(§1.5, §2.6)** `beforeunload`'s browser-native dialog text is not app-controllable in any
   current browser — BR-011-02/AC-011-02 are satisfied by the warning's *existence*, not its exact
   wording. This is a platform constraint, not an implementation gap, and is not expected to change.
3. The exact confirmation-prompt copy for in-app navigation (TS-011-03's suggested
   `window.confirm("Leaving this page will discard your unsaved expense. Continue?")`) is an
   SA-authored string — OVERVIEW/Gherkin only require that a warning appear and state that input
   will be discarded, not this literal wording. Low-stakes, one-line change if the user wants
   different copy.
