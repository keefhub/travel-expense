## 1. Business analysis — BA

### 1.1 Purpose

Feature 017 let friends join a trip, and feature 018 let a device switch between every trip it
belongs to, but nothing yet lets anyone see who else is actually on a trip, or leave/remove
someone once they're on it. This feature closes that gap: any creator or participant can open a
participants screen and see everyone currently on the trip, with the creator visibly distinguished
from everyone else; the creator alone can remove another participant; any non-creator participant
can leave voluntarily; and both actions require confirmation, need connectivity, and never rewrite
a departed participant's past expense history. The creator themselves has no "leave" option, since
per the feature file's own assumption 4, the equivalent action for them is deleting/replacing the
trip (out of this feature's scope).

### 1.2 Actors & preconditions

- **Actor:** the trip's **creator** (the device holding `getSharedTripLink()` for this trip) or any
  of its **participants** (a device holding a `JoinedTrip` entry for this trip's `shareToken`, per
  feature 017). Both roles view the same list; only the creator can remove someone else.
- **Precondition (all scenarios):** the trip is a shared trip (feature 016 has generated a link for
  it) and has at least one participant who joined via that link (feature 017).
- **Precondition (viewing the screen at all):** the visiting device must be either this trip's
  creator or one of its joined participants — see TS-019-05's stray-token guard, mirroring
  `SharedTripView.tsx`'s (018) identical guard for a foreign `/trips/[token]` visit.

### 1.3 Business rules

| ID | Rule | Source |
| --- | --- | --- |
| BR-019-01 | Any creator or participant on a shared trip can open a participants screen and see everyone currently on the trip. | Gherkin: "I view the trip's participants" |
| BR-019-02 | The creator is always visibly labeled as the creator in that list, distinct from participant rows. | Gherkin, same scenario |
| BR-019-03 | When the viewer is the creator, they can remove another participant, and once removed that participant is no longer listed. | Gherkin outline: "Only the creator can remove other participants" — "the creator" row |
| BR-019-04 | When the viewer is a non-creator participant, no remove action for any other participant is available to them. | Gherkin outline, same scenario — "a participant" row; Assumption 2 |
| BR-019-05 | A non-creator participant can voluntarily leave the trip at any time, with no approval step; once they leave, they are no longer listed. | Gherkin: "A participant leaves the trip voluntarily"; Assumption 3 |
| BR-019-06 | The creator is never offered a "leave" action for themselves. | Gherkin: "The creator has no option to leave their own trip"; Assumption 4 |
| BR-019-07 | Removing or leaving does not rewrite or delete that participant's already-recorded expenses; those expenses still show the departed participant's name, and the person is simultaneously no longer listed as a current participant. | Gherkin: "Removing or leaving preserves past expense history"; Assumption 1 |
| BR-019-08 | A participant is identified for removal by their own underlying record, not by display name, so removing one of two same-named participants removes only that specific one and leaves the other listed. | Gherkin: "Removing the correct participant among duplicate names"; Assumption 5 |
| BR-019-09 | Leaving or removing takes effect only after an explicit confirmation step; the action is not performed on the triggering tap/click alone. | Gherkin: "Leaving or removing requires confirmation"; Assumption 6 |
| BR-019-10 | Attempting to leave or remove while the device has no connectivity shows a friendly message that the action requires connectivity. | Gherkin: "Leaving or removing while offline"; Assumption 7; OVERVIEW §2 |
| BR-019-11 | If, after confirming, the app cannot reach the server, the visitor sees a friendly error message and the participant list is left unchanged. | Gherkin: "Leaving or removing fails when the server is unreachable" |

### 1.4 Data touched

- **Participant** (server entity, from feature 017 — read and, new to this feature, **deleted**):
  this feature's remove/leave action permanently deletes the target row. No other feature writes to
  this table today.
- **Trip** (server entity, read-only here): looked up by its internal id to authorize a request (does
  the caller's token match the trip's `creatorToken`, or one of its participants'
  `participantToken`?) and, implicitly, to confirm the trip itself still exists.
- **SharedTripLink** (local, creator's device, read-only): `getSharedTripLink()` supplies the
  creator's `tripId` and `creatorToken` for authorizing removal requests. Never written by this
  feature.
- **JoinedTrip[]** (local, participant's device, read **and** write): `getJoinedTrips()` supplies a
  participant's own `tripId`, `participantId`, and `participantToken`. Written once, by a
  participant who successfully leaves: their own entry for this trip is removed from the array so
  their own device stops offering that trip (consistent with feature 018's switcher, which then
  drops the entry from its list on this same device).
- **Expense** (not touched): no shared-trip expense entity exists yet (that is feature 020's job —
  see §1.6 and §7 Open Item 1). This feature's obligation under BR-019-07 is negative — do not
  delete or rewrite anything expense-shaped — which is trivially satisfied today since nothing in
  this feature's design reads or writes any expense data at all.

### 1.5 Edge cases & negative paths

- Cancelling the confirmation step leaves the participant list, and the server, completely
  untouched — no request is fired. `[derived]` from BR-019-09.
- A device that is neither this trip's creator nor one of its joined participants opens the
  participants screen via a stray/guessed URL → redirected home without seeing any list, mirroring
  `SharedTripView.tsx`'s (018) identical guard for a foreign `/trips/[token]` visit. `[derived]`
- A participant attempts to remove a participant id that does not belong to this trip (or has
  already been removed by a concurrent action) → the server responds "not found," and the confirming
  device sees the same generic friendly error BR-019-11 defines, with the list unchanged. `[derived]`
- A creator's device and a participant's own removal race (both act on the same participant near
  simultaneously) → the second request 404s once the row is gone; treated identically to any other
  "not found" failure, no special copy. `[derived]`
- What a **removed** (not self-leaving) participant's own device sees the next time it revisits the
  trip is explicitly out of scope — see the feature file's own Deferred section and §1.6.

### 1.6 Out of scope

(carried verbatim from the feature file, since the BA must not re-litigate scope already settled
there)

- What a removed or departed participant's own device sees the next time it tries to access the
  trip (e.g. being redirected out) — not addressed by this feature.
- Attributing expenses to participants or computing splits/balances — that is feature 020.
- Re-inviting a removed participant, or any block/ban list preventing them from rejoining via the
  same link.
- Transferring trip ownership to another participant.
- Editing a participant's own display name after joining (carried over from feature 017's scope).

Additionally, out of scope **by this analysis** (not stated in the feature file, but excluded
because no scenario in it exercises them):

- Distinguishing "offline" from "a reachable-but-erroring server" for the leave/remove action —
  both source scenarios describe the same underlying failure (a request that cannot complete) and
  are satisfied by one collapsed friendly-error branch; see Contrarian Review #1.
- Any dedicated handling for viewing the participants list itself while offline (as opposed to the
  leave/remove action) — no scenario asks for this; see Contrarian Review #1.
- Rate-limiting or abuse protection on the new participant-management endpoints — same accepted-risk
  category as feature 017's Open Question #1 for its own public join endpoint.

## 2. Technical specification — SA

### 2.1 Approach

Add one Route Handler pair under the trip's internal id — `GET /api/trips/[id]/participants` (list)
and `DELETE /api/trips/[id]/participants/[participantId]` (remove) — reusing the
`x-creator-token`/`participantToken` identity model features 016/017 already established, rather
than inventing a new auth scheme. The DELETE endpoint is deliberately **one** endpoint serving both
"the creator removes someone else" and "a participant leaves," distinguished only by which header
is presented and whose row it matches: a request is authorized when either `x-creator-token`
matches the trip's `creatorToken` (any participant may be targeted), or `x-participant-token`
matches the **target** participant's own `participantToken` (self only). This mirrors feature 017's
own single-`resolveTrip`-helper-serving-two-verbs precedent (§2.1 there) and avoids a second,
parallel "leave" endpoint whose authorization logic would otherwise duplicate the same trip/participant
lookups.

On the client, one new route, `/trips/[token]/participants`, serves both roles from a single
component, `components/ManageParticipants.tsx`. It determines the viewing device's role the same
way `components/TripSwitcher.tsx` (018) already does — by comparing local storage to the URL's
token — rather than trusting anything the server tells it about "who am I": `getSharedTripLink()`
matching this `token` means creator; failing that, `findJoinedTrip(getJoinedTrips(), token)`
matching means participant; matching neither means a stray URL, handled by TS-019-05's guard. Two
existing, already-shipped components each gain one new plain link into this screen —
`components/ShareTripLink.tsx` (creator, from Settings, 016) and `components/JoinedTripSummary.tsx`
(participant, from `/join/[token]` and `/trips/[token]`, 017/018) — both additive changes that leave
every existing rendered string those components' own Playwright specs already assert on fully
intact (see Contrarian Review #2).

Because no shared-trip `Expense` entity exists yet (feature 020), BR-019-07's "past expenses still
show the departed participant's name" is, for this feature, a **negative** constraint rather than
something to build: the removal design must not (and does not) touch, cascade to, or attempt to
rewrite anything expense-shaped. `prisma/schema.prisma`'s `Participant` model has no relation any
other model points to besides `Trip`, so a hard `db.participant.delete()` is safe today; see §7 Open
Item 1 for what feature 020 will need to preserve once it exists.

### 2.2 Design elements

| ID | Design element | Satisfies |
| --- | --- | --- |
| TS-019-01 | `GET /api/trips/[id]/participants` (`app/api/trips/[id]/participants/route.ts`) — looks up `db.trip.findUnique({ where: { id } })`; no match → `404 { error: "Trip not found." }`. Authorizes via `x-creator-token` (matches `trip.creatorToken`) **or** `x-participant-token` (matches any row from `db.participant.findMany({ where: { tripId: id } })`); neither → `403 { error: "Not authorized." }`. import type { ParticipantSummary } from "@/lib/types";

```ts
export type ParticipantAuth =
  | { role: "creator"; token: string }
```

### 2.6 Non-functional notes

- Mobile-first: `ManageParticipants.tsx`'s list follows `design.md`'s `divide-y
  border-[var(--border)]` list convention (the same rhythm used for the transaction and category
  lists) rather than a card per row; every destructive action renders through `.btn-danger`, per
  `design.md`'s "every clickable action renders through one of `.btn-primary`, `.btn-secondary`,
  `.btn-danger`, or `.btn-text`" rule.
- Offline: per BR-019-10/11, both the confirm-then-act request and (structurally, though untested —
  see §1.6) the initial list load can fail outright; there is no offline queueing or optimistic
  local state anywhere in this feature.
- Local-storage failure modes: the one local write this feature performs — a leaving participant's
  own `saveJoinedTrips` prune — follows the exact `SaveResult` try/catch convention already in
  `lib/storage.ts`. A failed prune is the same accepted eventual-consistency gap feature 018's own
  `SharedTripView.tsx` already tolerates for its analogous prune-on-deletion write (§2.6 there): the
  server-side removal already succeeded, so the leaving participant is genuinely gone from the
  trip; a stale local entry just means feature 018's switcher may still offer this trip once more
  until the next prune attempt, not that the leave itself failed.
- **Next.js check**: `app/trips/[token]/participants/page.tsx` nests a second dynamic-adjacent
  static segment (`participants`) under the existing `[token]` segment alongside the sibling
  `app/trips/[token]/page.tsx` — confirmed against
  `node_modules/next/dist/docs/01-app/01-getting-started/03-layouts-and-pages.md`, which documents
  nested folders as ordinary nested routes with no restriction against a dynamic segment having
  both its own `page.tsx` and a static child folder with its own `page.tsx`. `params` remains a
  `Promise` or the new route, unwrapped via `use()`, consistent with every other dynamic page in
  this app (REFERENCE.md §5).

```gherkin
  Scenario: Leaving or removing fails when the server is unreachable
    Given I confirm leaving the trip or removing another participant
    When the app cannot reach the server
    Then I see a friendly error message
    And the participant list is unchanged

  # AC-019-11 [derived]
  Scenario: Opening the participants screen for a trip I don't belong to
    Given I am neither the creator nor a participant of a given shared trip
    When I open that trip's participants screen via its URL
    Then I am redirected home
    And I see no participant data
```

Notes on changes from the source Gherkin:

- The source's Scenario Outline "Only the creator can remove other participants" (two Examples
  rows: creator succeeds, participant is refused) is split into two independent scenarios,
  AC-019-02 and AC-019-03, since — per §2.1 — they exercise genuinely different code paths (a
  `.btn-danger` control that exists vs. one that is never rendered at all), and a Scenario Outline
  whose two rows assert opposite presence/absence of a control is harder to read than two named
  scenarios; the underlying business rule (BR-019-03/04) is unchanged either way.
- AC-019-06 is a new, more precise restatement of the source's "Removing or leaving preserves past
  expense history" scenario. The source's literal assertion ("their past expenses still show their
  name") cannot be verified today — no shared-trip expense entity exists until feature 020 (§1.4,
  §7 Open Item 1) — so this AC instead asserts the part of BR-019-07 that **is** observable now:
  removing one participant leaves every other participant's own record completely unaffected,
  which is the same "no unintended side effects on unrelated records" property the expense-facing
  half of the rule depends on. The expense-facing half is tracked as an open item, not silently
  dropped.
- AC-019-08 makes the source's "requires confirmation" scenario concrete and observable (an
  explicit "but do not confirm" / "no removal takes effect" pair) rather than only asserting that a
  confirmation step exists, since G3 requires every step to be independently checkable.
  AC-019-11 is a `[derived]` addition for the stray-URL edge case in §1.5 that the source Gherkin's
  seven scenarios don't themselves state but that this feature's own routing design (TS-019-05,
  TS-019-07) makes unavoidable to define, mirroring feature 018's identical treatment of the same
  underlying guard.

| # | Raised by | Challenge | Resolution | Outcome |
| --- | --- | --- | --- | --- |
| 1 | SA → BA | The source Gherkin gives leave/remove **two** separate scenarios for what looks like the same failure — "no internet connection" and "the app cannot reach the server" — with slightly different `Then` clauses ("a friendly message that this requires connectivity" vs. "a friendly error message"). | 2 | BA → SA | TS-019-08/09 add new links into `components/ShareTripLink.tsx` and `components/JoinedTripSummary.tsx`, both of which already have their own committed, passing Playwright specs (`e2e/016-...spec.ts`, `e2e/017-...spec.ts`) that assert specific rendered text and link accessible names. ## 7. Open questions & risks

1. **(Challenge #3) BR-019-07's expense-preservation half cannot be fully verified until feature 020
   exists.** This feature's design satisfies it *negatively* (removal never touches, cascades to,
   or references any expense data — there is none to touch) and commits feature 020 to preserving
   it *positively* (snapshotting a participant's name onto each shared-trip expense at attribution
   time, rather than a live foreign key to `Participant.id`, mirroring the deleted-custom-category
   precedent already in this codebase). Whoever scopes feature 020 should re-read this feature's
   §2.5 before designing its expense-participant relationship, to avoid a live FK that this
   feature's hard `delete()` would then orphan or silently break.
2. **(Challenge #2) Two already-shipped, already-tested components gain new links.** The change is
   additive-only and should not affect `e2e/016-generate-shareable-trip-link.spec.ts` or
   `e2e/017-join-a-shared-trip-via-link.spec.ts`'s existing assertions, but this is worth an explicit
   check (re-running both specs) once TS-019-08/09 land, rather than assuming it from this analysis
   alone.
3. **The creator's display label has no personal name to show.** Nothing in features 001–018
   captures any name for the trip creator (unlike a participant, who supplies one when joining), so
   BR-019-02's "the creator is visibly labeled as the creator" is designed here as a fixed, generic
   "Trip creator" row rather than a personal name. No scenario in the source Gherkin asks for the
   creator to have or enter a name, so this reads as the correct minimal interpretation — but it is
   the single biggest interpretive call in this document, on the same footing as feature 018's own
   biggest judgment call (its Open Item 1), and is worth the user's explicit confirmation before
   implementation.
