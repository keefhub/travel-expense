## 1. Business analysis — BA

### 1.1 Purpose

A traveller who has recorded expenses in the app wants a copy they can keep, back up, or open in a
spreadsheet outside the app — the app itself has no cloud sync (OVERVIEW: "no backend"), so export is
the only way expense data survives beyond the browser it was entered in.

### 1.2 Actors & preconditions

- **Actor:** the traveller, using the app on their own device.
- **Precondition:** an active trip exists (the feature's entry point, per §2.2, is a page already
  gated on a trip existing, same as feature 013's reset action). Whether any expenses have been
  recorded is exactly the condition this feature's two scenarios distinguish, not a precondition.

### 1.3 Business rules

| ID | Rule | Source |
|---|---|---|
| BR-014-01 | Selecting export when at least one expense is recorded generates a CSV file containing every recorded expense's date, category, currency, amount, payment method, location, and description. | `features/014.export-expenses.md:9-13` |
| BR-014-02 | Selecting export when no expenses are recorded shows a message that there are no expenses to export, and generates no file. | `features/014.export-expenses.md:15-18` |
| BR-014-03 | The CSV includes every recorded expense — export is not filtered by date range, category, or currency. | `features/014.export-expenses.md:13` ("the export should include... [the fields]" for "the expense data", with no filtering condition stated) |
| BR-014-04 | Each exported row's description is blank when the expense has none, never the literal text "undefined" or "null". | OVERVIEW §2 confirmed requirement: "Description is optional." — `[derived]`, the same rule already applied to the on-screen expense detail view (feature 009's `app/expenses/[id]/page.tsx`, `?? "No description entered."`), applied here to what a CSV column shows for an absent value |
| BR-014-05 | A field's value that itself contains a comma, a double quote, or a line break is escaped so it does not corrupt the CSV's column structure. | `[derived]` — `Location` and `Description` are free-text fields (OVERVIEW §3 Assumption 7), so this is the one realistic way an export could produce a broken file; standard CSV quoting (RFC 4180) is the well-established fix |

### 1.4 Data touched

- **Expenses** — read-only. Every field of every recorded `Expense` is read; nothing is written,
  modified, or deleted by this feature.

### 1.5 Edge cases & negative paths

- **A location or description containing a comma, quote, or newline** `[derived]` — BR-014-05. Must
  not shift later columns or otherwise corrupt the file when the CSV is opened in a spreadsheet
  application.
- **An expense with no description** `[in spec, implied]` — BR-014-04. The Gherkin's own wording
  ("description if available") already flags this as expected, not exceptional.
- **Exactly one expense, and a very large number of expenses** `[derived]` — the export must not
  behave differently at either end; there is no stated minimum or maximum.
- **An amount with more than two decimal places, or a whole-number amount** `[derived]` — for
  consistency with this app's existing `CODE amount` display convention (`toFixed(2)` everywhere
  else in this codebase), the exported amount is formatted the same way rather than however the
  stored floating-point number happens to serialize.

### 1.6 Out of scope

- **Import** — explicitly not supported per OVERVIEW §2 ("Import is not supported"); this feature is
  export-only.
- **Filtering, date-range selection, or choosing which fields to export** — not requested by either
  scenario; every field for every expense, always.
- **A file format other than CSV** — OVERVIEW §3 Assumption 11 states the export format is CSV;
  this feature does not offer PDF, JSON, or any other format.
- **A UTF-8 byte-order mark or other spreadsheet-application-specific compatibility shim** — not
  requested; adding one would be an unrequested assumption about which application opens the file
  (see §6 Challenge 3).
- **Changing where or how expenses are recorded, validated, or displayed** — this feature only reads
  what features 005/006 already write.

## 2. Technical specification — SA

### 2.1 Approach

One pure formatting function plus one small piece of UI wiring. `lib/export.ts` turns an
`Expense[]` into a complete CSV string (header row + one row per expense, RFC 4180 field escaping),
with no DOM, no storage, and no clock — the same "pure function, dependency-free" convention every
other `lib/<name>.ts` module in this codebase already follows. `app/settings/page.tsx` (already the
home for this app's other data-management actions — exchange rates, and feature 013's reset) gets a
new "Export expenses" button: reading `getExpenses()` on click, showing a `role="status"` message if
the list is empty, or building the CSV string and triggering a standard browser file download
(`Blob` + a temporary `<a download>` element) if it isn't. No new dependency, no new storage key, no
new route.

### 2.2 Design elements

- **TS-014-01** (satisfies BR-014-01, BR-014-03, BR-014-04, BR-014-05) — add `lib/export.ts`:
  ```ts
  export function formatExpensesAsCsv(expenses: Expense[]): string
  ```
  Builds a CSV string: a header row (`Date,Category,Currency,Amount,Payment Method,Location,Description`)
  followed by one row per expense, in `expenses`' given order (no re-sorting — export reflects
  whatever the caller passes in), with columns in the Gherkin's own stated order: `date`, `category`,
  `currency`, `amount` (formatted via `.toFixed(2)`, matching this app's existing currency-display
  convention), `paymentMethod`, `location`, `description` (`""` when `undefined`, never the literal
  string `"undefined"`). Each field is passed through a private `escapeCsvField(value: string):
  string` helper that wraps the value in double quotes and doubles any embedded double quotes
  whenever it contains a comma, a double quote, or a `\n`/`\r` — otherwise returns it unquoted. Rows
  are joined with `\r\n` per RFC 4180.

- **TS-014-02** (satisfies BR-014-01, BR-014-02) — modify `app/settings/page.tsx`: add an "Export
  expenses" button (alongside the existing "Reset app data" trigger) and a
  `const [exportMessage, setExportMessage] = useState<string | null>(null)` for the empty-state
  message. On click: read `getExpenses()`. If empty, `setExportMessage("You have no expenses to
  export.")` (BR-014-02) and do nothing else. Otherwise, clear `exportMessage`, call
  `formatExpensesAsCsv(expenses)`, wrap the result in a `Blob` (`type:
  "text/csv;charset=utf-8;"`), create an object URL via `URL.createObjectURL`, create a temporary
  `<a>` element with `href` set to that URL and `download="expenses.csv"`, append it to `document.body`,
  call `.click()`, remove it, and revoke the object URL — the standard client-side
  "generate a file and trigger its download" pattern for a page with no `<form>` or server endpoint
  to post to (there is none in this app; per OVERVIEW, there is no backend). The `exportMessage`
  paragraph, when set, renders with `role="status"` (a non-blocking informational note, not an
  error — matching this app's established `role="status"`/`role="alert"` split).

### 2.3 Data model

No new persisted shape and no change to `Expense`. `formatExpensesAsCsv` returns a plain `string`.

### 2.6 Non-functional notes

- **Mobile-first / offline:** triggering a browser download from a click handler and reading
  already-loaded `localStorage` data both work identically offline — no network request is made.
  Mobile browsers vary in exactly how a triggered `<a download>` click surfaces (a downloads-folder
  save vs. a share sheet on some mobile Safari versions), but the underlying API call is the same
  standard mechanism regardless of platform; there is no simpler cross-platform primitive available
  to a browser-only app with no backend.
- **Local-storage failure mode:** none applies here — this feature is read-only against storage
  (`getExpenses()` already has its own safe fallback to `[]` on a missing/corrupt key, established
  by feature 012), so there is no `SaveResult`-style failure path to surface for this feature
  specifically.
- **Next.js check:** no new Next.js API is used. `Blob`, `URL.createObjectURL`, and a programmatic
  anchor click are standard browser APIs invoked from an existing `'use client'` page's click
  handler — the same category of client-only browser API this app already uses elsewhere
  (`window.localStorage`, `window.sessionStorage`, `crypto.randomUUID()`), not something requiring a
  vendored Next.js doc lookup.

## 6. Contrarian review — BA ↔ SA

| # | Raised by | Challenge | Resolution | Outcome |
|---|---|---|---|---|
| 1 | SA → BA | AC-014-05's Scenario Outline describes a raw value containing a literal `\n` inside a Gherkin table cell, which most Gherkin parsers don't render as an actual newline character — is this AC actually executable as written, or just illustrative? | Accepted, with a clarifying note added to §3: the Outline is illustrative of the *rule* (RFC 4180 quoting for comma/quote/newline), and an implementer/reviewer verifying UT-014-04 should construct the actual newline case directly in code (e.g. a template literal with `\n`) rather than trying to author a literal Gherkin table cell with an embedded line break. No change to the rule itself, since the underlying business requirement (BR-014-05) is unambiguous — only a note that this one Example row is representative, not copy-pasteable. |
| 2 | BA → SA | TS-014-02's design fires the CSV generation and the browser-download side effect from inside the same synchronous click handler that also does the empty-check — is there a risk this blocks the UI thread or drops the user gesture (some browsers block `URL.createObjectURL`/anchor-click downloads that aren't triggered synchronously from a user gesture)? | Rejected, with reason: `formatExpensesAsCsv` is a synchronous, pure string-building function with no I/O — for any realistic number of expenses a traveller could manually record over a single trip (dozens, not millions), string concatenation completes in well under a frame; and because everything (the `getExpenses()` read, the CSV build, the Blob creation, and the anchor click) happens synchronously inside the `onClick` handler with no `await`/`setTimeout` in between, the user-gesture requirement browsers impose on file downloads is satisfied by construction, not by luck. |
| 3 | BA → SA | Should the export add a UTF-8 byte-order mark for better compatibility with spreadsheet applications (a common real-world CSV-export gotcha for non-ASCII text)? | Rejected, with reason: neither Gherkin scenario nor any OVERVIEW bullet mentions spreadsheet-application compatibility, encoding, or non-ASCII handling — this is exactly the kind of unrequested addition Phase 6 exists to catch (§1.6 already lists it as explicitly out of scope). If a real compatibility problem surfaces later, it is a one-line, backward-compatible addition to `formatExpensesAsCsv`, not something worth speculatively building now. |
| 4 | SA → BA | BR-014-03 ("export includes every recorded expense, not filtered") is stated as a rule, but nothing in the Gherkin says so explicitly — is this rule actually sourced, or is the BA inferring a requirement that was never stated? | Accepted, with a wording clarification: the rule's Source column was tightened to quote the specific phrase ("the expense data", singular and unqualified) rather than implying a stronger textual mandate than the Gherkin actually contains. The rule itself stays, because the alternative (silently filtering some expenses without a single scenario asking for it) would be scope-narrowing, not scope-neutral — a design that omits data by default needs its own explicit requirement, which does not exist. |
