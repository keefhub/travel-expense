## 1. Business analysis — BA

### 1.1 Purpose

Feature 021 shows a shared trip's simplified balances but is explicitly read-only (BR-021-11):
nothing on that screen can change what's owed. This feature closes that gap — it lets a
participant mark a balance (in full or in part) as paid outside the app, so the balances view
stops showing debts that have already been squared up in cash, another app, or any other
out-of-band means. This is the last of the seven v2 shared-trip slices (`REFERENCE.md` §7).

### 1.2 Actors & preconditions

- **Actor**: any current member of a shared trip — the trip creator, or a participant who joined
  via the trip's share link (feature 017). Identity is device-bound, exactly as in features
  016–021; no login exists.
- **Preconditions**: an active shared trip exists with at least one non-zero balance line
  currently shown on its balances view (feature 021); the viewing device is either the creator or
  a joined participant of that specific trip; connectivity is available, since settlements are
  written server-side.
- **Non-actor**: a device that is neither the trip's creator nor one of its joined participants
  cannot reach the balances view at all (feature 021's existing guard), and therefore has no way
  to trigger a settle action either — this feature adds no new entry point of its own.

### 1.3 Business rules

| ID | Rule | Source |
| --- | --- | --- |
| BR-022-01 | Settling records that a debt was paid outside the app; it adjusts the tracked balance shown on the balances view and never moves real money. | Assumption 1 |
| BR-022-02 | Either party to a debt — the person who owes or the person who is owed — can mark it settled unilaterally; no confirmation from the other party is required. | Scenario Outline "Either party in a debt can mark it settled"; Assumption 2 |
| BR-022-03 | A user can settle any amount from just above zero up to (and including) the full outstanding balance — partial settlement is supported, not only the whole amount at once. | Scenario "I settle part of a debt"; Assumption 3 |
| BR-022-04 | A zero, negative, or non-numeric settle amount is refused with an error, and nothing is settled. | Scenario Outline "A zero, negative, or non-numeric settle amount is refused" |
| BR-022-05 | Attempting to settle more than the current outstanding balance between the two parties is refused with an error, and nothing is settled. | Scenario "Settling more than the outstanding balance is refused" |
| BR-022-06 | A settlement combines with the underlying expense-based ledger, so that a later expense recorded between the same two participants nets correctly against it, rather than the settlement being overwritten or ignored. | Scenario "A new expense after a partial settlement nets correctly"; Assumption 4 |

| BR-022-08 | Once a balance between two parties reaches exactly zero (by settlement or otherwise), it is omitted from the balances view — reusing feature 021's existing "zero balance not shown" behavior (BR-021-05), not new display logic. | Assumption 6 |
| BR-022-09 | Triggering the settle action requires an explicit confirmation step before it takes effect — the amount is not settled on the first tap. | Scenario "Settling requires confirmation" |
| BR-022-10 | When the server cannot be reached while confirming a settlement, a friendly error message is shown and the balance is left unchanged. | Scenario "Settling fails when the server is unreachable" |

| BR-022-13 [derived] | A device that is neither the trip's creator nor one of its joined participants cannot settle a balance on that trip — no new entry point exists outside the already-gated balances view (feature 021's BR-021-12). | derived from Actors & preconditions; inherits feature 021's stray-device guard |

### 1.4 Data touched

- **Trip** (read) — trip currency, for display and for resolving auth headers.
- **Participant** (read) — id and name, including participants who have since left or been
  removed (feature 019's `onDelete: SetNull`/hard-delete behavior; their name and id survive on
  past expenses via the snapshot columns, exactly as feature 021 already relies on).
- **Expense** / **ExpenseShare** (read, feature 020) — unchanged from feature 021; still the base
  ledger a settlement nets against.
- **ExchangeRate for a shared trip** (read, feature 021) — unchanged; still used to convert
  non-trip-currency expenses before netting.
- **Settlement** (read, and — new in this feature — write) — does not exist in the data model
  yet. See §2.1 for why this feature adds it.

### 1.5 Edge cases & negative paths

- Settling the full outstanding amount clears that pair's line entirely. **[in spec]**
- Settling part of a debt leaves the remainder as the new outstanding balance. **[in spec]**
- A zero, negative, or non-numeric amount is refused. **[in spec]**
- An amount greater than the outstanding balance is refused. **[in spec]**
- A settlement made after a prior partial settlement, then a new expense between the same two
  people, nets all three together correctly. **[in spec]**
- A departed/removed participant's balance can still be settled, under their retained name. **[in
  spec]**
- Settling always requires an explicit confirm step, regardless of full or partial amount. **[in
  spec]**
- Server unreachable while confirming → friendly error, balance unchanged. **[in spec]**
- Device offline while attempting to settle → friendly connectivity message. **[in spec]** — as
  with feature 021 (its §2.1/Challenge #3), in this app's actual architecture this is the *same*
  failure signature (a rejected `fetch`) as the server-unreachable case above; both are honored by
  the same collapsed error path. See §6 Challenge 3.
- **[derived]** Settling exactly the full outstanding amount (the upper boundary of BR-022-03) is
  allowed, not just amounts strictly below it — the feature file's own first scenario ("I settle a
  debt in full") is this exact boundary case, so it needs no separate rule.
- **[derived]** A balance pair with no line currently shown (already fully settled, or a stale
  client view) has nothing to settle — an attempt against it behaves identically to "more than the
  outstanding balance" (BR-022-05), since its outstanding amount is 0.
- **[derived]** Because feature 021's balances view renders no settle-able lines at all when the
  result is `isComplete: false` (a missing exchange rate) or when there are no lines, this feature
  introduces no new control reachable in either of those states — no separate rule or test is
  needed beyond what feature 021 already covers for those states.
- **[derived]** A stray device cannot reach any settle control, because it never reaches the
  balances view that hosts it (feature 021's BR-021-12/stray-device guard, inherited unchanged).

### 1.6 Out of scope

- A settlement history or log of who settled what and when (feature file's own Out of Scope).
- Any real payment processing, money transfer, or payment-provider integration.
- Concurrent settlement of the same balance from both sides at nearly the same time — treated the
  same as feature 020's general concurrent-edit exclusion for v2.
- Undoing or reversing a settlement once confirmed.
- Notifying the other participant that a settlement occurred, outside of the balances view itself
  updating.
- Restricting *who* may settle a given line to only its two named parties — see §6 Challenge 1;
  this feature treats "any current trip member" as authorized, consistent with every other
  shared-trip write endpoint's authorization model (016–021 never check "is this specific
  person," only "is this a member of the trip").

## 2. Technical specification — SA

### 2.1 Approach

A settlement must combine with the expense ledger every time balances are computed (BR-022-06),
not overwrite a cached number — feature 021's `getTripBalances` is already a stateless pure
function recomputed fresh on every request, so the natural design is to feed it one more signed
input alongside expenses, rather than build a second computation path. This feature therefore adds
a small `Settlement` Prisma model (id, tripId, `fromId`/`toId` — nullable strings using the same
"null = trip creator" convention `Expense.payerParticipantIdSnapshot` and `BalanceExpenseInput`
already use, amount, createdAt) and extends `lib/balances.ts`'s `getTripBalances` to net each
settlement after its expense-derived net positions are computed: the party who owed (`fromId`) is
credited the settled amount (their net position moves toward zero/positive) and the party who was
owed (`toId`) is debited by the same amount, in the same integer-cents arithmetic the function
already uses for expenses — no currency field is needed on `Settlement` because a settle action
always operates on an amount already expressed in the trip currency (the figure shown on the
balances view), never on a raw expense currency.

**Verified**: `Settlement` has no FK relation to `Participant`, unlike `Expense`/`ExpenseShare`.
Those two models need a *live* FK (`onDelete: SetNull`) because their UI (`SharedExpenseDetail.tsx`)
must detect "the previous payer has left" and block re-saving until a new payer is chosen.
Settlement has no such UI — nothing here edits a settlement after it is created — so `fromId`/
`toId` are stored as plain optional strings, exactly like `BalanceLine.fromId`/`toId` already are
in `lib/types.ts`. This also means no name snapshot column is needed on `Settlement`: a settle
action can only be triggered against an `(fromId, toId)` pair that a fresh `getTripBalances` call
has *just* produced a line for (see below), which guarantees both ids already have a resolved name
from expense processing by the time a `Settlement` row referencing them could ever exist.

Validating "more than the outstanding balance" (BR-022-05) reuses the same computation rather than
tracking a separate running total per pair: the new `POST /api/trips/[id]/settlements` endpoint
recomputes `getTripBalances` with the trip's expenses, rates, and *existing* settlements, finds the
line (if any) matching the request's `(fromId, toId)` pair, and treats that line's `amount` — or 0
if no such line exists — as the outstanding balance to validate the request against. Because each
computed line's amount is already the minimum of its matched creditor's and debtor's remaining net
magnitude at the point the greedy simplification paired them (feature 021's TS-021-03), settling up
to that amount can never make either party's net position overshoot zero in the wrong direction.
On success, the endpoint creates the `Settlement` row and recomputes `getTripBalances` once more
(now including the new settlement) so it can return the fresh result directly — the client replaces
its balances state with the response rather than issuing a second fetch.

Confirmation (BR-022-09) and partial-amount entry are the same UI gesture: tapping "Settle" on a
balances-view line opens a new modal, `components/ConfirmSettleBalance.tsx`, pre-filled with the
line's full outstanding amount and editable down to any smaller positive value; its own "Confirm"
button is the confirmation step the Gherkin scenario asks for, mirroring
`components/ConfirmParticipantAction.tsx`'s established `role="dialog"` pattern (019) rather than
inventing a new one. Invalid input (BR-022-04/05) is validated client-side first, via a new pure
`validateSettlementAmount` in `lib/balances.ts`, so the zero/negative/non-numeric and
exceeds-outstanding scenarios never need a network round trip in the golden path; the server
performs the same checks independently as the authoritative source (never trusting the client), but
— consistent with every other shared-trip fetch wrapper in this codebase (`lib/participants.ts`,
`lib/sharedExpenses.ts`, `lib/balances.ts`'s existing `fetchTripBalances`) — a server-side 400
collapses into the same generic friendly-error string as a network failure, never a distinct
message. See §6 Challenge 4.

### 2.3 Data model

```ts
// lib/balances.ts additions

export interface BalanceSettlementInput {
  fromId: string | null; // null = trip creator, same convention as BalanceExpenseInput.payerId
  toId: string | null;
  amount: number; // trip-currency; a settlement is never expressed in another currency
}

// getTripBalances gains a fourth parameter:
export function getTripBalances(
  expenses: BalanceExpenseInput[],
  tripCurrency: string,
  rates: Pick<SharedExchangeRate, "currency" | "rate">[],
  settlements: BalanceSettlementInput[]
): TripBalancesResult;

export type SettlementAmountValidation =
  | { valid: true; amount: number }
  | { valid: false; error: string };

export function validateSettlementAmount(
  amountInput: string,
  outstandingAmount: number
): SettlementAmountValidation;

export interface SettleBalanceInput {
  fromId: string | null;
  toId: string | null;
  amount: number;
}

export type SettleBalanceResult =
  | { ok: true; balances: TripBalancesResult; tripCurrency: string }
  | { ok: false; error: string };

export function settleBalance(
  tripId: string,
  input: SettleBalanceInput,
  auth: ParticipantAuth
): Promise<SettleBalanceResult>;
```

## 4. Playwright scenario mapping — SA

settle UI itself, unlike 021's balance-display scenarios which needed arbitrary payer/split

## 7. Open questions & risks

1. **Settling is open to any trip member, not restricted to the two named parties in a debt**
   (Challenge #1). This is the more permissive, more consistent-with-the-rest-of-the-app reading
   of Assumption 2, but the assumption's own wording ("either party... can mark it settled") could
   also be read as an implicit restriction. Recommend the user confirm this reading explicitly
   before implementation, since tightening it later would mean adding the one kind of
   per-identity authorization check this app's shared-trip API does not otherwise have anywhere.
2. **Server-side validation errors are never surfaced with their own specific text to the user**
   (Challenge #4) — a deliberate, codebase-wide consistency choice inherited from every prior
   shared-trip fetch wrapper, not a gap introduced by this feature. Noting it here in case the user
   wants a future pass to give `lib/participants.ts`/`lib/sharedExpenses.ts`/`lib/balances.ts`'s
   wrappers more specific error surfacing across the board.
3. **No settlement audit trail exists anywhere** (explicitly Out of Scope, per the feature file
   itself) — if a later feature needs "who settled what and when" (e.g. for a dispute), the
   `Settlement` model as designed here (§2.3) has no name snapshot and its `createdAt` is the only
   timestamp; a future feature adding history would likely want to add name snapshots at that
   point, mirroring `Expense`/`ExpenseShare`'s existing precedent (§2.1 "Verified" explains why
   this feature itself does not need them).
