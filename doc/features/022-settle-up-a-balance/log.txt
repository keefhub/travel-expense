Task 4: [Route] - POST /api/trips/[id]/settlements
Completed: 2026-09-19
Commit: 9f828d0

Summary:
  New Route Handler that records one settlement and hands back the recomputed balances. It parses
  the body in its own try/catch, 404s an unknown trip, reuses the balances GET's auth check, runs the
  four field checks in a fixed order before reading any ledger data, recomputes the current balances
  to find the pair's outstanding line, refuses an amount above it, rounds to the nearest cent, writes
  the row and responds 200 { balances, tripCurrency } with the new settlement already netted in.

Key Decisions:
  Attempt 1 failed its quality gate: a sub-cent amount (e.g. 0.001) passed the unrounded positivity
  check, rounded to 0 cents, made the cap comparison 0 > 0 false even for a pair with no line at all,
  and so wrote a zero-value Settlement row while returning 200. The fix gates the requested amount in
  integer cents before anything is written - a value rounding to zero cents now returns 400 "Enter a
  valid amount greater than zero." - and makes the outstanding figure explicit
  (matchingLine === undefined ? 0 : ...) instead of an ?? 0 fallback. Both gates then passed on
  attempt 2.

  Client-side awareness of the same hole: lib/balances.ts's validateSettlementAmount still accepts a
  positive amount whose cents round to zero, so the modal in Task 5 will let 0.001 through and the
  route will answer 400, which settleBalance collapses into the generic friendly error. No integrity
  impact (the route is now the gate), and that helper is committed outside this task's diff, so
  tightening it belongs to whichever task next owns lib/balances.ts.

  No db.$transaction around the read/validate/write: two racing requests can both read the same
  pre-settlement line and both pass. That is spec section 1.6's explicit Out of Scope, mirroring
  feature 020's identical concurrent-edit exclusion, and REFERENCE.md records it as deliberate.

Deviations:
  Two additions beyond the plan's literal step 7, both required by the attempt-1 finding: the
  amountCents <= 0 branch and the explicit undefined check for matchingLine. The four field checks,
  their order and their messages are unchanged.

  REFERENCE.md gained the route's entry in section 4 (the task's Files manifest named only the new
  route file) and that entry was then reworded after the fix, inside this same task's diff.

Files Changed:
  - app/api/trips/[id]/settlements/route.ts (created)
  - REFERENCE.md (modified)

Verification:

  between, pre-fills an "Amount to settle" input with the line's full outstanding figure, validates
  it through the pure validateSettlementAmount on Settle, shows a role="alert" error and calls
  nothing else when it fails, and calls onConfirm(amount) only on success. No fetch, no storage.

Key Decisions:
  The combined gate passed but flagged two issues, both originating in the plan's own quoted markup
  rather than in the implementation, so neither was fixed here (the plan's markup was mandated
  verbatim, and editing it would have invalidated the gate that had just passed):

  1. The component holds useState but carries no 'use client' directive, because the plan's premise
     ("mirrors ConfirmParticipantAction.tsx") is wrong - that file is genuinely stateless, while this
     one is not. It is runtime-safe as shipped, because the only render site (components/TripBalances.tsx,
     Task 6) is itself a client component, so the directive is not required for it to work. It should
     still gain "use client" for consistency with every other stateful component in components/ and
     with the UI slice's own rule.
  2. The dialog card uses "rounded p-6" where design.md locks radius to rounded-lg and where the
     sibling modal uses "flex w-full max-w-sm flex-col gap-4 rounded-lg bg-(--background) p-4". The
     spec's own 2.6 asked for the existing modal pattern to be followed, so the plan's literal markup
     is the drift. Cosmetic only.

  Passing the amount through validateSettlementAmount rather than re-implementing the rules keeps the
  client and the route agreeing on the two error strings. Note that the helper still accepts a
  positive sub-cent amount whose cents round to zero (recorded under Task 4); the route is the real
  gate, so the worst case is a 400 surfacing as the generic friendly error.

Task 7: [Behavioral] - Playwright coverage for the full feature
Completed: 2026-09-19

Summary:
  New e2e/022-settle-up-a-balance.spec.ts, ten tests covering AC-022-01 to AC-022-10: a full settle
  clearing the line, either party triggering it, a partial settle leaving the remainder, the three
  refused amounts replacing the plan's three-value case, an over-balance amount refused, a later
  expense netting against a partial settlement, a removed participant's line, cancelling without
  confirming, and an aborted settle request. Helpers are duplicated from the 021 spec, unchanged.

Key Decisions:
  The gate passed the artifact but not cleanly: its first cold whole-file run went red at E2E-022-04
  (the row still read 20.00 after the dialog closed) and it could not attribute the cause, because
  no test asserts the ABSENCE of the action error after a successful settle - a failed POST surfaces
  as a mysterious balance mismatch instead of "the settle request failed". Seven further runs
  (three whole-file, four isolated) were green, and the controller's own cold whole-file run before
  this commit was green too (10 passed). The gate's suggested hardening, which is not in this spec
  yet and is the first thing to try if the flake returns: after awaitSettleComplete on the success
  paths, assert balancesScreen(page).getByRole("alert") has count 0, or gate on waitForResponse for
  the POST and assert status 200 before asserting a balance.

  The gate also hypothesised a latent app race worth knowing about: components/TripBalances.tsx's
  mount-time load() sets balances unconditionally, and StrictMode's double invoke puts two GETs in
  flight at mount, so a mount GET resolving after a settle response could overwrite it with
  pre-settlement data. Not reproduced, and out of this task's scope, but it would be an app defect
  rather than a spec fix, so it belongs to a follow-up if it recurs.

  Serial mode is inherited from the 021 spec on purpose (one dev server compiling each dynamic route
  on first request). Its known cost, hit in practice here: a single failure skips every later test,
  so this file must always be verified whole, never with -g.

  Beyond the plan's bullets the spec also reloads the page in the two persistence cases and spies on
  the settlements endpoint with page.route in the cancel case. Both are required by spec 4 and
  materially strengthen the coverage, and awaitSettleComplete (the one helper added beyond the four
  the plan named) removes a real race against the dev server's cold-compile latency rather than
  hiding a failure.

Deviations:
  Three small ones, all reported: the extra awaitSettleComplete helper, the three spec-4 assertions
  above, and the test titles carrying an "E2E-022-NN - " prefix where the older specs use plain
  titles (the spec's own 4 table lists the plain names, so the prefix is a traceability addition).
  setExchangeRateViaApi was not duplicated, since no 022 scenario needs an exchange rate.
  REFERENCE.md was deliberately left untouched: a new spec file is not listed by name in section 4,
  and no dependency, storage key or module API changed.
