## 1. Business analysis — BA

### 1.1 Purpose

This is the feature every prior feature's `app/page.tsx` placeholder has been waiting for — the
comment `// Placeholder — replaced by feature 009 (home dashboard).` has sat in that file since
feature 001. The traveller lands here after setup and needs one screen that answers "where am I,
what have I spent, and what does that look like" without navigating anywhere else: trip summary,
total spend, budget standing, a category breakdown, and quick access to recent transactions.

### 1.2 Actors & preconditions

- **Actor:** the traveller.
- **Precondition:** an active trip exists (the `trip === null` branch — first-time setup — is
  unchanged by this feature; it already exists from feature 001).

### 1.3 Business rules

| ID | Rule | Source |
|---|---|---|
| BR-009-01 | With no expenses recorded, the dashboard shows the destination country, travel dates, number of travel days, and trip currency. | Scenario "User views dashboard with no expenses" |
| BR-009-02 | With no expenses recorded, the dashboard shows a zero spending summary (not a hidden/omitted section). | Same scenario |
| BR-009-03 | With no expenses recorded, the dashboard shows an empty state for recent transactions (a plain sentence, not a blank area). | Same scenario |
| BR-009-04 | With expenses recorded, the dashboard shows total spending, displayed using currency codes. | Scenario "User views total spending" |
| BR-009-05 | With expenses recorded across categories, the dashboard shows a pie chart of spending by category. | Scenario "User views spending by category" |
| BR-009-06a | With more than five expenses recorded, the dashboard shows only the latest five. | Scenario "User views last five transactions" |
| BR-009-06b | Those transactions are sorted newest-to-oldest by expense date. | Same scenario |
| BR-009-07a | With fewer than five expenses recorded, the dashboard shows all of them. | Scenario "User views fewer than five transactions" |
| BR-009-07b | Those transactions are also sorted newest-to-oldest by expense date. | Same scenario |
| BR-009-08 | Tapping or clicking a listed transaction shows that transaction's details. | Scenario "User views recent transaction details" |
| BR-009-09 | The transaction detail view includes date, category, currency, amount, payment method, location, and description if one was entered. | Same scenario |
| BR-009-10 | Budget and remaining budget are shown when a budget is set, per feature 008 (already implemented — unchanged by this feature, just relocated into the real dashboard layout). | REFERENCE.md §6 domain fact: "Dashboard: trip summary, total spend, budget/remaining (if set)..." |

### 1.4 Data touched

- **Reads:** `Trip` (unchanged from the current placeholder), the full `Expense` list, `ExchangeRate`
  list, and the combined category list (feature 010's `getAllCategories`, only indirectly — expenses
  already store the category name as a plain string, so no live category lookup is needed to group
  by category).
- **Writes:** none. This feature is entirely read/display logic over data every prior feature already
  writes.

### 1.5 Edge cases & negative paths

- An expense's currency has no saved exchange rate — the existing "conversion incomplete" caveat
  (feature 006) already covers this for the total-spend figure; the category pie chart has the same
  exposure (an expense in an unrated currency can't be converted to a comparable amount) and needs
  the same treatment. `[derived]`
- Exactly five expenses recorded — this is the boundary between "latest five" and "all of them"; both
  scenarios' outcomes are identical at this exact count (show all five, newest-first), so it isn't a
  meaningfully distinct rule, but is worth an explicit boundary-case AC. `[derived]`
- Tapping a transaction, then using the browser back button or a direct link to an expense id that no
  longer exists (e.g. bookmarked, then the trip was reset or replaced) — the Gherkin never describes
  this; the detail view needs *some* defined behavior rather than crashing. `[derived]`
- A transaction with no description entered — BR-009-09 says "description if available," meaning the
  detail view must not show `"undefined"` or crash when `Expense.description` is absent. `[derived]`
- Multiple expenses recorded on the exact same date — "sorted newest-to-oldest by expense date" only
  orders by date, not by entry order; ties need a defined, stable behavior even though the Gherkin
  doesn't specify one. `[derived]`

### 1.6 Out of scope

- Editing or deleting an expense from the detail view — OVERVIEW §3 Assumption 5 confirms the detail
  page is "view-only unless edit or delete is added later," and no later feature in this spec set
  adds that.
- Any change to how expenses, the trip, exchange rates, or the budget are entered — this feature only
  reads and displays what features 001–008 already write.
- Filtering, searching, sorting controls, or date-range selection on the dashboard — not requested by
  any scenario.
- A full transaction history / "view all expenses" list beyond the last five — not requested; the
  Gherkin's ceiling is explicitly five.

## 2. Technical specification — SA

### 2.1 Approach

The dashboard's data-fetching and rendering logic moves out of `app/page.tsx` into a new
`components/Dashboard.tsx`, matching the layer split every other route in this app already uses
(`TripEditForm`, `TripSetupForm`, `ExpenseForm`, `ExchangeRateForm` are all components a thin route
mounts) — `app/page.tsx` has been the one exception, inlining feature 006's and 008's additions
directly, specifically because each was framed as "minimal surface... will be folded into feature
009's full dashboard layout." This is that folding. Two small pure additions land in existing domain
modules: `getCategoryTotals` (mirroring `getConvertedTotals`'s shape) in `lib/currency.ts`, and
`getRecentExpenses` in `lib/expenses.ts`. The pie chart is hand-rolled with a CSS `conic-gradient`
(REFERENCE.md §2: no chart library is installed, and none should be added silently) rather than SVG
arc math, paired with a text legend so the data is available to screen readers, not just sighted
users. The tap-through detail view is a new dynamic route, `app/expenses/[id]/page.tsx` — the first
dynamic segment in this app, verified against the vendored Next.js 16 docs below.

### 2.2 Design elements

| ID | Element | Satisfies |
|---|---|---|
| TS-009-01 | `lib/currency.ts` — new `CategoryTotal { category: string; amount: number }` and `CategoryTotalsResult { categoryTotals: CategoryTotal[]; isComplete: boolean; missingCurrencies: string[] }`, plus `getCategoryTotals(expenses, tripCurrency, rates): CategoryTotalsResult`. For each expense: if its currency is the trip currency, its amount counts at face value; otherwise, if a rate exists, it's converted and counted; otherwise its currency is added to `missingCurrencies` and the expense is excluded from every category total (mirroring exactly how `getConvertedTotals` already excludes unrated currencies from its single total). | TS-009-02 | `lib/expenses.ts` — new `RECENT_EXPENSE_LIMIT = 5` and `getRecentExpenses(expenses, limit = RECENT_EXPENSE_LIMIT): Expense[]`, returning `[...expenses].sort((a, b) => b.date.localeCompare(a.date)).slice(0, limit)`. `Array.prototype.sort` is stable (ES2019+), so same-date expenses keep the order they were recorded in — a defined, deterministic tie-break for the §1.5 edge case. | BR-009-06a, 06b, 07a, 07b, and the same-date edge case in §1.5 |

| TS-009-04 | `components/Dashboard.tsx` — new, `{ trip: Trip; showSavedMessage: boolean }` props. | TS-009-05 | `app/page.tsx` — reduced to a thin shell: the two existing `useSyncExternalStore` stores (trip, saved-message) stay here since they're routing/hydration concerns, but the branch that previously inlined the whole dashboard body now renders `<Dashboard trip={trip} showSavedMessage={showSavedMessage} />`. The `trip === null` (first-time setup) branch is untouched. | Groundwork for TS-009-04; no new BR of its own |
| TS-009-06 | `app/expenses/[id]/page.tsx` — new dynamic route, this app's first. `'use client'` (localStorage access, per REFERENCE.md §5); reads the route param via `PageProps<'/expenses/[id]'>` and React's `use()` (confirmed pattern for Client Component pages — see Next.js check below); loads the expense list via the same hydration-safe `useSyncExternalStore`-over-a-per-mount-store pattern every other route in this app already uses; finds the expense whose `id` matches the param. ### 2.6 Non-functional notes

- **Hydration safety:** the new `app/expenses/[id]/page.tsx` follows REFERENCE.md §5 exactly —
  `localStorage` is never read during render; the `useSyncExternalStore` pattern already proven in
  `/trip/edit`, `/trip/new`, and `/expenses/new` is reused verbatim.
- **No new dependency:** the pie chart is CSS `conic-gradient` plus a text legend — zero runtime
  dependencies, per REFERENCE.md §2's explicit instruction not to silently add a chart library.
- **Accessibility:** the chart's `role="img"` + `aria-label` carries the same information the visual
  conveys, since a `background: conic-gradient(...)` has no accessible-tree representation on its
  own; the text legend is not decorative — for keyboard/screen-reader users it *is* the chart.
- **Currency display:** every new amount follows the existing `CODE amount` convention (`.toFixed(2)`
  after a currency code), unchanged from every prior feature.
- **Next.js check:** confirmed via
  `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/dynamic-routes.md`: (1)
  `params` is a `Promise` in App Router page components; (2) in a Client Component page, it's
  unwrapped with React's `use()` — the doc's own example is exactly this shape (`'use client'`,
  `import { use } from 'react'`, `const { slug } = use(params)`), with no `Suspense` boundary shown
  around it, since that document's `Suspense`-boundary guidance applies specifically to routes using
  "Cache Components" mode with server data fetching; this repo has no such config (`next.config.ts`
  is the default empty `NextConfig` object, verified directly) and every route in it is already a
  fully client-rendered `'use client'` island reading `localStorage`, not server-fetched data — so no
  `Suspense` wrapper is needed here, matching the doc's simplest documented case exactly. (3) Types
  come from the globally-generated `PageProps<'/expenses/[id]'>` helper, per REFERENCE.md §5's
  existing rule to never hand-write route prop interfaces.

## 3. BDD acceptance criteria — BA

```gherkin
# AC-009-01
Scenario: Dashboard with no expenses shows trip details and zero/empty states
  Given the user has an active trip with no expenses recorded
  When the user views the dashboard
  Then the destination country, travel dates, and number of travel days are shown
  And the trip currency is shown
  And total spending is shown as zero, using the trip's currency code
  And the recent-transactions area shows a plain empty-state sentence, not a blank area

Scenario: Total spending is shown with currency codes once expenses exist
  Given the user has recorded expenses totaling a nonzero amount
  When the user views the dashboard
  Then the total spending figure is shown
  And it is displayed as a currency code followed by the amount

# AC-009-03
Scenario: A pie chart of spending by category is shown
  Given the user has recorded expenses across at least two categories
  When the user views the dashboard
  Then a pie chart is shown with one slice per category
  And a legend names each category and its share of spending

# AC-009-04
Scenario: More than five expenses shows only the latest five, newest first
  Given the user has recorded six or more expenses on different dates
  When the user views the dashboard
  Then exactly five transactions are listed
  And they are the five with the most recent expense dates
  And they are ordered from newest expense date to oldest

# AC-009-05
Scenario: Exactly five expenses shows all five, newest first
  Given the user has recorded exactly five expenses on different dates
  When the user views the dashboard
  Then all five transactions are listed
  And they are ordered from newest expense date to oldest

# AC-009-06
Scenario: Fewer than five expenses shows all of them, newest first
  Given the user has recorded two expenses on different dates
  When the user views the dashboard
  Then both transactions are listed
  And they are ordered from newest expense date to oldest

# AC-009-07
Scenario: Tapping a recent transaction shows its full details
  Given the user is viewing the recent-transactions list
  When the user taps or clicks one of the listed transactions
  Then a detail view is shown for that transaction
  And it includes the date, category, currency, amount, payment method, and location
  And it includes the description if one was entered

# AC-009-08
Scenario: A transaction with no description shows no placeholder crash
  Given the user taps a transaction that has no description
  When the detail view is shown
  Then the view renders without error
  And no literal "undefined" text is shown for the description

# AC-009-09
Scenario: Budget and remaining budget still appear on the real dashboard
  Given the user has an active trip with a budget set and every used currency rated
  When the user views the dashboard
  Then the budget amount is shown
  And the remaining budget is shown

# AC-009-10
Scenario: A transaction detail link for an expense that no longer exists shows a not-found state
  Given the user navigates directly to a transaction detail URL whose id matches no stored expense
  When the page loads
  Then a plain "not found" message is shown
  And a link back to the home screen is shown
  And the app does not crash
```

## 7. Open questions & risks

1. **(Challenge 5)** When an entire category's spending is excluded from the pie chart because its
   only currency lacks a saved rate, the existing shared "conversion incomplete" note is the only
   signal that something is missing — it doesn't say *which category* vanished. This spec proceeds
   with the existing, already-shipped note as sufficient (consistent with feature 006's precedent),
   but if user testing shows this is confusing, a category-specific version of the note would be a
   small, isolated follow-up change to `CategoryPieChart.tsx` alone.
2. **The uncommitted dark-mode theming refactor** sitting in the working tree (see §2.4) is unrelated
   to this feature and must not be touched, referenced, or built upon by this plan — flagged again
   here for the implementer's attention, since it touches some of the same UI territory (forms,
   layout) this feature's dashboard also lives in.
