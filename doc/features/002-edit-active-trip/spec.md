## 1. Business analysis — BA

### 1.1 Purpose

A traveller's plans change mid-trip: a flight gets rebooked, a side trip is added, or a budget
guess turns out wrong. This feature lets the user correct the destination country, travel dates,
or budget of the one active trip after it has already been set up (feature 001), without deleting
and re-creating the trip (that destructive path is feature 003). The outcome is that the single
`Trip` record in storage always reflects the traveller's current plan, and every value derived from
it (travel-day count, trip currency, budget-dependent dashboard math) stays consistent with the
edit.

### 1.2 Actors & preconditions

- **Actor:** the traveller, the app's only user role.
- **Precondition:** an active trip already exists in storage (feature 001/012 — `getTrip()` returns
  a non-null `Trip`). If no trip exists, there is nothing to edit; per feature 001's existing routing
  (`app/page.tsx`), the user would be on the setup form instead, not an edit screen.

### 1.4 Data touched

- **Reads:** the single `Trip` record (`destinationCountry`, `currency`, `startDate`, `endDate`,
  `budget?`) via `lib/storage.ts`'s `getTrip()`.
- **Writes:** the same `Trip` record, replaced in place via `saveTrip()` — there is only ever one
  trip key in storage (`STORAGE_KEYS.trip`), so "update" and "create" are the same storage
  operation; only the UI entry point and the pre-filled values differ from feature 001.
- Does **not** touch `Expense`, `Category`, or `ExchangeRate` storage.

### 1.5 Edge cases & negative paths

- No active trip exists when the edit route is opened directly (e.g. stale bookmark, direct URL
  entry) — there is nothing to edit. `[derived]`
- Saving with every field unchanged (no-op edit) must still succeed and leave the trip equivalent.
  `[derived]`
- Trip has no budget today; user adds one for the first time — the reverse of Scenario 3, and must
  work the same way BR-002-08 describes for any other field. `[derived]`
- Budget field contains only whitespace — must be treated as "no budget" (matching feature 001's
  `validateTripForm`, which trims before checking), not as an invalid, non-numeric value. `[derived,
  consistent with existing `lib/trip.ts` behavior]`
- Destination country changed to a different supported country: the previously derived currency is
  replaced by the new one (BR-002-10), even though existing `Expense` records recorded before the
  edit still carry the old trip's currency. Reconciling those is out of scope (§1.6). `[derived]`
- `saveTrip()` fails (storage full/unavailable, per feature 012's `SaveResult`) — the user must see a
  friendly error and the form must keep their unsaved edits so they don't have to retype them.
  `[derived from OVERVIEW §2 "Local storage errors should show a user-friendly error message" and
  012's `SaveResult` contract]`

### 1.6 Out of scope

- Deleting the trip or replacing it with a different one — that is feature 003 (Create New Trip),
  including its confirmation-to-delete flow.
- Reconciling already-recorded `Expense` amounts/currency when the trip's country/currency changes.
  The spec only asks that the *trip's* expected currency update (BR-002-10); nothing in the Gherkin
  or OVERVIEW asks for existing expenses to be rewritten, converted, or flagged.
- Any dashboard rendering behavior ("the dashboard should no longer show remaining budget
  calculations" in Scenario 3) — the dashboard itself is feature 009, not yet implemented. This spec
  is only responsible for the `Trip` record in storage correctly losing its `budget` field; the
  dashboard consuming that correctly is 009's responsibility when it's built.
- A confirmation dialog before saving an edit. Feature 003's "create new trip" flow has one because
  it's destructive to other data (expenses, etc.); nothing in this feature's Gherkin asks for a
  confirmation step on a plain field edit.
- Undo / revert-to-previous-values after a successful save.

## 2. Technical specification — SA

### 2.1 Approach

Feature 001 already built exactly the domain logic this feature needs: `TripFormValues`,
`validateTripForm`, and `submitTripSetup` in `lib/trip.ts` validate a form, derive the currency from
the selected country, and call `saveTrip()`. Because storage holds exactly one trip, "save" is
already an upsert — `submitTripSetup` requires no change to serve edits too. The only genuinely new
piece is turning a stored `Trip` back into `TripFormValues` to pre-fill the form (`getTripFormValues`),
plus a new route/component pair that mirrors `TripSetupForm`'s shape but starts from those pre-filled
values and displays the read-only derived fields (travel days, currency) that Scenario 1 asks for.
Reusing rather than duplicating validation/derivation logic keeps BR-002-10/11/13/14 correct by
construction, since they're the same rules feature 001 already implements and tested implicitly via
its own commit.

### 2.2 Design elements

| TS-002-02 | `app/trip/edit/page.tsx` — new client route. On mount, reads `getTrip()`. §1.4 and the out-of-scope list in §1.6.

### 2.3 Data model

No new or changed types. Reuses `Trip` from `lib/types.ts` and `TripFormValues` /
`TripValidationResult` / `SubmitTripResult` from `lib/trip.ts` exactly as feature 001 defined them.

```ts
// lib/trip.ts — addition only
export function getTripFormValues(trip: Trip): TripFormValues {
  return {
    destinationCountry: trip.destinationCountry,
    startDate: trip.startDate,
    endDate: trip.endDate,
    budget: trip.budget !== undefined ? String(trip.budget) : "",
  };
}
```

### 2.6 Non-functional notes

- **Hydration safety:** `getTrip()` reads `localStorage`, so `app/trip/edit/page.tsx` must not read
  it during the initial render. It follows `app/page.tsx`'s existing pattern (render `null` until a
  client-only read resolves, then render real content) rather than introducing a second pattern —
  per REFERENCE.md §5, "Never read `localStorage` during render/SSR; read it in `useEffect` (or a
  client-only hook)."
- **Mobile-first form:** `TripEditForm` follows `design.md` §6 (label above input, helper/error text
  below, `gap-2` per field block) and reuses the same input types `TripSetupForm` already uses
  (`<select>` for country, `type="date"` for dates, `inputMode="decimal"` text input for budget) so
  the two forms look and behave identically apart from pre-fill and the two read-only derived
  fields.
- **Derived-field display (travel days, currency):** rendered as plain `font-mono` text per
  `design.md` §3 ("numbers get mono"), not as disabled `<input>` elements, since the user cannot
  edit them directly — only the underlying dates/country.
- **Offline:** no network calls anywhere in this feature; unaffected by offline requirement.
- **Next.js check:** `app/trip/edit/page.tsx` is a plain static-segment route (no dynamic params, no
  `searchParams`), consistent with `app/expenses/new/page.tsx` and `app/categories/page.tsx`
  already in the tree — no new App Router convention introduced. Post-save/no-trip navigation uses
  `useRouter().push`/`.replace` from `next/navigation`, confirmed current for this Next.js version
  by reading `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/use-router.md`
  (`router.push(href)` / `router.replace(href)` signatures unchanged from training data; the doc's
  own example is a `'use client'` component calling `router.push` from an event handler, the same
  shape used here).

## 7. Open questions & risks

1. **(from Challenge 5)** Confirm that changing a trip's destination country/currency mid-trip is
   not expected to retroactively alter any already-recorded `Expense.currency` values. This
   spec proceeds on the assumption that it should not — each `Expense` is currency-independent
   (feature 006) and a trip-level currency change only affects the trip's own record and future
   dashboard math (feature 009), never past expenses. If this assumption is wrong, feature 006's
   spec (not yet written) is the place to define the reconciliation behavior, not this one.
2. **Entry-point placement (TS-002-04, BR-002-16)** is decided by this spec as a link inside the
   existing placeholder branch of `app/page.tsx`, since no dashboard exists yet (feature 009). When
   009 replaces that placeholder, it should carry the same "Edit trip" entry point forward into the
   real dashboard layout — flagging this so 009's implementer doesn't drop it.
