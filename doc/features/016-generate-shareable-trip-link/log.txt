Task 11: [Behavioral] — Playwright coverage for the full feature
Completed: 2026-09-17
Commit: 849e78e

Summary:
  Added e2e/016-generate-shareable-trip-link.spec.ts covering all 11 scenarios
  from spec.md §4 against a real Neon database (this stack has no mock/test-
  double layer). Ran the suite, found and fixed one real flake, then re-ran
  clean before committing.

Key Decisions:
  - E2E-016-04 renamed to "the previous link's token is genuinely replaced
    after regeneration": creatorToken never rotates by design (only
    shareToken does), so literally replaying the old creatorToken against
    regenerate can never fail even against a broken implementation — that
    would be a false-positive test. The honest, achievable check is the
    user-observable proxy: the old shareToken string is genuinely gone from
    what the UI shows, confirmed alongside a direct API check that
    creatorToken still authorizes a further call.
  - Scenarios exercising regenerate/teardown create a real Trip row via a
    direct API call first (createRealTripLink), then seed its real
    id/tokens into localStorage — a seeded-but-fake link would 404 the
    moment a test regenerates or edits it, since those routes look the row
    up for real.
  - role="alert"/role="status" assertions are scoped to ShareTripLink's own
    container (via the "Invite friends" heading's parent) to avoid
    colliding with Next.js's route announcer and the Settings page's other
    status regions (ExchangeRateForm, export/reset messages).
  - The "editing trip details" and "starting a new trip" scenarios navigate
    back to Settings via an in-app Link click, not page.goto — a full
    navigation re-fires page.addInitScript and would re-seed the original,
    pre-change localStorage values right back in, masking the very
    regression each test exists to catch.
  - The double-click scenario dispatches two raw MouseEvent click events via
    element.evaluate rather than two Playwright .click() calls: .click()
    waits for the element to be "enabled," but the component disables the
    button synchronously on the first click (before any await), so a second
    .click() would deadlock waiting for a state that never recurs before
    the button unmounts on success.

Deviations:
  - First run: "generates a link the first time you invite friends" failed
    — expect(paragraph).toBeVisible() timed out at the default 5s. This is
    the one scenario that creates a brand-new Neon row through the UI
    without a prior warm connection (every other scenario's
    createRealTripLink already has one by the time it runs), and a cold
    serverless connect exceeded 5s. Fixed by waiting for the real
    POST /api/trips response explicitly via page.waitForResponse, matching
    the pattern the regenerate scenario already used — not a code defect in
    components/ShareTripLink.tsx or lib/sharedTrip.ts, confirmed by reading
    both before making the change.

Files Changed:
  - e2e/016-generate-shareable-trip-link.spec.ts (created)
