## 1. Business analysis — BA

### 1.1 Purpose

A trip creator currently has no way to let anyone else see or contribute to their trip — every
screen reads and writes `localStorage` on one device. This feature gives the creator a single
shareable link for their active trip so they can send it to friends. Generating the link is also
the moment the trip stops being purely a local, single-device record and gets a server-side
counterpart that a link recipient will (in feature 017) be able to resolve. This feature covers
only the creator's side of that moment: creating the link, viewing it again, replacing it, and
having it invalidated when the trip it points to goes away.

### 1.2 Actors & preconditions

- **Actor:** the trip creator — the one device that set up the currently active trip (features
  001/002/003). No other actor exists in the product yet: a participant-side role and view are
  introduced by feature 019, and joining a link is feature 017. Until those land, this device is
  structurally the only one that can ever see the invite/generate/regenerate action, because it is
  the only device that has the trip at all.
- **Precondition (all scenarios):** an active trip exists (`getTrip()` is non-null) — every route
  this feature touches already redirects to `/` when it is not, per the pattern in every existing
  route (REFERENCE.md §4).
- **Precondition (regenerate, reopen, refresh, edit, copy scenarios):** a link has already been
  generated for this trip in this browser.

### 1.4 Data touched

- **Trip** (business entity): destination country, currency, dates, budget — the fields that exist
  locally today (`lib/types.ts`'s `Trip`). Generating a link takes a snapshot of these into the new
  server-side record. This feature does not define what happens to that server snapshot when the
  creator later edits the trip locally (see §1.6 and Open Questions).
- **Share link**: a new business concept — a unique, opaque token identifying a trip, plus whatever
  private credential lets the creator's device prove it is the creator on later calls (regenerate).
  Both are new; neither exists anywhere in the app today.

### 1.5 Edge cases & negative paths

- Network failure during generation → friendly error, trip stays unshared. **[in spec]** (BR-016-09/10)
- Double-tap / rapid repeat of the generate action → exactly one link. **[in spec]** (BR-016-11)
- Regenerating invalidates the prior link. **[in spec]** (BR-016-04/05)
- Starting a new trip tears down the outgoing trip's link. **[in spec]** (BR-016-06/06a)
- Refresh after generating → link still shown. **[in spec]** (BR-016-12)
- Network failure during **regenerate** (as opposed to first generation) — the Gherkin only states
  the failure scenario for first-time generation. **[derived]** — treated identically: friendly
  error, the previous link stays valid and displayed (regenerate is all-or-nothing; a failed
  attempt must not silently drop the working link the creator already has).
- Attempting to generate a link with no active trip — structurally impossible, since every route
  that could host this action already redirects home when `getTrip()` is `null`. **[derived]** — no
  new handling needed, existing route-gate pattern covers it.
- The server accepts a regenerate/delete call for a trip whose creator credential doesn't match
  (e.g. a stale or tampered credential) — **[derived]**: rejected by the server (see BR-016-15/19),
  surfaced to the creator's own device only if its own stored credential is somehow lost or corrupt;
  see Open Questions for how narrow this needs to be given no other actor can reach the action yet.
- What "reset app data" (013, already built) does to a generated link — **[derived]**: a full data
  reset must not leave a dangling, still-valid link nobody local remembers generating; see Design
  §2.2 for the change this requires to `resetAppData()`.

### 1.6 Out of scope

(carried verbatim from the feature file, since the BA must not re-litigate scope already settled there)

- Sharing the link via the device's native share sheet (copy-to-clipboard only).
- Any participant-facing behavior — opening the link and joining is feature 017.
- Viewing or managing who has joined via the link — feature 019.
- Link expiry by time or by number of uses.
- Working offline for generate/regenerate.

Additionally, out of scope **by this analysis** (not stated in the feature file, but excluded
because no scenario in it exercises them):

- Keeping the server-side trip snapshot in sync with later local edits (BR-016-07/08 only requires
  the *link* to survive an edit unchanged, not that the server copy reflects the edit — see Open
  Questions §7).
- Moving existing recorded expenses to the server when a link is first generated — none of this
  feature's scenarios mention expenses; a joiner seeing expense data is necessarily downstream of
  feature 017 at the earliest.
- Any UI for a friend/participant — there is no such user yet.

## 2. Technical specification — SA

### 2.1 Approach

Introduce the smallest server surface that satisfies the nine scenarios: one Prisma model
(`Trip`) in a new Neon-backed Postgres database, three Route Handlers under `app/api/trips/`
(create, regenerate, delete), and a new client-side domain module that wraps those three calls
behind a small result type mirroring the existing `SaveResult` convention. The creator's own
device keeps using `lib/storage.ts`/`localStorage` exactly as it does today for the trip it set up
(001/002/003) and for expense recording (005) — nothing about the existing local-first experience
changes. What's added is a second, small local record — a "share pointer" — that remembers three
opaque strings once a link exists: the server trip's id, the link's public token, and a private
credential that proves this device is the creator. `lib/storage.ts` gains this as a fifth key,
following its existing get/save-with-`SaveResult` shape.

Authentication for regenerate/delete is a shared-secret header (`x-creator-token`), checked against
the value stored on the `Trip` row. This is a deliberately minimal mechanism — not a session or
account system — appropriate because no other identity concept exists in the app yet and none of
this feature's scenarios require one; it is also exactly the credential 017 will need to reuse
architecturally when participants get their own per-trip device identity later.

Double-submission (BR-016-11) is handled client-side: the generate control tracks an in-flight
flag in a `useRef` (not `useState`, whose update is not guaranteed synchronous before a second
click handler runs in the same tick) and ignores a second invocation while a request is
outstanding.

### 2.6 Non-functional notes

- Mobile-first: `ShareTripLink` follows the existing Settings-page section pattern (§4 rhythm,
  `gap-6` between sections) — no new layout primitive.
- Offline: per BR-016-18, generate/regenerate are allowed to fail outright when offline; no
  offline queueing or optimistic local state is introduced. A failed `fetch` (thrown `TypeError`)
  is caught and mapped to the same friendly error as a non-2xx response.
- Local-storage failure modes: `sharedTripLink` follows the exact fallback/error conventions
  already in `lib/storage.ts` (`null` fallback, `SaveResult` on write failure) — no new failure
  mode class is introduced.
- **Next.js check**: confirmed against `node_modules/next/dist/docs/01-app/01-getting-started/15-route-handlers.md` —
  Route Handlers are plain `export async function POST/DELETE(request)` inside `route.ts` files
  under `app/`, cannot share a URL segment with a `page.tsx`, and a dynamic segment's params are
  typed via the global `RouteContext<'/api/trips/[id]'>` helper and are a `Promise` (`await
  ctx.params`), consistent with the `params`-is-a-Promise rule already noted in REFERENCE.md §5.
  `app/api/trips/route.ts` sits at a segment with no `page.tsx`, so there is no conflict.

Notes on changes from the source Gherkin:

- AC-016-03 and the source's single "regenerate" scenario are split: AC-016-03 covers the
  observable UI change (new link shown), AC-016-04 covers the "previous link no longer works"
  clause separately, since the two are independently verifiable and the second needs the server,
  not the UI, as its point of observation (G3 requires atomic, single-assertion-family scenarios).
- AC-016-05 similarly splits the new-trip-invalidation scenario into the server-side rejection
  (mirroring AC-016-04) and adds the derived clause that the new trip starts with no link.
- AC-016-08 and AC-016-09 are `[derived]` additions for edge cases from §1.5 that the source
  Gherkin's single "Link generation fails" scenario did not cover (it only covers first
  generation, not regeneration) and the double-tap scenario's own missing assertion of *how* one
  link is guaranteed (request count, not just outcome).
- AC-016-11 makes "the link is copied" and "I see a confirmation" both explicit, since the source
  scenario's "I tap the copy action... the link is copied so I can paste it elsewhere" bundles an
  unobservable clipboard-content assertion with an observable UI-confirmation one; both are kept
  but the confirmation is what a Playwright test can actually check (clipboard content is also
  checkable via the Clipboard API grant in Playwright — mapped in §4).

## 7. Open questions & risks

1. **No test/dev database exists in this repo yet.** This is the first feature requiring
   `DATABASE_URL` to point at a real reachable Postgres instance (Neon). `/writing-plans` and
   `/sdd` cannot make `npm run build` or any Playwright spec in §4 pass without one. **This blocks
   implementation start, not just this document** — the user needs to provision a Neon project (or
   confirm an existing one) and supply `DATABASE_URL` before `/writing-plans` schedules a task that
   runs `npx prisma migrate` or before `/sdd` executes any task touching `app/api/trips/*`.
2. Whether the server's trip snapshot should ever be re-synced after a local edit (Challenge #1) is
   left unresolved for 016 and should be revisited when feature 017 (join) defines what a joiner
   actually sees.
3. Server-side idempotency for link creation (Challenge #3) beyond the client-side guard is not
   built; acceptable for now since no scenario requires it, but worth a hardening pass once 017
   introduces real concurrent, multi-device traffic against these endpoints.
4. `resetAppData()` (TS-016-07) clears the local pointer but does not delete the server row,
   leaving an orphaned `Trip` record after a reset. Accepted per §1.5/TS-016-07's own reasoning
   (v2 has no idle-time expiry by design — Assumption 5 — so an orphan is inert, not a live bug),
   but flagged in case a future data-hygiene pass wants a cleanup job.
5. What happens to a `Trip` row if `POST /api/trips` succeeds server-side but the response never
   reaches the client (e.g. connection drop after the write) — the client sees the failure branch
   (BR-016-09/10) and creates the local pointer only on a parsed success response, so it correctly
   never claims a link exists, but the orphaned server row persists with no local record. Same
   accepted-risk reasoning as #4 applies (no expiry model in v2).
