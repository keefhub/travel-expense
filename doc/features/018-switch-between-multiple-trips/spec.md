## 1. Business analysis — BA

### 1.1 Purpose

Features 016 and 017 gave a device two ways to belong to more than one trip: it can generate a
share link for its own trip (becoming that trip's "creator"), and it can join any number of other
people's shared trips via their links (becoming a "joined" participant on each). Nothing today lets
a device actually move between these trips once it belongs to more than one — `/` always shows the
device's own local trip, and the only way to see a joined trip again is to still have its exact
`/join/{token}` URL. This feature adds the switcher: a way to see every trip a device belongs to,
labeled by the device's relationship to each, and to move between them — while making sure a
shared trip that has stopped existing quietly drops out of the list, an offline attempt to view a
shared trip fails honestly instead of showing stale or wrong data, and switching away from an
in-progress expense entry doesn't silently discard it.

### 1.2 Actors & preconditions

- **Actor:** any device that belongs to at least one trip — the same device could be a trip's
  creator (001/002/003 plus 016), a joiner of one or more shared trips (017), both at once, or (a
  case this feature must not break) a device that has only ever joined shared trips and has no
  local trip of its own at all (017 §1.2 explicitly allows this).
- **Precondition (all scenarios):** at least one trip is reachable from this device — either
  `getTrip()` is non-null, or `getJoinedTrips()` is non-empty, or both.
- **Precondition (scenarios exercising the switcher UI itself):** the device belongs to **more
  than one** trip in total, per BR-018-04.

### 1.4 Data touched

- **Trip** (local, read-only): `getTrip()` — determines whether an "own"/"created" entry exists at
  all, and supplies that entry's label.
- **SharedTripLink** (local, read-only): `getSharedTripLink()` — distinguishes "own trip" from
  "created" for the local trip entry (BR-018-10). This feature never writes it.
- **JoinedTrip[]** (local, read **and** write): `getJoinedTrips()`/`saveJoinedTrips()` — supplies
  every "joined" entry. This feature writes to it in exactly two cases: refreshing a joined trip's
  cached summary after a successful revalidation, and removing an entry once its trip is confirmed
  gone (BR-018-06).
- No new persisted storage key. `resetAppData()` (013) already clears all three of the above keys
  (verified in `lib/storage.ts`, read directly — see §2.5), so a full reset needs no change here.

### 1.5 Edge cases & negative paths

- A device with joined trips but **no local trip at all** lands on `/` → must not be stuck at
  `TripSetupForm`; see BR-018-12. `[derived]`
- A device belonging to **zero** trips (a fresh install, before trip setup) → the switcher must not
  render anything and must not error. `[derived]`
- A local trip that **has** been shared (a `sharedTripLink` exists) but that nobody has joined yet
  → total trip count is still 1 (the local trip only) → switcher stays hidden per BR-018-04, exactly
  as an unshared trip would. `[derived]`
- A joined trip's token stops resolving because the creator **regenerated** the link (rather than
  deleting the trip outright) → indistinguishable from deletion at the HTTP level (both are a `404`
  from `GET /api/join/[token]`, per feature 017's `resolveTripByToken`); both are treated identically
  by BR-018-06, mirroring feature 017's own BR-017-06 collapsing of causes. `[derived]`
- The switcher itself is opened while offline → must render the list from local cache without
  attempting any network call and without erroring; only the act of switching **to** a joined trip
  depends on connectivity (BR-018-08). `[derived]`
- Switching to the device's own/created trip is **never** gated on connectivity, even while offline,
  since it is pure local data — contrast with BR-018-08, which applies only to joined trips.
  `[derived]`
- A device revisits a joined trip's view after being offline and coming back online (e.g. a stale
  tab, reloaded later) → must re-resolve successfully rather than staying stuck on a previously
  rendered offline message. `[derived]`

### 1.6 Out of scope

(carried verbatim from the feature file, since the BA must not re-litigate scope already settled there)

- Leaving a shared trip or removing another participant — that is feature 019.
- Two browser tabs on the same device staying in sync when one switches trips.
- Any server-side concept of a "default" or "last active" trip shared across devices — the
  last-viewed trip is remembered per device only.
- Merging or comparing data across multiple trips at once.

Additionally, out of scope **by this analysis** (not stated in the feature file, but excluded
because no scenario in it exercises them):

- Any expense, budget, or category data for a joined shared trip — none of that exists until
  feature 020, exactly as feature 017 already established (see BR-018-13).
- Real-time or push notification of a trip's deletion — detection is lazy, on the next attempt to
  view that trip, not instant for every device holding it (see Contrarian Review #4).
- Any change to `/join/[token]`'s own already-shipped behavior (in particular, its shortcut of
  skipping the network entirely when a local `JoinedTrip` match already exists) — this feature adds
  a **separate** route for switcher-driven viewing rather than modifying feature 017's tested one;
  see §2.1 and Contrarian Review #3.
- Managing or renaming the participant name a joined trip was joined under — that is feature 019's
  territory if it exists at all; this feature only ever reads the cached `participantName`.

## 2. Technical specification — SA

### 2.1 Approach

Add a new, always-mounted header component, `TripSwitcher.tsx`, that renders nothing unless the
device belongs to more than one trip (BR-018-04), and otherwise offers a modal listing every trip
labeled by role, each rendered as a plain in-app link. Add a new route, `/trips/[token]`, and its
component `SharedTripView.tsx`, which is how a joined trip is viewed **from the switcher** — it is
deliberately a new route rather than a modification of feature 017's `/join/[token]`, because the
two need to behave differently: reopening a raw join link is meant to skip the network entirely once
already joined (feature 017's BR-017-09, already shipped and tested), while switching **to** a
joined trip must always revalidate over the network, because that is the only way this feature can
honestly satisfy both "an offline switch shows a connectivity message" (BR-018-08) and "a deleted
trip disappears from the switcher" (BR-018-06) — a purely local render could do neither. Patch
`app/page.tsx`'s home route so a device with no local trip but at least one joined trip lands on
that joined trip instead of being forced into `TripSetupForm` (BR-018-12) — the one behavior change
this feature makes to an already-shipped file outside of what it adds.

No new storage key is introduced, and "the last-viewed trip survives a refresh" (BR-018-09) needs no
dedicated code at all: the local trip lives at `/` and each joined trip lives at its own
`/trips/{shareToken}` URL, so which trip is shown is simply a function of the current URL, which the
browser already preserves across a refresh. Likewise, "switching away from unsaved expense-form
input warns first" (BR-018-07) needs no new warning code: `hooks/useUnsavedChangesWarning.ts` (011)
already intercepts **any** in-app anchor click while its `isDirty` argument is true, regardless of
destination, and every switcher entry is rendered as a plain `<Link>` — so a click on a switcher
entry from a dirty `/expenses/new` is already caught by the existing document-level capture listener
exactly as a `BottomNav` click would be. Confirmed by reading `hooks/useUnsavedChangesWarning.ts` in
full (see §2.5): its click handler walks up from `event.target` to the nearest `a[href]`, with no
special-casing of which component rendered that anchor.

### 2.6 Non-functional notes

- Mobile-first: `TripSwitcher`'s modal follows `AddCategoryModal.tsx`'s existing
  `role="dialog" aria-modal="true"` fixed-overlay convention (design.md's established modal
  pattern); the trigger sits in a small header row above `main`, not inside `BottomNav` (which stays
  a fixed 4-item nav per feature 015 and is not extended here).
- Offline: the switcher's own list render is 100% local-storage-driven and never blocks or errors
  offline (§1.5); only `SharedTripView`'s always-revalidate fetch is connectivity-gated, per
  BR-018-08. This mirrors the existing asymmetry OVERVIEW already establishes between "the app works
  offline" (local trips) and "requires connectivity" (any shared-trip network action).
- Local-storage failure modes: `SharedTripView`'s two writes (refreshing a cached summary, pruning a
  deleted entry) go through the existing `saveJoinedTrips`/`SaveResult` path; a write failure there
  is a pre-existing, already-handled failure mode (same class as feature 017's `persisted: false`
  case) and needs no new handling — a failed prune simply leaves the stale entry to be pruned again
  on the next visit, which is an acceptable eventual-consistency gap, not a crash.
- **Next.js check**: `app/trips/[token]/page.tsx` uses the same `use(props.params)`
  Promise-unwrapping dynamic-segment pattern already shipped twice in this repo
  (`app/expenses/[id]/page.tsx`, `app/join/[token]/page.tsx`) and documented in REFERENCE.md §5; no
  new Next.js API is introduced. `app/trips/` is a new top-level segment with no sibling
  `page.tsx`/`route.ts` conflict (verified via `git ls-files app/`).

  (switching **to** a joined trip, which is connectivity-gated) and AC-018-02 (switching **back to**

  plain `/` navigation), so G3 requires them as separate, independently-observable scenarios rather
  than one bundled assertion.
- AC-018-01 rewords the source's "I see that trip's dashboard and data" to "that trip's own
  summary" for a **joined** trip specifically — the underlying behavior is unchanged from what
  feature 017 already ships (no financial dashboard exists for a shared trip yet); see BR-018-13 and
  Contrarian Review #2. AC-018-02, which covers the **local** trip, keeps "dashboard and data"
  verbatim since that trip genuinely does render the full `Dashboard.tsx`.
- The source's "switcher shows my relationship to each trip" scenario, which lists three
  simultaneous roles ("my own solo trip, a shared trip I created, and a shared trip I joined"), is
  split into AC-018-11 and AC-018-12 — one local trip role plus one joined trip role each — because
  the product's own data model (BR-018-05) makes "own solo trip" and "created shared trip" mutually
  exclusive states of the *same* local trip, not two trips a device can hold at once; see Contrarian
  Review #1 for the full reasoning.
- AC-018-05, AC-018-13, and AC-018-14 are `[derived]` additions for the edge cases in §1.5 that the
  source Gherkin's seven scenarios don't themselves state but that this feature's own premise
  (a switcher over "every trip a device belongs to") makes unavoidable to define.

## 7. Open questions & risks

1. **(Challenge #1)** The source Gherkin's "own solo trip, a shared trip I created, and a shared
   trip I joined" scenario describes three simultaneous trips that the shipped 016/017 data model
   cannot actually produce for one device (only one local trip exists at a time, either unshared or
   shared). This spec reinterprets the scenario as needing both realizable role pairs covered
   instead. This is the single biggest judgment call in this document — worth the user's explicit
   confirmation before implementation, the same way feature 017 flagged its own biggest judgment call
   (the "joined" view's scope) in its own Open Questions.
2. **(Challenge #3)** `/trips/[token]` and `/join/[token]` now have deliberately different
   connectivity behavior for what a user would think of as "the same trip" — one always revalidates,
   the other skips the network once already joined. Both behaviors are individually required by
   already-shipped or newly-specified scenarios, but the divergence itself is easy to "clean up"
   accidentally in a later feature without realizing it would regress one side or the other.
3. **(Challenge #4)** A shared trip's deletion is only detected the next time someone actually
   selects it from the switcher, not proactively when the switcher is opened. Accepted for now as
   the simpler design; revisit if a "stale entry sitting in the switcher" complaint ever surfaces in
   practice.
4. **(Challenge #5)** Which joined trip a device with no local trip of its own is shown first
   (`app/page.tsx`'s redirect, TS-018-05) is array order — arbitrary but deterministic. No scenario
   specifies a preference; flagged in case the user wants a different rule (e.g. most-recently-joined)
   once this case is common enough to matter.
